### 20. External Reference Notes (2026-08-08)

สรุปจาก research ภายนอก 3 ระบบที่ทำเพื่อหา pattern มาใช้ในการออกแบบ [§6](ARCHITECTURE.md#6-session--conversation-persistence)/[§7](ARCHITECTURE.md#7-long-horizon-autonomous-execution--run-until-done-mode)/[§11.2](ARCHITECTURE.md#112-agent-manifests--declarative-setup-model) ข้างต้น — เก็บไว้เป็นภาคผนวกสำหรับ provenance/เหตุผลอ้างอิง ไม่ใช่เนื้อหาสถาปัตยกรรมหลัก **หลักการเลือกว่าอะไร borrow ได้**: ทั้ง 3 ระบบมี scale/target user ต่างจากระบบนี้มาก (Skywork = cloud multi-tenant SaaS, Posit Workbench = enterprise multi-user server) — ไม่ copy ตรงๆ แต่ดึงเฉพาะ *mechanism* ที่ transferable มาที่ single-user desktop app จริงๆ

#### 20.1 Claude / Claude Agent SDK

| Pattern ของ Claude | สถานะในระบบนี้ |
|---|---|
| Subagent คืนแค่ summary กลับ parent context ไม่ใช่ transcript เต็ม | **ตรงกับ [§5.3](ARCHITECTURE.md#53-subagent-context-isolation) ที่ตัดสินใจไว้แล้วตั้งแต่ต้น** — งานวิจัยรอบนี้ยืนยันว่าเป็นแนวทางเดียวกับที่ Anthropic ใช้จริงใน production multi-agent research system ของตัวเอง (isolated subagent ทำให้ eval ดีขึ้น 90.2% เทียบ single-agent) เพิ่มความมั่นใจว่า design เดิมมาถูกทาง ไม่ต้องเปลี่ยน |
| Agent/Skill/Hook/MCP ทั้งหมดประกาศผ่านไฟล์ config ไม่ hardcode ในโปรแกรม | ตรงกับ `skill-registry` (SKILL.md frontmatter) ที่มีอยู่แล้ว แต่ agent persona เดิมยัง hardcode เป็น Rust const — ช่องว่างที่ [§11.2](ARCHITECTURE.md#112-agent-manifests--declarative-setup-model) แก้ |
| Compaction เป็น server-side primitive: สรุป message เก่า, **ทิ้ง raw tool-output เก่าก่อนเป็นอันดับแรก** (ถูกที่สุด, agent แทบไม่ต้องอ่านซ้ำ), คำสั่งที่ให้ตอนต้น session อาจหายหลัง compact เลยต้องมี durable rule file แยกต่างหาก | ระบบนี้ไม่มี compaction เลยตอนนี้ (ไม่มีแม้แต่ multi-turn history — ดู [§6](ARCHITECTURE.md#6-session--conversation-persistence)) — เอา insight นี้ไปใช้ตรงใน [§7](ARCHITECTURE.md#7-long-horizon-autonomous-execution--run-until-done-mode) |
| Cognition (ผู้สร้าง Devin) เตือนว่า multi-agent แบบ isolated-context ใช้ไม่ได้กับงานที่ coupled กันแน่น (เช่นแก้โค้ดหลายไฟล์ที่พึ่งกัน) — ต้อง full shared context ไม่ใช่ summary | **ตรงกับ decision D3 ที่มีอยู่แล้ว** ([§17.2](LOG_ARCHIVE.md#232-โค้ดจริงเบี่ยงจากแผนเดิมของเอกสารนี้เอง-บันทึกดั้งเดิม-2026-08-08)) — เหตุผลที่ไม่แยก `code-agent` เป็น subagent ต่างหากแต่ให้วิ่งผ่าน `Orchestrator` เดียวกับ context เต็มตรงกับ finding นี้เป๊ะ ยืนยัน design เดิมถูกแล้ว |
| Plan Mode: โหมด "คิด/สำรวจได้ แต่ห้าม execute" แยกจาก autonomy threshold | ตรงกับ `AutonomyMode::PlanOnly` ที่มีอยู่แล้ว ([§5.4](ARCHITECTURE.md#54-plan-only-mode)) |
| Workflow tool: script กำหนด fan-out/fan-in ของ subagent หลายสิบ-ร้อยตัวแบบ deterministic (pipeline/parallel primitives) | เกินสเกลที่ระบบ personal นี้ต้องการ — **ตัดสินใจไม่ borrow มาทั้งชุด**, เอาแค่แนวคิด "pipeline vs parallel มี tradeoff ต่างกันชัดเจน" ไปใช้ตอนออกแบบ [§7](ARCHITECTURE.md#7-long-horizon-autonomous-execution--run-until-done-mode)'s task execution loop |

Source: research agent report อิงจาก Claude Platform Docs (compaction, context editing), Anthropic Engineering blog ("Effective context engineering for AI agents", "How we built our multi-agent research system", "Building effective AI agents"), Cognition "Don't Build Multi-Agents"

#### 20.2 Skywork.ai

| Pattern ของ Skywork | สถานะในระบบนี้ |
|---|---|
| Hierarchical planner → specialized subagent (Deep Analyzer/Deep Researcher) รันขนาน | ตรงกับ [§3](ARCHITECTURE.md#3-layered-architecture) Layer 2/3 ที่วางไว้ (Master Agent → SA1-4) แต่ **ยังไม่ implement จริง** — ปัจจุบันมนุษย์เลือก agent เองผ่าน dropdown ไม่มี auto-routing เลย (ยืนยันจาก `app-tauri/src/lib.rs:168-177`'s comment ที่บอกตรงๆ ว่า "still no master-agent routing layer") |
| "Act → Observe → Optimize → **Remember**" loop — มี memory subsystem เก็บ trace/summary ข้าม session โดยเฉพาะ | ตรงกับช่องว่างใน [§6](ARCHITECTURE.md#6-session--conversation-persistence)/[§7](ARCHITECTURE.md#7-long-horizon-autonomous-execution--run-until-done-mode) — "Remember" step ของเขาคือสิ่งที่ระบบนี้ไม่มีเลยตอนนี้ |
| Background cloud execution ที่รอดจากปิด tab/browser | Mac mini เป็น local process อยู่แล้ว ไม่มี "ปิด tab" concept แบบ SaaS — แต่ insight ที่ borrow ได้คือ **agent session ต้องรอดจากปิด/เปิดแอปใหม่** เหมือนกัน (ผ่าน DB persistence ไม่ใช่ cloud) |
| "Studio panel" โชว์ live workflow visualization + task list ระหว่างรัน | ตรงกับ [§13.1](ARCHITECTURE.md#131-live-monitor--card-model--parallel-execution) Live Monitor's card model ที่มีอยู่แล้ว — [§7](ARCHITECTURE.md#7-long-horizon-autonomous-execution--run-until-done-mode) จะขยายให้โชว์ task list ทั้ง session ไม่ใช่แค่ step ปัจจุบัน |
| **ไม่มี explicit approval gate ต่อ step** — ใช้แค่ "automatic clarification" แทน hard stop, และเป็นจุดที่ review บ่นเรื่อง trust/cost transparency (billing complaint เยอะ) | **ตัดสินใจไม่ borrow** — HITL Gate ([§5.2](ARCHITECTURE.md#52-hook-chain-gate-architecture)) เป็น differentiator ที่ตั้งใจเก็บไว้ ยิ่งเห็น weak spot ของ Skywork ยิ่งมั่นใจว่า decision เดิมถูกทาง โดยเฉพาะกับ long-horizon mode ที่เสี่ยง cost/action บานปลายได้ง่ายถ้าไม่มี gate |

Source: research agent report อิงจาก skywork.ai product pages, github.com/SkyworkAI/DeepResearchAgent (open-source framework, MIT license), third-party reviews (eesel.ai, aiagentsdirectory.com) — **ข้อควรระวัง**: บริษัทไม่เปิดเผยว่า production consumer app ใช้ stack เดียวกับ open-source framework เป๊ะหรือไม่ ต้องถือเป็น "น่าจะเกี่ยวข้อง" ไม่ใช่ "ยืนยันแล้ว"

#### 20.3 Posit Workbench

| Pattern ของ Posit Workbench | สถานะในระบบนี้ |
|---|---|
| "Launcher" เป็น broker แยกต่างหากจาก execution backend — interface เดียว (submit/status/kill/logs), backend เป็น plugin สลับได้ (Local/Slurm/K8s) โดย caller ฝั่งบนไม่ต้องรู้ว่าข้างล่างเป็นอะไร | **แนวคิดที่ borrow ได้สำหรับอนาคต**: `executor` ตอนนี้ผูกกับ local subprocess ตรงๆ ([§12](ARCHITECTURE.md#12-execution-engine-mac-mini)) ตาม decision "ไม่ dispatch ไป GX10 ใน v1" ([§16](LOG.md#16-decisions-log)) — ถ้าวันหนึ่งต้องการ dispatch ไป GX10 จริง (v2+) แนะนำเพิ่ม thin `ExecutionBackend` trait ตอนนั้น (ไม่ใช่ตอนนี้) แทนที่จะรื้อ `executor` ทั้งก้อน — บันทึกไว้เป็น future-proofing note ไม่ใช่ task ของรอบนี้ |
| Suspend/resume ใช้ได้เฉพาะ runtime ที่ serialize state ได้จริง (R session ทำได้เพราะ object graph เป็น `.rds`-serializable, Jupyter/VS Code kernel ทำไม่ได้ ต้อง kill/restart อย่างเดียว) | บทเรียนสำคัญ: "pause" ต้องแยก 2 code path ตาม capability ของสิ่งที่ pause ไม่ใช่ assume ว่า universal pause มีจริง — **ระบบนี้จริงๆ ได้เปรียบกว่า**: pause/stop ผ่าน process-group signal (SIGSTOP/SIGCONT/SIGTERM, [§12](ARCHITECTURE.md#12-execution-engine-mac-mini)) ทำงานกับ subprocess ใดก็ได้โดยไม่ต้องพึ่ง in-memory serialization ของ runtime นั้นๆ — **ยืนยัน design เดิมถูกแล้ว ไม่ต้องเปลี่ยน**, แค่ต้องขยายแนวคิด pause ให้ครอบคลุมระดับ "long-horizon session loop" ด้วยใน [§7](ARCHITECTURE.md#7-long-horizon-autonomous-execution--run-until-done-mode) (คนละชั้นจาก process pause) |
| Resource profile เป็นเมนูที่ admin กำหนดไว้ล่วงหน้า (เช่น "1 CPU/2GB"–"30 CPU/240GB") ให้ user เลือก แทนกรอกค่าอิสระ | เกิน scope ของ single-user local app ([§12.1](ARCHITECTURE.md#121-การใช้ทรัพยากร-local-compute-cpugpunpu-บน-mac-mini) ใช้ทรัพยากรเครื่องเดียวเต็มที่อยู่แล้ว ไม่มี multi-tenant ให้ quota) — **ตัดสินใจไม่ borrow** |
| Admin Dashboard: ตาราง session ทั้งหมด (state/CPU/mem/kill/suspend ต่อแถว) | insight ที่ borrow ได้บางส่วน: หน้า "process manager" แบบย่อ (ตาราง active subprocess/agent session + kill control) มีประโยชน์แม้ single-user — อยู่ใน backlog [§19](#237-phase-d--backlog-เดิม-p2) Phase D รวมกับ [§17.1](LOG_ARCHIVE.md#231-feature-gaps--user-feedback-audit-บันทึกดั้งเดิม-2026-08-08) แถว #21 ที่เป็น PARTIAL อยู่แล้ว |

Source: research agent report อิงจาก docs.posit.co (Session Management, Job Launcher Configuration, Kubernetes Plugin, Administrative Dashboard, Session Timeout)

### 21. ข้อค้นพบใหม่จาก UX/Architecture Review (2026-08-09)

Review รอบนี้ทำ 3 อย่าง: (1) ค้นคว้า best practice ภายนอกเรื่อง UX/UI และ workflow ของระบบ personal AI agent ที่ทำ coding/data-analysis/document-generation ผ่าน Desktop app + chat-bridge, (2) audit source code จริงทั้ง `frontend/src` และ `crates/` (ไม่ใช่แค่เทียบกับเอกสาร) เพื่อหา bug/ความไม่สอดคล้องระหว่าง frontend-backend, (3) แยก+เรียบเรียง `ARCHITECTURE.md` ฉบับรวมเดิมออกเป็น 3 ไฟล์ ตารางด้านล่างคือบั๊ก/ความเสี่ยงที่ยืนยันจริงต่อ source code ที่ยังไม่เคยถูกบันทึกใน [§18 Known Bugs](LOG.md#18-known-bugs) เดิม
