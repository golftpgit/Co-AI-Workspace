### E.3.1 merge layer ให้ผลอะไรจริง — วัดตอน P2.2 (แก้ข้อสันนิษฐานเดิม)

ตอนตั้ง P2.2 เขียน Done-when ไว้ว่า "วัด BM25 recall เทียบก่อน/หลัง merge layer" โดยสันนิษฐานว่า recall จะดีขึ้น **วัดจริงแล้วไม่ใช่** — บน corpus 10 เอกสาร / 5 query (`Tests/KnowledgeTests/RetrievalMeasurementTests.swift`):

| | recall@1 | MRR |
|---|---|---|
| ไม่มี merge layer | **1.00** | **1.00** |
| มี merge layer | **1.00** | **1.00** |

เหตุผลคือสิ่งที่ E.3 เขียนไว้เองอยู่แล้ว: index กับ query ผ่าน tokenizer ตัวเดียวกัน `โลจิสติก` จึงแตกเป็น `โล|จิ|สติ|ก` เหมือนกันทั้งสองฝั่งและยังเจอเอกสารเดิม

**สิ่งที่ merge layer แก้จริงคือ precision** — ค้น `สติ` (คำไทยแท้ แปลว่าความรู้สึกตัว) โดยไม่มี merge layer ได้เอกสารเรื่อง logistic regression ติดมาด้วย เพราะมันมี fragment `สติ` อยู่ข้างใน พอเปิด merge layer เอกสารนั้นหายไปและเหลือเฉพาะเอกสารที่พูดเรื่องสติจริงๆ · ตรวจเพิ่มด้วยว่า merge layer **ไม่เพิ่ม** ผลลัพธ์ที่ไม่มี merge layer หาไม่เจอ (subset check ทุก query)

## E.11 embedding model ที่ "ตาบอดภาษาไทย" — เจอตอน P2.4 (2026-08-11)

`text-embedding-nomic-embed-text-v1.5` ที่ LM Studio เสิร์ฟ **คืน vector ตัวเดียวกันเป๊ะทุกครั้งสำหรับ input ภาษาไทย** ไม่ว่าข้อความจะต่างกันแค่ไหน:

| input | vector 3 ตัวแรก |
|---|---|
| `การให้อินซูลินในผู้ป่วยเบาหวาน` | `-0.00297, 0.00135, -0.15952` |
| `การควบคุมระดับน้ำตาลในเลือด...` | `-0.00297, 0.00135, -0.15952` |
| `การปนเปื้อนโลหะหนักในแหล่งน้ำดิบ` | `-0.00297, 0.00135, -0.15952` |
| `insulin therapy in diabetic patients` | `0.00015, 0.06579, -0.14905` ✅ ต่างกันปกติ |

ไม่ใช่ปัญหา batch — ยิงทีละ request ก็ได้ผลเดียวกัน · ภาษาอังกฤษทำงานปกติ → tokenizer ของโมเดลไม่รู้จักสคริปต์ไทยเลย

**ทำไมอันตราย**: cosine ระหว่าง vector ที่เท่ากันคือ 1.0 ทุกคู่ ระบบจะ "ค้นเจอ" เสมอและจัดอันดับมั่วโดยไม่มี error ให้เห็น — เป็นการพังแบบเงียบที่แย่กว่าพังดังๆ · **ยืนยันการตัดสินใจของ P2.1 ([E.10](#e10-d-2--เลือก-embedding-model-วัดจริง-ปิดแล้ว)) ว่าทำไมต้อง `bge-m3`**

**สิ่งที่ทำ**: `diagnose(_ embedder:)` ใน `Knowledge` ยิงประโยคที่ต่างกันชัดเจน 2 ประโยคต่อสคริปต์ (ไทย + ละติน) ถ้าได้ vector เท่ากันเป๊ะ = `.blind(to:)` ไม่ใช่ threshold แต่เทียบว่า "เท่ากันเป๊ะ" เพราะโมเดลที่แค่มองว่าสองประโยคคล้ายกันคือทำงานถูกแล้ว — P2.3 จะไม่ยอม index ผ่าน embedder ที่อยู่ในสถานะนี้

## E.12 Vision OCR รองรับไทยแค่โหมดเดียว — ตรวจตอน P2.3 (2026-08-11)

`VNRecognizeTextRequest.supportedRecognitionLanguages()` บนเครื่องนี้:

- `.accurate` → **30 ภาษา รวม `th-TH`** ✅
- `.fast` → `en-US, fr-FR, it-IT, de-DE, es-ES, pt-BR` เท่านั้น — **ไม่มีไทย**

แปลว่าสำหรับคลังเอกสารไทย `.accurate` ไม่ใช่ตัวเลือกเรื่องคุณภาพแต่เป็นทางเดียวที่ใช้ได้ · ถ้าเผลอตั้ง `.fast` เพื่อความเร็ว หน้าที่เป็นภาษาไทยจะคืนค่าว่างโดยไม่มี error → `TextRecognizer` ล็อก `.accurate` ไว้ตายตัวและ expose `supportedLanguages` ให้ UI บอกผู้ใช้ได้ว่าเครื่องนี้อ่านภาษาอะไรได้บ้าง

รันจริงแล้วบนเครื่องนี้ ([spikes/EmbeddingRuntime/](../spikes/EmbeddingRuntime/FINDINGS.md)):

| เช็ค | ผล |
|---|---|
| โหลด bge-m3 ผ่าน `MLXEmbedders` | ✅ 1024 มิติ ตรงกับที่ P2.1 ล็อก |
| อ่านภาษาไทย | ✅ ประโยคใกล้กัน 0.764 vs ไม่เกี่ยวกัน 0.379 (ต่างจาก nomic ใน [E.11](#e11-embedding-model-ที่-ตาบอดภาษาไทย--เจอตอน-p24-2026-08-11) ที่คืน vector เดียวกันหมด) |
| ความเร็ว | ✅ **232 chunk/วินาที** → re-embed 10,000 chunk ใช้เวลาไม่ถึงนาที (โหลดครั้งแรก ~43 วิรวมดาวน์โหลด) |

**🔴 กับดักที่เจอ — "bge-m3" สองบิลด์ให้ vector space ที่ตั้งฉากกัน**

เทียบ vector ของประโยคเดียวกันระหว่าง MLX conversion กับ GGUF ที่ LM Studio เสิร์ฟ: cosine = **−0.0008, −0.0068, 0.0512** ไม่ใช่ "ต่างกันนิดหน่อย" แต่คือ**ไม่เกี่ยวข้องกันเลย**

ใครที่คิดว่าชื่อโมเดลคือสิ่งที่สำคัญ จะสลับสองอันนี้โดยใช้ index เดิม แล้ว**ทำลาย KB แบบเงียบสนิท** — ค้นได้ปกติ แต่จัดอันดับมั่ว นี่คือสิ่งที่ `EmbeddingProfile.revision` มีไว้ดัก และตอนนี้ไม่ใช่สมมติฐานอีกแล้ว

**อุปสรรค 3 ข้อที่ต้องผ่าน (ไม่มีข้อไหนเกี่ยวกับตัวโมเดล)**:

1. **Metal Toolchain ไม่ได้ติดตั้ง** — Xcode 26 แยกเป็น component ต่างหาก ถ้าไม่มี MLX ตายที่ `Failed to load the default metallib` แก้ด้วย `xcodebuild -downloadComponent MetalToolchain` (ติดตั้งแล้วบนเครื่องนี้) → **เป็น prerequisite ของเครื่องที่ build โปรเจกต์นี้ตั้งแต่นี้ไป**
2. **SwiftPM สร้าง Metal shader ไม่ได้** — README ของ mlx-swift เขียนเอง ต้อง build ผ่าน `xcodebuild` ขณะที่ `check.sh`/`build-app.sh` เป็น SwiftPM โดยเจตนา → ต้องมีขั้น `xcodebuild` เพิ่มเพื่อสร้าง `.metallib` อย่างเดียว
3. **`EmbedderRegistry.bge_m3` โหลดไม่ขึ้น** — มันชี้ไป `BAAI/bge-m3` ที่ weight ใช้ชื่อ layer แบบ HF แต่ BERT port ต้องการชื่อแบบ MLX (`keyNotFound(["encoder","layers","0","ln2","weight"])`) ต้องใช้ `mlx-community/bge-m3-mlx-8bit` แทน — **entry ใน registry ผิดกับโมเดลที่มันตั้งชื่อไว้เอง** ควรระวัง entry อื่นด้วย

## E.14 MLX chat runtime (Tier 0.5) — รันจริงตอน P5.1 (2026-08-12)

โมเดลสนทนาในโปรเซสเราเอง ผ่าน `LLMExecutor` ตัวเดียวกับอีกสอง tier วัดบน qwen3.5-9B-4bit (16 GB, LM Studio ปิด):

| เช็ค (เคสเดียวกับ Tier 0/Tier 1) | ผล |
|---|---|
| สตรีมเป็นชิ้น | ✅ 29 text + 456 reasoning delta |
| reasoning แยกจากคำตอบ | ✅ 676 ตัวอักษรของความคิด ไม่ปนเข้าคำตอบ |
| structured output ถอด JSON ได้ | ✅ 1.3 วิ (ก่อนแก้: ล้มเหลว 102.7 วิ — ดูข้างล่าง) |
| tool call ประกอบกลับเป็น JSON | ✅ `lookup_patient_count{"cohort":"diabetes"}` |
| prompt เกิน context | ✅ ปฏิเสธก่อนยิง ไม่ใช่ไปพังตอนรัน |
| โหลดค้างไว้ / ปลดตอน idle / โหลดกลับ | ✅ ทั้งสามข้อ |

**สามข้อที่ tier นี้ต้องทำเอง เพราะไม่มีโปรโตคอลไหนทำให้**

1. **`<think>` ที่ไม่มีแท็กเปิด** — chat template ของ Qwen ปิดท้าย generation prompt ด้วย `<think>\n` โมเดลจึงเริ่ม*กลาง*ความคิด และ output มีแต่ `</think>` ปลายทาง · splitter ที่รอแท็กเปิดจะรายงานความคิดทั้งก้อนเป็นคำตอบ = [E.9](#e9-vllmexecutor-spike--tier-1-ผ่าน-openai-compatible-endpoint) เคส 8c เวอร์ชัน local · แก้ด้วยการ **ถาม template** (render พรอมป์ต์ทดสอบแล้วดูว่า block ยังเปิดค้างอยู่ไหม) ไม่ใช่เดาจาก output — เดาไม่ทัน เพราะกว่า `</think>` จะมาถึง ความคิดก็ถูกสตรีมออกไปเป็นคำตอบแล้ว
2. **ไม่มี guided generation ใน mlx-swift-lm** — ไม่มี grammar/logit-constraint API เลย (ต่างจาก Tier 0 ที่มี `@Generable` และ Tier 1 ที่มี `response_format`) · schema จึงเป็นคำสั่งใน prompt แล้วดึง JSON object แรกที่ balanced และ parse ผ่านออกมา · **ไม่มี JSON = error ที่ escalate ได้ ไม่ใช่สตริงว่าง** — สตริงว่างคือสิ่งที่ปลายทางอ่านว่า "ไม่พบข้อขัดแย้ง"
3. **🔴 โมเดล reasoning + schema = คิดจนหมดเพดานแล้วไม่ตอบ** — ขอ routing object สองฟิลด์ ให้เพดาน 2,048 token: โมเดลใช้ทั้ง 2,048 ไปกับการคิด **102.7 วินาที ได้สตริงว่าง** · ปิด thinking ผ่าน `enable_thinking: false` ใน additionalContext ของ template → **1.3 วินาที** · ในงานที่คำตอบคือ "เติมสองช่องนี้" ไม่มีอะไรให้คิด และ tier ที่ทำงานได้เฉพาะตอนผู้เรียกใจกว้างเรื่องเพดาน ไม่ใช่พื้นรับประกันตาม [§9.2](../ARCHITECTURE.md#92-model-router-tier-0--05--1) ข้อ 4

**สองข้อที่กระทบการออกแบบต่อไป**

- **context window ที่ประกาศ ≠ ที่เครื่องรับไหว** — config บอก 262,144 แต่ประกาศแค่ 32,768 · router คัดผู้สมัครจากตัวเลขนี้ ตัวเลขที่ใจกว้างจึงเท่ากับเชิญพรอมป์ต์ที่ทำเครื่องล่มเข้ามาพอดี (วัดไว้: prompt 7.6k โทเคน 9B = ~7.4 GB) — P5.3 จะแทนด้วยการวัด RAM จริง
- **sandbox ทำให้แอปกับ `check.sh` เห็นโมเดลคนละชุด** — `~/.lmstudio` และ `~/.cache/huggingface` อยู่นอก container จึงมองไม่เห็นจากในแอป (ที่เห็นคือ `Documents/huggingface/models` ของ container เอง ซึ่ง `HubApi` ใช้อยู่แล้ว) · แปลว่า "ใช้โมเดลที่มีอยู่แล้ว" ใน [§9.4](../ARCHITECTURE.md#94-mlx-local-tier-05--model-management) ต้องมาพร้อม open panel + security-scoped bookmark ไม่ใช่แค่ path ใน settings — งาน P5.2

## E.15 Model manager ในแอปที่ sandbox — เจอตอน P5.2 (2026-08-12)

Tier 0.5 คือ inference ในแอปนี้เอง แอปจึงต้องเป็นที่ที่โมเดล**มาจาก**ด้วย ([§9.4](../ARCHITECTURE.md#94-mlx-local-tier-05--model-management)) — กดโหลดจริงในแอปแล้ว (Qwen3-0.6B, 335 MB) ระหว่างทางเจอห้าเรื่องที่เทสระดับหน่วยไม่มีทางเห็น:

| อาการ | สาเหตุจริง |
|---|---|
| `Qwen3-VL-4B` ถูกเสนอเป็นโมเดลแชท แล้วพังตอนโหลด | มีไฟล์ครบทุกอย่างของโมเดลแชท (weights + tokenizer + chat template) แต่ `LLMModelFactory` ไม่มี implementation ของ `qwen3_vl` · และเป็นโมเดลใหญ่สุดบนเครื่อง จึงถูกเลือกเป็น Tier 0.5 พอดี → **ถาม `typeRegistry` ของ mlx-swift-lm ก่อนเสมอ** ทั้งตอนสแกนของที่มีอยู่และตอนทำรายการแนะนำ |
| โมเดล 335 MB กินดิสก์ 670 MB | `HubApi` มีที่เก็บสองที่โดยการออกแบบ: snapshot ที่ `downloadBase` กับแคชกลางแบบ content-addressed — สำเนาที่โควตาของเรามองไม่เห็นคือสำเนาที่ทำดิสก์เต็ม → `HubApi(downloadBase:cache: nil)` |
| กด "ยกเลิก" ขึ้น error สีแดง `NSURLErrorDomain -999` | การยกเลิก Task ไปถึง URLSession ก่อน จึงกลับมาเป็น NSError ไม่ใช่ `CancellationError` — ต้องแปลเองที่ขอบของ installer |
| แถบ progress เดินแต่ตัวเลขค้าง "0 MB / 0 MB" | `Progress` ที่ `snapshot` ส่งกลับนับ **ไฟล์** (unit ละไฟล์ ซอยย่อยข้างใน) ไม่ใช่ byte — ใช้ `fractionCompleted` คูณกับขนาดที่บันทึกไว้ |
| โมเดลใน HF cache รายงานขนาด ~0 | snapshot ในแคชเป็น symlink ไป `blobs/` — `fileSize` ของ link คือ 76 byte จึงแพ้ `preferred()` ให้ไฟล์จริงเสมอ |

**สองข้อที่เป็นเรื่องของการออกแบบ ไม่ใช่บั๊ก**

- **ดาวน์โหลดที่ยกเลิกไว้ต้องไม่นับว่า "ติดตั้งแล้ว"** — ไฟล์เล็กมาก่อน โมเดล 17 GB ที่ค้างจึงมี config + template + shard เดียว และอ่านว่าพร้อมใช้จนไปพังตอนโหลด · เช็ครายชื่อ shard จาก `model.safetensors.index.json` ให้ครบก่อน · เก็บไฟล์ไว้ (นั่นคือ resume) แต่ไม่เสนอ
- **Tier 0.5 เป็น "ช่อง" ไม่ใช่โมเดลตายตัว** — router ประกอบครั้งเดียวตอน boot แต่โมเดลเปลี่ยนระหว่างแอปทำงาน (โหลดตัวแรก, สลับ 4B→8B) ถ้าใส่ `MLXExecutor` ตรงๆ ทุกการเปลี่ยนต้องรีสตาร์ท — และการโหลดครั้งแรกบนเครื่องที่ไม่เคยมีโมเดล คือจังหวะที่คนกำลังดูอยู่พอดีว่ามันใช้ได้ไหม

**ผลข้างเคียงที่สำคัญต่อ [§9.2](../ARCHITECTURE.md#92-model-router-tier-0--05--1)**: พอ Tier 0.5 มีจริง การเรียงแบบ "ถูกที่สุดก่อน" กลายเป็นอันตราย — เครื่องที่มีโมเดล 0.6B จะส่ง **planning/delegation** ไปให้มันแทน 27B บน endpoint · router จึงเรียงงาน high-impact ตามสายของ §9.2 (**1a → 0.5 → 1b**) ส่วน Tier 0.5 ยังอยู่ในสายในฐานะพื้นรับประกัน เพียงแต่ไม่ใช่ตัวแรก

## E.16 Admission control ที่วัดจากรูปร่างของโมเดล — P5.3 (2026-08-12)

สิ่งที่ชั้นนี้กันไม่ใช่คำตอบผิด แต่คือ**เครื่องหยุดตอบสนอง** — โมเดลที่ใหญ่กว่าที่ว่างไม่ได้ fail fast มันเข้า swap แล้วลากทั้งเครื่องไปด้วยหลายนาที

**ประเมินจาก config ของโมเดลเอง ไม่ใช่กฎคร่าวๆ** — `2 × layers × kv-heads × head-dim × 2 bytes` ต่อโทเคน บวก weights บวก overhead 0.5 GB:

| | qwen3.5-9B-4bit |
|---|---|
| weights บนดิสก์ | 5.6 GB |
| KV cache | 128 KB/token (32 layers × 4 kv heads × 256) → ~1.0 GB ที่ 7.6k |
| overhead | 0.5 GB |
| **ประเมินรวม** | **7.1 GB** |
| **วัดจริง** ([§9.2](../ARCHITECTURE.md#92-model-router-tier-0--05--1) note ใน `Engine.swift`) | **~7.4 GB** |

คลาดต่ำกว่า 10% และมีเทสยืนยันตัวเลขนี้ — ตัวเลขที่ผิดทางสูงจะกันโมเดลที่รันได้ ตัวเลขที่ผิดทางต่ำจะทำเครื่องค้าง

**บังคับสามจุด ไม่ใช่จุดเดียว**

1. **ตอนตั้งเป็นตัวหลัก** — ปุ่มถูก disable พร้อมตัวเลขทั้งสองข้าง ([§9.4](../ARCHITECTURE.md#94-mlx-local-tier-05--model-management) บอกว่า "เตือนและไม่ให้ตั้ง default")
2. **ตอนทุก request** — `isAvailable()` ถามใหม่ทุกครั้ง เพราะโมเดลที่พอดีตอนเปิดแอปไม่พอดีตอนงานวิเคราะห์ถือ 10 GB · tier ที่ตอบว่า "ตอนนี้ไม่ว่าง" ทำให้ router ขึ้น tier ถัดไป ([§9.2](../ARCHITECTURE.md#92-model-router-tier-0--05--1) ข้อ 2) ซึ่งดีกว่า tier ที่รับงานแล้วทำเครื่องล่ม · ถ้าโมเดลโหลดค้างอยู่แล้วถือว่าผ่าน — หน่วยความจำนั้นจ่ายไปแล้ว
3. **ตอนเลือกเองอัตโนมัติ** — `preferred()` คือ**ตัวใหญ่ที่สุดที่พอดี** ไม่ใช่ตัวใหญ่ที่สุด · ถ้าไม่มีตัวไหนพอดีเลยจะคืนตัวเล็กที่สุด (ไม่ใช่ nil) เพื่อให้ tier ยังมีชื่อโมเดลไว้อธิบาย และกลับมาใช้ได้ทันทีที่ RAM ว่าง

**เกิดขึ้นจริงระหว่างตรวจ**: LM Studio ถือ RAM อยู่ เหลือว่าง 6.1 GB → 9B ถูกปฏิเสธ → contract ทั้งชุดข้ามแบบดังๆ แทนที่จะรัน · นั่นคือพฤติกรรมที่ถูก และเป็นเหตุผลที่ `MLXCheck` ต้องแยก "ข้ามเพราะไม่มีที่" ออกจาก "ล้มเหลว" — ไม่งั้นชั้นที่ทำงานถูกจะรายงานว่าตัวเองพัง

## E.17 พื้นรับประกันที่ใช้ได้จริง — วัดตอน P5.4 (2026-08-12)

ปิด LM Studio จริง แล้วให้แอปตอบจากโมเดลบนเครื่อง — หัวแชทขึ้น `mlx:mlx-community/Qwen3-VL-4B-Instruct-4bit · tier 0.5` เส้นทางของ [§9.2](../ARCHITECTURE.md#92-model-router-tier-0--05--1) ข้อ 4 จึงเป็นของจริงแล้ว ไม่ใช่ข้อความในเอกสาร

**VL checkpoint คือโมเดลแชท — แค่คนละโรงงาน** · `qwen3_vl` อยู่ใน `VLMModelFactory` ไม่ใช่ `LLMModelFactory` · ถามแค่ registry เดียวแปลว่าบนเครื่องที่มีแต่โมเดล VL จะ**ไม่มี Tier 0.5 เลย** ทั้งที่โมเดลตอบข้อความได้สบาย

**สี่อย่างที่ต้องมี ไม่งั้นโมเดล 4B ใช้งานจริงไม่ได้** (วัดบน Qwen3-VL-4B-4bit):

| อาการ | สิ่งที่แก้ |
|---|---|
| `{"role: "engineer"` — key ขาด quote ปิด ไม่มีปีกกาปิด | ใส่ **ตัวอย่างให้ลอก** ที่สร้างจาก schema (`{"role": "researcher", "needsClarification": false}`) แทนการยื่น spec ให้ตีความ |
| ขอ JSON แล้วได้บ้างไม่ได้บ้าง | **temperature 0** ตอนมี schema — การสุ่มคือสิ่งที่ทำให้ quote หาย |
| retry แล้วผิดซ้ำแบบเดิมเป๊ะ | ที่ temperature 0 การลองใหม่ได้โทเคนชุดเดิม → **รอบสองต้อง sample ต่างออกไป** (0.4) พร้อมบอกตรงๆ ว่ารอบแรกไม่ใช่ JSON |
| ตอบ `ไมรนบน` สามร้อยรอบ บน transcript ไทยที่ย่อแล้ว | **repetition penalty 1.05** — endpoint แบบ hosted ใส่ให้อยู่แล้ว, mlx-swift-lm ไม่ใส่ให้ถ้าไม่สั่ง |

นอกจากนั้นยังต้อง**เก็บกู้ tool call ที่ parser มองไม่เห็น**: โมเดลลอกตัวอย่างใน chat template ของตัวเองแล้วพิมพ์ `<tool_call>` สองครั้ง — ตัว call ถูกต้องทุกอย่าง แต่ห่ออยู่ในแท็กเกินหนึ่งอัน จึงหลุดออกมาเป็น prose

**คุณภาพที่ได้จริง — พูดตรงๆ**: เลขถูก (17×3 = 51) แต่สะกดไทยเพี้ยน ("เทากบ") และตัดสินคู่ metformin ("ต้องให้" กับ "ห้ามให้") ว่า**ไม่ขัดแย้ง** · ตรงกับตาราง [§9.4](../ARCHITECTURE.md#94-mlx-local-tier-05--model-management): เครื่อง < 16 GB ได้โมเดลระดับ fallback ไม่ใช่ระดับนักวิเคราะห์ · พื้นรับประกัน**มีจริง** แต่พื้นก็คือพื้น

**สองข้อที่เปลี่ยนวิธีทำงานของโปรเจกต์**

- **`tier 0.5` ไม่ใช่ `tier 1`** — UI พิมพ์ `rawValue` ของ enum ทำให้โมเดลบนเครื่องดูเหมือน endpoint ที่มันเพิ่งตกลงมาจาก · tier มีชื่อของมันใน §9.2 แล้ว UI ต้องเรียกตามนั้น
- **skip ต้องดังแต่ไม่ทำให้ build แดง** — เดิมสวีต Tier 1 บันทึกการข้ามเป็น Issue เครื่องที่ไม่มี LM Studio จึงไม่มีวันได้ชุดเทสสีเขียว ทั้งที่นั่นคือ*ปลายทาง*ของ P5 · ตอนนี้พิมพ์ `SKIPPED:` แล้ว `check.sh` ยกมาแสดง — เห็นชัดเท่าเดิม แต่ไม่ลงโทษเครื่องที่รันตัวเองได้ล้วนๆ

## E.26 รวมเอนทิตีข้ามภาษาด้วย embedding — วัดแล้วทำเองไม่ได้ (2026-08-16)

§11.8/P18.3 วางไว้ว่าจะรวมโหนดข้ามภาษาด้วยระยะ embedding · [E.25](#e25-ด่านกรอง-คำแปล-ด้วย-embedding--วัดแล้วทำไม่ได้-2026-08-16) พบว่า*ประโยค*แยกไม่ได้ แต่*ชื่อเอนทิตี*เป็นคนละคำถาม — ไม่มีข้อความให้ขัดแย้งกัน จึงต้องวัดแยก · วัดด้วย `EmbeddingCheck` บนน้ำหนักจริง:

| กลุ่ม | cosine |
|---|---|
| ชื่อเดียวกันคนละภาษา (`ภาวะหมดไฟ`↔`burnout` · `ภาวะซึมเศร้า`↔`depression` · `เบาหวานชนิดที่ 2`↔`type 2 diabetes` · `ความดันโลหิตสูง`↔`hypertension`) | 0.485 · 0.506 · 0.525 · 0.620 |
| คนละความหมาย (`ความดัน`↔`pressure` · `การนอนหลับ`↔`anaesthesia` · `ไต`↔`kidney stone` · `วัคซีน`↔`antibiotic`) | 0.414 · 0.504 · 0.510 · **0.919** |

**คู่ที่ได้คะแนนสูงที่สุดในชุดทั้งหมดคือคู่ที่ต้องไม่รวม** — `ความดัน` (โลหิต) กับ `pressure` (แรงดัน) ที่ **0.919** ซึ่งสูงกว่าทุกคู่ที่ถูกต้อง และเป็นตัวอย่างที่ §11.8 เขียนเตือนไว้เองพอดี ⇒ **ไม่มีเกณฑ์ไหนที่รับคู่ที่ถูกครบแล้วกันคู่นี้ออกได้**

**ผลต่อการออกแบบ**: ระบบ**เสนอ**ได้ แต่**ไม่รวมเองจนกว่าคนจะยืนยัน** — `canonicalKey` นับเฉพาะ alignment ที่ `confirmedByHuman` · โครงสร้างที่เหลือ (โหนดเดียวหลายชื่อ · แสดงชื่อตามภาษาที่อ่าน · คีย์คงที่ไม่ขยับตามภาษา · แยกคืนได้) ยังถูกและยังจำเป็น ไม่ว่าใครจะเป็นคนเสนอการรวม

**เช็คนี้อยู่ใน `check.sh` และเขียวตราบใดที่สองกลุ่มยังทับกัน** — วันไหนแยกกันได้จะแดงพร้อมข้อความให้กลับไปอ่าน P18.3 ใหม่ เหมือนที่ E.25 ทำกับ P18.2

## E.25 ด่านกรอง "คำแปล" ด้วย embedding — วัดแล้วทำไม่ได้ (2026-08-16)

P18.2 วางไว้ว่า: `bge-m3` ฝังไทยกับอังกฤษในสเปซเดียวกัน ([E.10](#e10-d-2--เลือก-embedding-model-วัดจริง-ปิดแล้ว)) ⇒ คู่ที่**คนละภาษาแต่ใกล้กันมาก** น่าจะเป็นคำแปลของกันและกัน กรองทิ้งก่อนถึงโมเดลได้ · วัดบนน้ำหนักจริงด้วย `EmbeddingCheck` — 4 คู่ที่เป็นคำแปล เทียบกับ 4 คู่ที่**ขัดแย้งกันจริงข้ามภาษา**:

| กลุ่ม | cosine (เรียงจากน้อยไปมาก) |
|---|---|
| คำแปลของกันและกัน | 0.401 · 0.644 · 0.710 · **0.760** |
| ขัดแย้งกันจริง | 0.322 · 0.541 · 0.630 · **0.770** |

**สองกลุ่มทับกันเกือบทั้งช่วง — ไม่มีเกณฑ์ไหนแยกได้** และเหตุผลเป็นเชิงโครงสร้าง ไม่ใช่เรื่องปรับตัวเลข: **embedding วัดว่าข้อความ*เกี่ยวกับอะไร* ส่วนข้อความที่ขัดแย้งกันคือข้อความที่เกี่ยวกับเรื่องเดียวกันเป๊ะ** — คู่ที่ใกล้ที่สุดในชุดทั้งหมด (0.770) คือ "ผู้ใหญ่ควรนอนอย่างน้อย 7 ชั่วโมง" กับ "adults need no more than four hours of sleep" ซึ่งเป็นข้อขัดแย้งที่ชัดที่สุดในชุด

**ผลต่อแผน**: P18.2 ตามที่เขียนไว้**ทำไม่ได้** — ไม่ใช่ยังไม่ได้ทำ · สิ่งที่เหลือคือครึ่งที่ราคาถูกและไม่โกหก: อ่าน*สคริปต์*ของข้อความจากตัวอักษร (ไทย/ละติน/ปนกัน/ตัดสินไม่ได้) แล้วให้ `ConflictDetector` ใช้มัน**ยกระดับเกณฑ์** ของคู่ข้ามภาษา แทนที่จะข้ามโมเดล — เป็นกฎเรื่อง*หลักฐานที่ต้องมี* ไม่ใช่ทางลัดที่เดาแทนโมเดล

**แล้วเกณฑ์ที่เอามาแทนได้ผลไหม — วัดกับโมเดลจริงบน GX10** (`swift run TierOneCheck`, ชุดเดียวกันทั้ง 8 คู่):

| | ผล |
|---|---|
| คำแปลที่ถูกยกเป็นการ์ดผิด | **0/4** (ทุกคู่ตกที่ `notMutuallyExclusive`) |
| ข้อขัดแย้งจริงข้ามภาษาที่จับได้ | **4/4** ที่ความมั่นใจ 0.92 · 0.95 · 0.95 · 0.98 |

**ต้องวัดทั้งสองด้าน** — เกณฑ์ที่แน่นจนคำแปลไม่หลุดแต่ข้อขัดแย้งจริงหลุดตามไปด้วย คือความเสียหายอีกด้านที่มองไม่เห็นถ้าดูแต่ false positive · ค่าความมั่นใจทั้งสี่อยู่เหนือเกณฑ์ข้ามภาษา 0.9 พอดี ๆ ซึ่งแปลว่าเกณฑ์นี้ตั้งไว้ใกล้ขอบ — ถ้าเปลี่ยนโมเดลต้องวัดซ้ำ

**เช็คของ embedding ยังอยู่ใน `check.sh` และเขียวอยู่ตราบใดที่สองกลุ่มยังทับกัน** — ถ้าวันหนึ่ง embedder ใหม่แยกสองกลุ่มได้ เช็คจะแดงพร้อมข้อความว่าให้กลับไปอ่าน P18.2 ใหม่ · การเก็บไว้แบบนี้ทำให้ "ทำไมถึงไม่มีด่านกรอง" เป็นข้อเท็จจริงที่ยังถูกวัดอยู่ ไม่ใช่ความทรงจำ

## E.24 prefix cache จ่ายจริง — 3.35 วิ → 0.32 วิ (2026-08-16)

วัดด้วย `swift run TierOneCheck` (ส่วน P15.4) · TTFT = เวลาจนโทเคนแรกถึงผู้ใช้ ซึ่งเป็นเวลาที่คนรอจริง ๆ · prefix ยาว ~40 ย่อหน้า

| คำขอ | TTFT |
|---|---|
| คำขอแรก prefix ที่ไม่เคยเห็น | **3.35 วิ** |
| คำขอที่สอง **prefix เดิม** ต่อท้ายอีกหนึ่งเทิร์น | **0.32 วิ** (เร็วขึ้น **90%**) |
| **ตัวคุม**: prefix อื่น ยาวเท่ากัน | **3.45 วิ** |

**ตัวคุมคือส่วนที่ทำให้เชื่อได้** — ถ้าไม่มี ตัวเลข 0.32 วิ อธิบายได้ด้วย "เครื่องอุ่นขึ้น" เท่า ๆ กับ "cache ทำงาน" · prefix ที่ยาวเท่ากันแต่ต่างเนื้อหากลับไปใช้ 3.45 วิ ⇒ ที่ประหยัดได้คือ prefix ที่ซ้ำจริง

**สิ่งที่ต้องไม่พังเพื่อให้ตัวเลขนี้อยู่ต่อ**: `ToolGateway.adverts` เรียงตามชื่อเสมอ — รายการทูลถูก render ไว้*หน้า*บทสนทนา ถ้าปลั๊กอินตัวหนึ่งโหลดเร็วกว่าเดิมเสี้ยววินาทีแล้วลำดับสลับ prefix จะกลายเป็นคนละก้อนและทุกบทสนทนาเสีย cache เงียบ ๆ **สามวินาทีต่อเทิร์นแขวนอยู่กับลำดับที่ไม่มีใครนึกว่าต้องรักษา** — มีเทสคุมแล้ว

## E.23 หลายสายพร้อมกัน — และเพดานที่เจอตัวแรกไม่ใช่ของ GPU (2026-08-16)

วัดด้วย `swift run TierOneCheck http://192.168.1.205:8000/v1 96 <ระดับ>` — **ยิงผ่าน `ModelRouter` ไม่ใช่ curl** เพราะเลขที่ต้องการคือเลขของเส้นทางที่แอปเดินจริง · 96 โทเคน/คำขอ · อ่าน `vllm:num_requests_running` จาก `/metrics` ระหว่างรัน

**รอบแรก — ตัวเลขที่อ่านไม่เข้ากัน**:

| สาย | เวลารวม | กลาง | โทเคน/วิ | คิวสูงสุด |
|---|---|---|---|---|
| 6 | 9.3s | 9.1s | 59.1 | 5 |
| **7** | **14.9s** | **9.3s** | 42.8 | 2 |
| 8 | 16.3s | 9.3s | 43.1 | 5 |

**หกสายเร็วเท่าสายเดียว แต่สายที่เจ็ดทำให้เวลารวมพุ่งขึ้น 60% ทั้งที่เวลาต่อคำขอไม่ขยับ** — แปลว่าสายที่เจ็ด*ไม่ได้ออกไปพร้อมกัน* มันรอ และสิ่งที่มันรอไม่ได้อยู่บน GPU: `URLSession.shared` เปิดได้ **6 connection ต่อ host** เป็นค่าเริ่มต้นของ Foundation

**เพดานจริงของแอปจึงเป็น 6 มาตลอด โดยไม่มีอะไรบอก** — ทีมสี่ specialist + แชท + ลำดับงาน = ครบโควตาพอดี และอาการของการเกินคือ "ช้าลงเฉย ๆ" ไม่ใช่ error → `VLLMExecutor` ใช้ session ของตัวเองที่ตั้ง `httpMaximumConnectionsPerHost = 16`

**รอบสอง — หลังยกเพดานฝั่ง client**:

| สาย | เวลารวม | กลาง | โทเคน/วิ | คิวสูงสุด (รัน/รอ) |
|---|---|---|---|---|
| 1 | 7.3s | 7.3s | 11.4 | 1/0 |
| 4 | 9.0s | 8.8s | 39.6 | 4/0 |
| 8 | 9.6s | 9.4s | 75.6 | 8/0 |
| 12 | 10.5s | 10.1s | 101.9 | 12/0 |
| **16** | **11.0s** | **11.0s** | **128.5** | **16/0** |

**ข้อสรุปที่ใช้ตัดสินใจได้**:

1. **16 สายขนานทำงานพร้อมกันจริง** — `num_requests_running` อ่านได้ 16 และ `num_requests_waiting` เป็น 0 ตลอด คือ**ยังไม่เจอเพดานของ GPU** เลย เพดานที่ 16 เป็นเพดานที่*เราตั้งเอง*
2. **ราคาของการขนานถูกมาก**: 1 → 16 สาย เวลาต่อคำตอบแย่ลง **1.5 เท่า** (7.3 → 11.0 วิ) แต่ปริมาณงานรวมขึ้น **11 เท่า** (11.4 → 128.5 โทเคน/วิ)
3. **span of control ของ P16 = 16 ตามที่วัดได้** ไม่ใช่ 7 ที่ยืมมาจาก ICS ซึ่งนับ*คน* — และไม่ใช่ 6 ที่ Foundation ตั้งให้โดยไม่มีใครเลือก

### สองอย่างที่ยังต้องแก้ และอันหนึ่งเป็นกับดักที่ไม่มีข้อความเตือน

**1. `--tool-call-parser hermes` ไม่ตรงกับรูปแบบที่โมเดลนี้ปล่อยออกมา** — `tool_calls` เป็น `null` และของจริงไปโผล่ใน `content` เป็น XML:

```
<tool_call><function=lookup_patient_count><parameter=cohort>diabetes</parameter></function></tool_call>
```

นี่คือรูปแบบ `qwen3_xml` (บาง build เรียก `qwen3_coder`) ไม่ใช่ Hermes ซึ่งเป็น JSON · **อาการนี้อันตรายกว่าตอนได้ `400`**: เซิร์ฟเวอร์ตอบ 200 ทุกครั้ง ระบบจะอ่านว่า agent ตอบเป็นข้อความธรรมดาแล้วไม่เคยเรียกทูลเลย โดยไม่มีอะไรผิดพลาดให้เห็น

**2. สมุดทดกิน `max_tokens` และคำตอบว่างเปล่าโดยไม่มี error** — คำขอที่ตั้ง `max_tokens: 200` ได้ `content` **ยาว 0 ตัวอักษร**, `reasoning` ยาว 931 ตัวอักษร, `finish_reason: "length"` · โมเดลใช้โควตาทั้งก้อนไปกับการคิดแล้วถูกตัดก่อนเริ่มตอบ

⇒ **`max_tokens` ต้องกันที่ให้ทั้งสองส่วน** และ `VLLMExecutor` ต้องอ่าน `finish_reason == "length"` คู่กับ `content` ที่ว่าง แล้วรายงานว่า "คิดจนหมดโควตาก่อนตอบ" ไม่ใช่ปล่อยข้อความว่างขึ้นหน้าจอ — เพราะคำตอบว่างที่ไม่มีเหตุผลกำกับ อ่านเหมือนโมเดลไม่มีอะไรจะพูด

**ชื่อฟิลด์คือ `message.reasoning` ไม่ใช่ `reasoning_content`** บน vLLM 0.27.1 — ผู้อ่านที่ดักผิดชื่อจะได้ `nil` เงียบ ๆ ซึ่งดูเหมือนโมเดลไม่ได้คิด

## E.18 ทะเบียน endpoint กับเพดานเงิน — สร้างตอน P5.5–P5.7 (2026-08-12)

สร้างทั้งชั้นก่อนที่จะมี endpoint จริงให้ต่อ (GX10 ยังไม่เสร็จ) — สิ่งที่พิสูจน์ได้ตอนนี้คือ*พฤติกรรม*ของมัน ไม่ใช่ตัวเลขค่าใช้จ่ายจริง และหน้าจอบอกความจริงข้อนั้นเองว่า "ยังไม่มี endpoint ที่คิดเงิน เพดานจึงยังไม่มีผลกับอะไร"

**สามการตัดสินใจที่มีผลกับโครงสร้าง**

| เรื่อง | ทำไมเป็นแบบนี้ |
|---|---|
| **บันทึก endpoint ได้ต่อเมื่อ probe ผ่าน** | [E.9](#e9-vllmexecutor-spike--tier-1-ผ่าน-openai-compatible-endpoint) เคส 8a: เซิร์ฟเวอร์ OpenAI-compatible ตอบรับชื่อโมเดลที่ไม่มีอยู่ ความผิดพลาดจึงไปโผล่ทีหลังในที่ที่ไม่มีใครรู้ว่าพิมพ์ชื่อผิด · ทะเบียนที่เต็มไปด้วย endpoint ที่ไม่เคยต่อติดคือรายการงานที่ต้องมาไล่เช็คเองทีหลัง |
| **`SpendLedger` อยู่ใน AgentKit** | สามโมดูลต้องใช้และไม่ควรต้องรู้จักกัน: `Config` เขียนเพดาน, `Persistence` เก็บยอด, `LLMProviders` เป็นที่ที่สองอย่างนั้นมาเจอกัน — รูปแบบเดียวกับ `Embedder` ที่ `Knowledge` ประกาศแล้ว `EmbeddingRuntime` ทำ |
| **API key เก็บแค่ชื่อตัวแปร env** | bootstrap.plist เป็นไฟล์ธรรมดาใน Application Support · คีย์ในนั้นคือคีย์ที่วางอยู่บนดิสก์ · Keychain จริงเป็น P9.2 แต่ระหว่างนี้ paid endpoint ต้องใช้งานได้ |

**เพดานที่บอกว่าชั้นไหนเต็ม** — "เกินงบ" เฉยๆ คือข้อความที่ทำให้คนปิดระบบงบทิ้ง ข้อความจึงบอกทั้งชั้นที่ชน ยอดที่ประเมิน และยอดที่เหลือ · และ**เกินเพดานไม่ใช่ error**: งานตกไป Tier 1a/0.5 แล้วทำต่อ ([§9.2](../ARCHITECTURE.md#92-model-router-tier-0--05--1) ข้อ 4) ผู้ใช้รู้จาก span ไม่ใช่จากความล้มเหลว

**ประเมินก่อน จ่ายจริงทีหลัง** — ตัดสินใจด้วยการประเมินจาก `maxTokens` (มองโลกในแง่ร้ายโดยตั้งใจ: ประเมินต่ำคือวิธีที่เพดานถูกข้ามโดยไม่เคยชน) แล้วลงบัญชีจาก `usage` ที่ endpoint คืนมาจริง ซึ่ง E.9 ยืนยันแล้วว่ามีทั้งแบบ streaming และไม่ streaming · **endpoint ที่คิดเงินแต่ไม่ได้ตั้งราคา = governor ไม่ยอมให้ใช้เลย** ดีกว่าเดาด้วยเงินคนอื่น

**P4.7 ที่ค้างอยู่ก็ปิดในรอบเดียวกัน** — ปุ่มสั่งแก้/ยกเลิกรายชิ้น · สองอย่างที่ไม่ใช่รายละเอียด: (1) การสั่งแก้**บังคับให้พิมพ์เหตุผล** และเหตุผลนั้นเดินทางไปทางเดียวกับ findings ของ QA — "ทำใหม่อีกรอบ" เฉยๆ คือคำสั่งที่ทำให้ loop ของ v1 วน (2) การยกเลิกถูก**บันทึกเป็น `cancelled` ไม่ใช่ลบทิ้ง** และ run-until-done ข้ามมันเหมือนที่ข้าม escalation — ทั้งคู่คือการตัดสินใจของคน และการหยิบขึ้นมาทำเองคือการกลับคำตัดสินนั้น

ข้อสรุป 4 ข้อที่มีผลต่อสถาปัตยกรรม:

1. **ปฏิเสธงานวิจัยการแพทย์ปกติจริง** — "หางานวิจัยวัคซีน mRNA ในผู้สูงอายุ" และ "ตรวจสอบขนาดยา metformin ตามแนวทางเวชปฏิบัติ" ไม่ใช่คำขอที่มีปัญหาใดๆ
2. **ไม่ deterministic** — prompt วัคซีนภาษาไทยถูกปฏิเสธในรอบแรก แต่ผ่านในรอบสอง ส่วนภาษาอังกฤษกลับกัน → **ทำนายไม่ได้ ต้องออกแบบให้ทนต่อมันแทนที่จะหลบ**
3. **`permissiveContentTransformations` ไม่ช่วย** — ปฏิเสธเคสเดียวกันเป๊ะ (การตั้งชื่อบอกอยู่แล้วว่าเกี่ยวกับ *content transformation* ไม่ใช่การผ่อนเรื่อง safety topic)
4. **คุณภาพการ route ปานกลาง** — prompt เดียวกันให้คำตอบต่างกันระหว่างสองโหมด (`แก้บั๊กใน main.swift` → `engineer` แล้ว `researcher`), งานวิเคราะห์หลายอันได้ `researcher` แทน `analyst` → ใช้ตัดสินใจสำคัญไม่ได้

## E.10 D-2 — เลือก embedding model (วัดจริง, ปิดแล้ว)

ชุดทดสอบ: 20 เอกสาร (ไทย 10 / อังกฤษ 10) เนื้อหาการแพทย์+สถิติ พร้อม distractor คนละโดเมน · 12 query · วัด recall@1, recall@3, MRR และ **cross-lingual** (query ภาษาหนึ่งดึงเอกสารอีกภาษาที่เกี่ยวข้องได้ไหม) — harness เก็บไว้ที่ [`spikes/EmbeddingEval/`](../spikes/EmbeddingEval/)

| provider | dim | recall@1 | recall@3 | MRR | cross-lingual | fails |
|---|---|---|---|---|---|---|
| `NLEmbedding.sentence` | 512 | 50.0% | 50.0% | 0.500 | 0.0% | **16** |
| `NLContextualEmbedding` | 512 | 50.0% | 66.7% | 0.599 | 0.0% | 0 |
| `nomic-embed-text-v1.5` | 768 | 66.7% | 75.0% | 0.751 | 41.7% | 0 |
| **`bge-m3`** | **1024** | **100%** | **100%** | **1.000** | **100%** | 0 |

**ข้อเท็จจริงที่ตัดสินเรื่องนี้ — เป็นข้อจำกัดเชิงโครงสร้าง ไม่ใช่การปรับจูน**:

1. 🔴 **Apple ไม่มี sentence embedding ภาษาไทย** — `NLEmbedding.sentenceEmbedding(for: .thai)` คืน `nil` (fail ทั้ง 16 ครั้งคือฝั่งไทยล้วน)
2. 🔴 **`NLContextualEmbedding` แยกโมเดลตามสคริปต์ ไม่ใช่ multilingual ตัวเดียว** — ตรวจ `languages` จริง: โมเดลของไทยครอบ **1 ภาษา (`th`) เท่านั้น**, โมเดล Latin ครอบ 20 ภาษา (cs, da, de, en, …) **แต่ไม่มีไทย** → เอกสารไทยกับอังกฤษอยู่คนละ vector space **cross-lingual retrieval จึงเป็นไปไม่ได้เชิงโครงสร้าง** ไม่ว่าจะ pooling แบบไหน
3. ✅ **`bge-m3` ทำได้ 100% ทุกมิติบนชุดนี้** — สร้างมาเพื่อ multilingual retrieval โดยตรง (100+ ภาษา, context ยาวถึง 8192 token), ขนาด 634MB (567M params)

**Decision (2026-08-10): ใช้ `bge-m3` ที่ 1024 มิติ** — เหตุผลที่ชี้ขาดคือ **cross-lingual**: KB ของระบบนี้มี proposal ภาษาไทยปนกับ paper ภาษาอังกฤษเสมอ ถ้าค้นด้วยคำไทยแล้วไม่แตะเอกสารอังกฤษเลย ระบบจะพลาดครึ่งหนึ่งของ KB **โดยที่ผู้ใช้ไม่มีทางรู้** — เป็น failure mode ที่เงียบและอันตรายที่สุดของ RAG

**ข้อจำกัดของการวัดนี้ (ต้องบันทึกไว้)**: ชุดทดสอบมีแค่ 20 เอกสาร/12 query — คะแนนเต็ม 100% แปลว่าชุดนี้**แยกความต่างที่ปลายบนไม่ได้อีกแล้ว** ไม่ใช่ว่าโมเดลสมบูรณ์แบบ ใช้ตัดสินได้เพราะช่องว่างกับอันดับสอง (1.000 vs 0.751) กว้างมาก แต่ถ้าจะเทียบ bge-m3 กับ multilingual ตัวอื่นในอนาคต **ต้องสร้างชุดที่ยากกว่านี้ก่อน**

**ผลต่อสถาปัตยกรรม**: มิติ 1024 ถูกล็อกเข้ากับ HNSW index — เปลี่ยนโมเดลทีหลัง = re-index ทั้ง KB และ **bge-m3 ต้องรันในเครื่องเราเอง ไม่ใช่พึ่ง LM Studio** ([§9.4](../ARCHITECTURE.md#94-mlx-local-tier-05--model-management) `MLXRuntime` ต้องโฮสต์โมเดล embedding ด้วย ไม่ใช่แค่โมเดลสนทนา)

## E.28 สะพาน R — วัดกับ R จริงบนเครื่องนี้ (2026-08-16)

**ทำไมต้องวัดก่อนเขียน**: [ARCH §12.7](../ARCHITECTURE.md#127-r--เรียกจากข้างนอกแบบ-rstudio-พร้อมตัวช่วย-p14) วาดสะพานด้วย **plumber** — และบนเครื่องนี้ `plumber` **ไม่ได้ติดตั้ง** ส่วน `httpuv` กับ `jsonlite` มีอยู่แล้ว ถ้าเดินตามรูปโดยไม่วัด คำสั่งแรกที่หน้าตั้งค่าจะพูดกับผู้ใช้คือ "ติดตั้งแพ็กเกจก่อน ตัวช่วยถึงจะทำงาน" ซึ่งเป็นราคาที่แพงเกินไปสำหรับ syntax แบบ decorator — plumber เองก็เป็นชั้นบน `httpuv` อยู่แล้ว

| สิ่งที่วัด | ผล |
|---|---|
| `R --version` | **4.5.3** (aarch64-apple-darwin20) ที่ `/usr/local/bin/R` |
| แพ็กเกจที่มี | `httpuv` ✅ · `jsonlite` ✅ · **`plumber` ✗** |
| `GET /health` | `{"ok":true,"r":"4.5.3","pid":99741}` |
| `POST /eval` — `cat()` + data frame | `{"printed":"hello from R","frame":{"columns":["id","name","value"],"types":["integer","character","numeric"],"rows":[["1","a","1.5"],["2",null,"2.5"],["3","c","3.5"]]}}` |
| `POST /eval` — โค้ดที่ parse ไม่ผ่าน | HTTP 400 `{"error":"<text>:2:0: unexpected end of input\n1: sum(1,\n   ^"}` |

**สามข้อที่การขับจริงเป็นคนตอบ ไม่ใช่การอ่านเอกสาร**:

1. **`NA` ของ R ต้องมาเป็น JSON `null` ไม่ใช่สตริง `"NA"`** — `toJSON(..., na = "null")` ทำให้แถวที่สองได้ `null` จริงตามที่เห็นข้างบน ถ้าปล่อยเป็นค่าเริ่มต้น คอลัมน์ตัวเลขที่มีค่าว่างจะกลายเป็นข้อความทั้งคอลัมน์ตอนเข้า DuckDB
2. **error ของ R ต้องเป็น 400 พร้อมข้อความของ R เอง** — ข้อความจริงบอกบรรทัดและตำแหน่ง (`<text>:2:0`) ซึ่งเป็นสิ่งเดียวที่บอกได้ว่าโค้ดผิดตรงไหน 500 เปล่า ๆ ทิ้งข้อมูลนั้นทั้งหมด
3. **ค่าที่ไม่ใช่ data frame ไม่ใช่ความล้มเหลว** — plot, โมเดล, การ assign คืน `frame: null` และนั่นคือคำตอบที่ถูกต้อง

**สิ่งที่เทสไม่ได้พึ่ง**: เทสทั้ง 15 ข้อของ `RBridgeTests` ไม่เรียก R เลย — ใช้รูปคำตอบที่บันทึกไว้ข้างบนแทน เครื่องที่ไม่มี R คือเครื่องที่ฟีเจอร์นี้มีไว้ให้ ถ้าเทสต้องมี R ถึงจะผ่าน มันจะพังบนเครื่องแบบนั้นเป็นอันดับแรก

## E.30 ขับหน้าจอจริง + ตรวจ VoiceOver ด้วยตัวขับ (2026-08-16)

เจ้าของเครื่องให้สิทธิ์ **Accessibility** และ **Screen Recording** แล้ว (§23.2 ข้อ 1 — ระบบให้สิทธิ์ตัวเองไม่ได้) จึงขับได้จริงเป็นครั้งแรก · เครื่องมือคือ [`Sources/ScreenCheck`](../Sources/ScreenCheck/main.swift) ซึ่งอ่าน accessibility tree ของแอปที่ระบุชื่อ — **ต้นไม้เดียวกับที่ VoiceOver อ่าน** ⇒ ปุ่มที่ไม่มีชื่อตรงนี้ คือปุ่มที่ VoiceOver พูดว่า "button" เฉย ๆ

| รอบ | ผล |
|---|---|
| Finder (แอปอื่น เพื่อพิสูจน์ว่าตัวขับใช้ได้จริง) | อ่านได้ · ปุ่มไร้ชื่อ 0 |
| Co-AI Workspace รอบแรก | **ปุ่มไร้ชื่อ 6** |
| หลังแยก chrome ของระบบออก | เหลือ **2** — และทั้งสองคือปุ่มปิด/ย่อของหน้าต่าง |
| หลังแก้ + กวาดทั้ง 5 พื้นที่ (⌘1–⌘5) | **0 ทุกพื้นที่** |

**สิ่งที่การขับสอน ซึ่งการอ่านโค้ดไม่สอน**:

1. **สี่ในหกไม่ใช่ของเรา** — เป็นชิ้นส่วนของ `AXScrollBar` ที่ AppKit วาดเองและ VoiceOver อ่านตาม role · อีกสองคือปุ่มปิด/ย่อของหน้าต่าง · การนับพวกนี้เป็นความผิดคือการใส่ความล้มเหลวถาวรหกข้อลงในทุกรายงาน ซึ่งเป็นวิธีทำให้ไม่มีใครอ่านรายงาน ⇒ เพิ่ม `subrole` ลง `ScreenElement` เพราะ**นั่นคือสิ่งที่แยกเฟอร์นิเจอร์ของระบบออกจากปุ่มที่เราวาด**
2. **`.accessibilityLabel` บน `Button` ไม่พอเมื่อ label เป็น `Image` ล้วน** — AppKit เปิดเผย element ของ `Image` ออกมาด้วย ป้ายต้องอยู่บน `Image` (กติกาที่ `FilesView` เขียนไว้อยู่แล้ว และตอนนี้พิสูจน์ด้วยของจริง) แก้ 13 จุดในสองไฟล์
3. **placeholder ไม่ใช่ label** — ช่อง "ชื่อโปรเจกต์ใหม่" ในหน้าแผนถูกอ่านว่าเป็นช่องข้อความไม่มีชื่อ เพราะ placeholder หายไปทันทีที่พิมพ์

4. **ตัวตรวจเองก็มีบั๊ก และการขับจริงเป็นตัวเปิดโปง** — `accessibility-audit.py` อ่านแค่ 10 บรรทัดหลัง `Button` ⇒ ปุ่มที่คอมเมนต์อธิบายเหตุผลยาวหกบรรทัดถูกรายงานว่า "ไม่มี label" ทั้งที่มี · **กฎที่ลงโทษการเขียนเหตุผลกำกับ คือกฎที่สอนให้คนเลิกเขียน** · ขยายหน้าต่างเป็น 24 แล้วเจอ**สัญญาณเตือนผิดสี่จุดทันที** เพราะมันไปเห็น `Image` ของวิวถัดไป ⇒ แก้ให้ตัดบล็อกของปุ่มก่อนแล้วค่อยถาม (พิสูจน์ว่ายัง fail ได้ด้วยการถอด label ออกจากปุ่มจริงหนึ่งตัว)

### ลำดับโฟกัส — เดิน Tab จริง 20 ครั้ง

`ScreenCheck --focus-order` ส่ง Tab ผ่านทางเดียวกับคีย์บอร์ดจริง แล้วอ่าน `AXFocusedUIElement` ทุกครั้ง ผลบนหน้าแชท:

| จุดที่โฟกัสหยุด | ซ้ำ |
|---|---|
| `AXTextField` ข้อความถึงผู้ช่วย | ทุก 3 ครั้ง |
| `AXTextField` ค้นข้อความในบทสนทนาเก่า | ทุก 3 ครั้ง |
| `AXOutline` Sidebar | ทุก 3 ครั้ง |

**อ่านว่า**: ลำดับ**วนกลับ**ที่เดิม (ไม่มีกับดัก ออกจากหน้าต่างไม่ได้ค้าง) และ**ทุกจุดมีชื่อ** — สองข้อนี้คือสิ่งที่ลำดับโฟกัสต้องผ่าน · แต่ **Tab ไปไม่ถึงปุ่มเลยสักตัว** ซึ่งไม่ใช่บั๊กของแอป: macOS ให้ Tab เดินเฉพาะช่องข้อความกับรายการ เว้นแต่ผู้ใช้เปิด Full Keyboard Access เอง — ตรงกับที่ §14.4 เขียนไว้ว่า "ไปถึงได้ถ้าไปเปลี่ยนการตั้งค่าระบบ" ไม่เท่ากับ "ไปถึงได้"

**สิ่งที่การเดินนี้จับได้**: ปุ่ม **"บทสนทนาใหม่" ไม่มีคีย์ลัด** ⇒ ในค่าเริ่มต้นของ macOS การเริ่มบทสนทนาใหม่ทำได้ด้วยเมาส์อย่างเดียว ซึ่งเป็นข้อที่ §14.4 มีไว้เพื่อกันพอดี — ใส่ **⌘N** แล้ว

### "ถ้าฟัง จะฟังว่าอย่างไร" — ตรวจป้ายในฐานะ*คำพูด* ไม่ใช่ในฐานะ*ช่องที่กรอกแล้ว*

"มีป้ายครบ" กับ "ฟังแล้วรู้ว่าอันไหนคืออันไหน" ไม่ใช่เรื่องเดียวกัน · `ScreenCheck` จึงถามเพิ่มสองข้อที่ตอบได้จากต้นไม้ตรง ๆ คือ **ป้ายที่ยาวเกิน 80 ตัวอักษร** (VoiceOver อ่านทั้งประโยค ไม่ได้ตัดให้) และ **ปุ่มที่ชื่อซ้ำกัน** (ได้ยินเหมือนกันทุกประการ) กวาด ⌘1–⌘5:

| พื้นที่ | ป้ายยาวเกิน 80 | ชื่อซ้ำ (รอบแรก) |
|---|---|---|
| แชท · แผน · ความรู้ · ระบบ | 0 | 0 |
| **โต๊ะทำงาน (⌘3)** | 0 | **4 ชุด** — ×3 "รันเซลล์นี้" · ×3 "ลบเซลล์นี้" · ×3 "Python" · ×3 "SQL" |

**เจอเพราะขับเท่านั้น**: โน้ตบุ๊กมีสามเซลล์ ⇒ ปุ่มรันสามปุ่มชื่อ "รันเซลล์นี้" เหมือนกันหมด · คำว่า "นี้" ทำงานได้ด้วย*สายตา* เพราะตาเห็นว่าปุ่มอยู่ในกรอบไหน แต่**หูไม่เห็นกรอบ** — คนที่ฟังอย่างเดียวได้ยิน "รันเซลล์นี้" สามครั้งติดกันโดยไม่มีอะไรบอกว่าเป็นเซลล์ที่เท่าไร ⇒ ร้อยเลขลำดับเข้าไปใน `CellView` แล้วเปลี่ยนเป็น **"รันเซลล์ที่ 1/2/3"**, **"ลบเซลล์ที่ N"**, **"ชนิดของเซลล์ที่ N"**

**ส่วน ×3 "Python" / ×3 "SQL" กลับไม่ใช่ความผิด** และการรีบแก้จะทำให้แย่ลง: มันคือ*ตัวเลือก*ในตัวเลือกแบบแบ่งช่อง ซึ่งอยู่ใต้ตัวควบคุมที่มีชื่อของตัวเองแล้ว ⇒ ที่ได้ยินจริงคือ "ชนิดของเซลล์ที่ 2, Python, เลือกอยู่" ซึ่งไม่กำกวมเลย · ตัวตรวจจึง**ไม่นับลูกที่พ่อแม่มีชื่อ** (`hasNamedParent`) — ถ้านับ ทุก segmented picker ในแอปจะขึ้นเป็นความผิดตลอดไป ซึ่งคือวิธีทำให้ตัวเลขนี้ไร้ความหมาย

หลังแก้และกวาดใหม่ทั้งห้าพื้นที่: **ป้ายยาวเกิน 80 = 0 · ชื่อซ้ำ = 0**

**ที่ยังเหลือจริง ๆ**: การไล่ดูด้วย VoiceOver เปิดจริงเพื่อฟังว่า*สำเนียงและจังหวะที่พูด*ฟังรู้เรื่องไหม — ต้นไม้ตอบได้ว่ามีชื่อ ชื่อไม่ซ้ำ ชื่อไม่ยาวเกิน และลำดับไม่พัง แต่ตอบไม่ได้ว่าเสียงสังเคราะห์อ่านคำไทยปนอังกฤษออกมาแล้วเพราะหูหรือเปล่า

## E.31 DB connector กับเซิร์ฟเวอร์จริง (2026-08-16)

แผนเขียนไว้ตั้งแต่ P6.2 ว่า PostgreSQL กับ MySQL "ใช้เส้นทางเดียวกันเป๊ะ" และ**ไม่มีใครยืนยันกับเซิร์ฟเวอร์จริง เพราะไม่มีเซิร์ฟเวอร์** · รอบนี้ยกคอนเทนเนอร์ชั่วคราวขึ้นมาสองตัวบนเครื่องนี้แล้วยิงจริงด้วย [`Sources/ConnectorCheck`](../Sources/ConnectorCheck/main.swift)

| สิ่งที่ยิง | ผล |
|---|---|
| PostgreSQL 16 — `ATTACH` + อ่าน `information_schema` + `SELECT` | ✅ ต่อได้ · เห็นตาราง · คืนค่าครบ |
| **ชื่อตารางและคอลัมน์ภาษาไทย** (`ผู้ป่วย`, `ชื่อ`, `คะแนน`) | ✅ อ่านผ่าน DuckDB ได้ตรง ไม่ต้องแปลง |
| MySQL 8 — เส้นทางเดียวกัน | ✅ ต่อได้ · `SELECT label, value FROM my.readings` คืน 2 แถวถูกต้อง |
| ชนิดข้อมูลที่ DuckDB รายงานกลับ | `varchar` / `double` ทั้งสองฝั่ง — ไม่มีคอลัมน์ไหนกลายเป็น NULL ทั้งคอลัมน์ (กับดักที่ E.x ของ P6.1 บันทึกไว้) |
| **รหัสผ่านผิด** | ✅ ล้มเหลวพร้อมข้อความอ่านรู้เรื่อง และ**รหัสผ่านถูกปิดเป็น `••••`** — DuckDB คืนคำสั่งที่ล้มเหลวกลับมาทั้งประโยค ซึ่งคือ connection string ที่มีรหัสผ่านอยู่ในนั้น |

**สรุป**: ข้อความในแผนที่ว่า "สองเส้นทางเหมือนกัน" เป็นจริงตามที่เขียน — ทั้งสองใช้ `ATTACH` แบบ key/value เดียวกัน ต่างกันแค่ชื่อ extension · และการปิดรหัสผ่านทำงานบนเส้นทางที่มันสำคัญที่สุด คือตอนล้มเหลว

**เก็บกวาดแล้ว**: คอนเทนเนอร์ทั้งสองถูกลบ (`--rm`) และ Docker ถูกปิดหลังวัดเสร็จ — ไม่มีอะไรค้างบนเครื่อง

## E.32 ขับแอปจริงแล้วเจอสองบั๊กที่เทสทั้งชุดมองไม่เห็น (2026-08-16)

ตั้งใจจะปิดของค้างของ **P15.1** (ถามผ่านหน้าแชทจริงให้ GX10 ตอบ) แต่การขับหยุดที่บั๊กสองตัวก่อน — **ทั้งคู่เป็นชนิดที่ชุดเทสสีเขียวทั้งชุดมองไม่เห็นโดยหลักการ ไม่ใช่เพราะเขียนเทสน้อย**

### 1. ฟิลด์ที่เพิ่มทีหลัง ทำให้แถวเก่าบันทึกอะไรไม่ได้อีกเลย

พิมพ์คำถามลงหน้าแชทแล้วกด "ส่ง" — ข้อความไม่ถูกบันทึก และบนจอขึ้นว่า

```
บันทึกข้อความไม่สำเร็จ: server(1): stmt 1 ERR: Couldn't coerce value for field
`pinned` of `conversation:ijab6unitfg3diz09izt`: Expected `bool` but found `NONE`
```

`DEFINE FIELD … TYPE bool DEFAULT false` **อ่านเหมือนครอบคลุมแถวที่มีอยู่แล้ว แต่ไม่ใช่**: `DEFAULT` เติมค่าตอน*สร้าง*แถว และแถวเก่าถูกสร้างไปแล้ว ⇒ ฟิลด์เป็น `NONE` และการตรวจชนิดจะไปเกิดตอน**อัปเดตแถวนั้นครั้งถัดไป** — อัปเดตอะไรก็ได้ ไม่ใช่เฉพาะที่แตะ `pinned` (การ `append` ข้อความแตะแค่ `updated_at`)

| ทำไมเทสจับไม่ได้ | |
|---|---|
| ฐานข้อมูลของเทสเกิดใหม่ทุกครั้ง | ทุกแถวถูกสร้าง*หลัง*ฟิลด์มีอยู่แล้ว จึงไม่มีแถวเก่าให้พัง |
| CI ก็เหมือนกัน | ความล้มเหลวนี้ต้องการ "เครื่องที่ใช้แอปมาก่อนหน้านี้" ซึ่งเป็นสิ่งเดียวที่ CI ไม่มี |

**เทสที่เขียน** จำลองแถวเก่าตามลำดับที่มันเกิดจริง — ถอดฟิลด์ออก สร้างแถว แล้วนิยามฟิลด์กลับ — แล้วยืนยันว่าแดงด้วยข้อความเดียวกันเป๊ะกับที่ผู้ใช้เห็น

**สิ่งที่แก้**: `bootstrap` เติมค่าย้อนหลังหลังนิยามฟิลด์เสร็จ และ **คำสั่งเติมถูก*สร้างจากรายการนิยามฟิลด์เอง* ไม่ได้เขียนมือ** — รายการที่เขียนมือคือรายการที่ล้าสมัยครั้งแรกที่มีคนเพิ่มฟิลด์แล้วไม่ได้นึกถึงไฟล์นี้อีกครึ่งหนึ่ง ซึ่งคือความผิดพลาดที่กำลังแก้อยู่พอดี · ฟิลด์ `option<…>` ถูกข้าม เพราะการไม่มีค่าคือความหมายของมัน · รันทุกครั้งที่เปิดแอป ไม่ผูกกับเลขเวอร์ชัน: การซ่อมที่ทำงานต่อเมื่อมีคนจำได้ว่าต้องบวกเลข คือการซ่อมที่จะถูกข้ามพอดีในครั้งที่สำคัญ

### 2. บูตค้างตลอดกาล เพราะถาม Keychain ว่า "โทเคนคืออะไร" แทนที่จะถามว่า "มีโทเคนไหม"

หลัง build ใหม่ แอปค้างที่ "กำลังเริ่มระบบ…" **ที่ CPU 0% ไม่มีกำหนด** · `sample` ตอบทันทีว่าค้างตรงไหน:

```
Engine.build → ChannelAccount.isReady → .token → SecretStore.value
  → KeychainVault.read → SecItemCopyMatching     (main thread, 1716/1716 samples)
```

`SecItemCopyMatching` ที่ขอ `kSecReturnData` คือการขอ**ตัวข้อมูล** และการคืนตัวข้อมูลคือสิ่งที่ ACL ของ item นั้นคุ้มครองอยู่ · แอปที่เพิ่ง build ใหม่คือไบนารีคนละตัวสำหรับ ACL นั้น ⇒ macOS ขึ้นกล่องขออนุญาต และ**เรียกไม่คืนจนกว่าจะมีคนตอบ** — บนเมนเธรด ทั้งแอปจึงรอ พร้อมตัวหมุนที่บอกไม่ได้ว่ารออะไร (ยืนยันด้วยภาพหน้าจอ: กล่อง *"Co-AI Workspace wants to use your confidential information stored in 'com.coaiworkspace.app.secrets'"*)

**คอมเมนต์สองบรรทัดเหนือจุดนั้นรู้กฎอยู่แล้ว** — *"a channel that cannot run must not stop the app from starting"* — แต่แพ้ที่**วิธีถาม ไม่ใช่สิ่งที่ตัดสิน**: `isReady` ต้องรู้แค่ว่า*มี*โทเคนไหม แล้วไปอ่าน*ค่า*เพื่อหาคำตอบ

**สิ่งที่แก้**: `SecretVault` มี `exists(_:)` แยกจาก `read(_:)` และฝั่ง Keychain ถาม**แอตทริบิวต์ ไม่ใช่ข้อมูล** ซึ่งไม่ติด ACL จึงขึ้นกล่องไม่ได้และค้างไม่ได้ · `status`/`has` เดินทางนี้ทั้งหมด ส่วน `value` ยังอ่านของจริงเหมือนเดิม — **ย้ายที่ ไม่ใช่เอาออก** และย้ายไปอยู่กับ channel ที่กำลังจะส่งจริง ซึ่งไม่ใช่เมนเธรดและไม่ใช่ตอนบูต

**วัดหลังแก้**: `sample` ชี้ว่าเมนเธรดอยู่ใน run loop ปกติ (1736/1736) ไม่ได้อยู่ใน `SecItemCopyMatching` อีก — ซึ่งคือความต่างที่วัดได้ตรง ๆ ระหว่างก่อนกับหลัง

### ที่ยังปิดไม่ได้ และเพราะอะไร

กล่อง Keychain ที่ค้างอยู่บนจอ **ขอรหัสผ่าน login keychain ของเจ้าของเครื่อง** ⇒ เป็นสิ่งที่ระบบนี้กรอกแทนไม่ได้และไม่ควรกรอก · ตราบใดที่ยังไม่มีคนตอบกล่องนี้ หน้าต่างแอปไม่ขึ้น จึงยังขับต่อไม่ได้ ⇒ **P15.1 ข้อ "ถามผ่านหน้าแชทจริง" ยังค้าง** และค้างที่คน ไม่ใช่ค้างที่โค้ด

## E.33 ตัวขับหน้าจอบนของจริง — และการ "พิมพ์สำเร็จ" ที่แอปไม่รู้เรื่องด้วย (2026-08-16)

ปิด **P17.1** และ **P17.2** ด้วยการขับบนแอปจริง (สิทธิ์ Accessibility ที่เจ้าของเครื่องให้ไว้แล้ว)

### P17.1 — กดปุ่มจากชื่อที่ screen reader อ่าน

| สิ่งที่ทำ | ผลจริง |
|---|---|
| กด "ส่งข้อความ" | `กด ส่งข้อความ \| ขึ้นใหม่: …` — ระบุด้วยว่าหน้าจอเปลี่ยนอะไรบ้าง |
| กด "โมเดล" ตอนมีห้าอันชื่อคล้ายกัน | **ปฏิเสธ**: "เจอที่มีคำว่า 'โมเดล' 5 อัน — ต้องระบุให้เจาะจงกว่านี้ ก่อนจะกดอันไหนก็ได้แล้วหวังว่าถูก" |
| กดชื่อที่ไม่มีบนจอ | บอกว่าหาอะไรไม่เจอ **และแสดงรายการที่เห็นจริง** ไม่ใช่คลิกที่ว่าง |

ข้อกลางคือข้อที่มีค่าที่สุด: กฎ "เจอสองอันขึ้นไป = error" เคยพิสูจน์ได้แค่ในเทส รอบนี้**ยิงใส่หน้าจอจริงแล้วมันยิงกลับ**

### P17.2 — พิมพ์ไทยลงช่องค้นหาแล้วผลค้นต้องเปลี่ยน (และรอบแรกมันไม่เปลี่ยน)

พิมพ์คำไทยลงช่อง "ค้นข้อความในบทสนทนาเก่า" — **ตัวอักษรขึ้นบนช่องครบ แต่รายการผลลัพธ์ไม่ขยับเลย ไม่ว่าจะพิมพ์คำไหน** รวมถึงคำที่อยู่ในข้อความที่เก็บไว้แบบเห็น ๆ ทุกคำได้ป้ายเดียวกันคือ *"— ตรงกับเรื่องที่คุยกัน ไม่ใช่คำที่พิมพ์ —"* ซึ่งเป็นป้ายของผลที่มาจาก**เวกเตอร์**เท่านั้น

ไล่ที่มาทีละชั้นแทนการเดา:

| ชั้น | วัดได้ว่า |
|---|---|
| ข้อความในฐานข้อมูลจริง | มีคำนั้นอยู่จริง 3 แถว |
| `BM25Index` บนคลังจริงทั้ง 42 ข้อความ (ดึงออกมารันนอกแอป) | **เจอ 3 hits คะแนน 4.168** · และ "หมดไฟ" ที่ไม่มีจริง = **0 hits** ⇒ ตัวค้นถูกต้อง |
| `ConversationStore.search` กับคลังรูปทรงเดียวกัน (เทสใหม่ 2 ข้อ) | ✅ ผ่าน — ยกประโยคที่ตรงมาให้ |

⇒ สิ่งที่ไม่เกิดขึ้นคือ **การค้นเอง** · `AXUIElementSetAttributeValue(kAXValue)` บน `TextField` ของ SwiftUI **คืน `.success`** แต่ไม่ได้เดินผ่าน responder chain ⇒ binding ไม่เปลี่ยน ⇒ วิวที่รันใหม่ด้วย `.task(id: query)` ไม่มีอะไรให้รันใหม่

**บทเรียนที่เป็นกฎ**: **การเขียนค่าที่ตัวควบคุมยอมรับ ไม่เท่ากับการเขียนที่แอปรับรู้** — และตัวขับ*แยกสองอย่างนี้จากภายนอกไม่ได้* เพราะค่าขึ้นบนจอเหมือนกันทั้งคู่ · เดิมโค้ดเลือก `AXValue` ก่อนด้วยเหตุผลว่า "เร็วกว่าและรบกวนน้อยกว่า" ซึ่งเป็นเหตุผลที่จริงและ**ตอบผิดคำถาม** ⇒ สลับลำดับ: **คีย์บอร์ดคือทางหลัก เขียนค่าคือทางสำรอง**สำหรับช่องที่รับโฟกัสไม่ได้ และเมื่อใช้ทางสำรอง หลักฐานจะเขียนออกมาตรง ๆ ว่า "แอปอาจไม่รู้ว่าค่าเปลี่ยน" · ราคาคือหนึ่งคีย์ต่อหนึ่งตัวอักษร ซึ่งเป็นราคาที่ถูกกว่าตัวขับที่รายงานว่าสำเร็จทั้งที่แอปข้างใต้ไม่ได้ทำอะไร — ความล้มเหลวชนิดเดียวกับการคลิกที่พิกัด

**วัดใหม่หลังแก้** — ผลเปลี่ยนตามคำที่พิมพ์จริง และแยกได้สี่แบบตามที่ออกแบบไว้:

| พิมพ์ | ได้ |
|---|---|
| `ผ่าตัด` (อยู่กลางประโยคไม่มีช่องว่างล้อม) | **ยกประโยคนั้นมา** — ตรงด้วยคำ |
| `นาที` (ท้ายประโยค) | ยกประโยคนั้นมา |
| `หมดไฟ` (ไม่มีในข้อความ แต่เรื่องใกล้กัน) | *"— ตรงกับเรื่องที่คุยกัน ไม่ใช่คำที่พิมพ์ —"* — ตรงด้วยเวกเตอร์ และ**บอกว่าตัวเองเป็นแบบไหน** |
| `เบาหวาน` (ไม่มีและไม่ใกล้) | **ไม่มีผลลัพธ์เลย** |

แถวที่สามคือเหตุผลที่ป้ายนั้นมีอยู่: ผลที่มาจากเวกเตอร์ล้วนที่แสดงบรรทัดแรกของบทสนทนาเป็น "ผลการค้น" คือการทำให้คนอ่านเชื่อว่าเจอคำที่พิมพ์

## E.34 แท็บจำที่ของตัวเองไหม — และการวัดที่กลืนคำปฏิเสธของตัวเองทิ้ง (2026-08-16)

ปิด **P21.1** ด้วยการขับจริง และรอบนี้**สิ่งที่ผิดคือการวัด ไม่ใช่แอป** ซึ่งเป็นบทเรียนที่ใหญ่กว่าตัว task

### สิ่งที่วัดได้ในที่สุด

เปิดสามแท็บ ตั้งคนละพื้นที่ แล้วไล่กลับ:

| ขั้น | ตั้ง | อ่านกลับ |
|---|---|---|
| 1 | tab1 = โต๊ะทำงาน | โต๊ะทำงาน |
| 2 | General = คลังความรู้ | คลังความรู้ |
| 3 | tab2 = ระบบ | ระบบ |
| 4 | กลับ tab1 | **โต๊ะทำงาน** |
| 5 | กลับ General | **คลังความรู้** |
| 6 | กลับ tab2 | **ระบบ** |

⇒ Done-when ของ P21.1 ("แต่ละอันจำสถานะของตัวเอง · ไม่มีข้อมูลของอีกโปรเจกต์รั่วมา") **ผ่านบนหน้าจอจริง**

### ทางที่ไปผิด และทำไมมันดูน่าเชื่อ

รอบแรกวัดได้ว่า **ทั้งสามแท็บอ่านกลับเป็น "ระบบ" หมด** ซึ่งอ่านเหมือนบั๊กรั่วข้ามแท็บที่ชัดเจนมาก · ที่จริงคือ**ไม่มีการสลับแท็บเกิดขึ้นเลยสักครั้ง**: คำสั่งกดแท็บถูก**ปฏิเสธ**เพราะชื่อกำกวม —

```
"แท็บ Burnout among ICU nurses · กดเพื่อสลับมา"
"ปิดแท็บ Burnout among ICU nurses — ปิดแค่หน้าต่าง ไม่ใช่ปิดโครงการ"
```

คำว่า `ปิดแท็บ` **ลงท้ายด้วย** `แท็บ` ⇒ ถามหา "แท็บ X" แล้วเจอสองอัน ⇒ ตัวขับปฏิเสธตามกฎของมันเอง (ซึ่งถูกต้อง) · **แต่สคริปต์ที่ใช้วัดเขียนว่า `>/dev/null`** ⇒ คำปฏิเสธห้าครั้งอ่านออกมาเป็นการสลับแท็บสำเร็จห้าครั้ง และสิ่งที่เกิดขึ้นจริงคือการเปลี่ยนพื้นที่ของแท็บ General ห้ารอบ

**บทเรียน**: *ตัวขับที่ปฏิเสธอย่างถูกต้อง ไม่มีค่าเลยถ้าผู้เรียกทิ้งคำปฏิเสธ* — และความเสียหายไม่ใช่แค่เสียเวลา แต่คือ**เกือบยื่นบั๊กใส่แอปในเรื่องที่แอปไม่เคยถูกสั่งให้ทำ** · เทียบเคียงตรง ๆ กับ E.33: ที่นั่นตัวขับรายงานสำเร็จทั้งที่แอปไม่รู้เรื่อง ที่นี่ตัวขับรายงานล้มเหลวแต่ผู้เรียกไม่ฟัง — ความล้มเหลวเงียบสองด้านของสิ่งเดียวกัน

**ตรวจสมมติฐานย้อนหลังแล้ว**: build โค้ดเดิม (ก่อนแก้) พร้อม trace แล้ววัดด้วยวิธีที่กดติดจริง — **โค้ดเดิมก็ผ่านทั้งหกขั้น** ⇒ ที่แก้ไปจึงเป็น **การรัดกุมขึ้น ไม่ใช่การแก้บั๊กที่วัดได้** และบันทึกไว้ตรงนี้อย่างนั้น

### สิ่งที่แก้จริงในรอบนี้

1. **`TabAreaMemory` (ProjectKit, 5 เทส)** — เดิมเป็น `onChange` สองตัวบน state สองก้อน และ**ทั้งคู่ทิ้งค่า `previous` ที่ SwiftUI ส่งให้** แล้วไปอ่าน `active` เพื่อเอา id มาเก็บ ซึ่งระหว่างการสลับมันขยับไปแล้ว ⇒ แท็บที่กำลัง*ออก*ถูกเก็บใต้ชื่อแท็บที่กำลัง*เข้า* · และเพราะการกู้คืนเขียนลง `area` ตัวเดียวกับที่ตัวบันทึกเฝ้าอยู่ **การกู้คืนจึงแยกไม่ออกจากการที่คนเลือกเอง** ⇒ เหลือ observer เดียวที่รับทั้งสองปลายของการสลับมาพร้อมกัน (`leaving` / `showing` / `arriving`) ไม่มีอะไรต้องเดาจาก state ที่กำลังเคลื่อน · เทสที่ทำให้แดงก่อนคือการถอดความพฤติกรรมเดิมตรง ๆ (เก็บใต้ id ปลายทาง)
2. **"ตรงที่ต้นชื่อ ชนะตรงที่กลางชื่อ" ใน `ElementFinder` (4 เทส)** — ตัวควบคุมที่ชื่อ*ขึ้นต้น*ด้วยสิ่งที่ถาม คือตัวที่ถูกเรียกชื่อ ส่วนตัวที่แค่*เอ่ยถึง*คืออีกตัวที่พูดถึงเรื่องเดียวกัน · **เป็นการหุบวงเท่านั้น**: ถ้าไม่มีอันไหนขึ้นต้นตรง ก็ใช้ชุดเดิม และเสมอจริง (ปุ่ม "บันทึก" สามอัน) ยัง**ปฏิเสธเหมือนเดิม** เพราะกฎห้ามเดายังเป็นเหตุผลของฟังก์ชันนี้ทั้งฟังก์ชัน
3. **`AXNavigator.locate` มีตรรกะการจับคู่ของตัวเอง** และไม่ได้รับกฎข้อ 2 ไปด้วย ⇒ แก้แล้วทั้งสองทางใช้ helper เดียวกัน — **การมีสองอิมพลีเมนต์ของ "ชื่อนี้หมายถึงตัวไหน" คือวิธีที่อันหนึ่งได้กฎที่อีกอันไม่มี** ซึ่งคือสิ่งที่เพิ่งเกิดขึ้นจริง

## E.35 ตาข่ายกันถอยหลังสำหรับสิ่งที่ตัดสินใจก่อนถามโมเดล (P9.1, 2026-08-16)

P9.1 ค้างมาตลอดด้วยเหตุผลว่า "ต้องมีงานจริงที่สำเร็จแล้วพอเป็นชุด regression ก่อน" ซึ่ง**จริงสำหรับรูปที่คิดไว้ตอนแรก** (เล่นซ้ำการรันของ agent ทั้งรอบ) และรูปนั้นไปต่อไม่ได้: การเล่นซ้ำต้องมีโมเดล และโมเดลคือสิ่งเดียวที่ `check.sh` บนแล็ปท็อปไม่มี

**สิ่งที่ควรตรึงไม่ต้องใช้โมเดลเลย** — ก่อนจะถาม LLM สักคำ ระบบตัดสินไปแล้วว่า **tier ไหนจะตอบและเพราะอะไร**, **ทูลที่กำลังจะเรียกอันตรายแค่ไหนและเพราะอะไร** ทั้งสองเป็นฟังก์ชันบริสุทธิ์ของคำขอ และเป็นจุดที่การถอยหลังแบบเงียบแพงที่สุด: ไม่มีอะไรพัง ไม่มีอะไร fail — คำตอบแค่เริ่มมาจากโมเดลที่เล็กลง หรือคำสั่งเชลล์เลิกถามก่อนรัน และสัญญาณแรกไปโผล่ในผลงานของใครบางคนอีกหลายสัปดาห์ถัดมา

**รูปแบบ**: ชุดงานคงที่ + ไฟล์บันทึกการตัดสินใจวางไว้ข้าง ๆ เทส · **ไฟล์คือสาระ** — `#expect` บอกว่า "อันนี้ควรเป็นความเสี่ยงสูง" ส่วนไฟล์บอกว่า**ภาพรวมของการตัดสินใจทั้งชุดวันนี้หน้าตาแบบไหน** และ diff ของมันอ่านรู้เรื่องสำหรับคนที่ไม่ได้อยู่ตอนเขียน · การเปลี่ยนพฤติกรรมยังทำได้ แต่ต้องแก้ไฟล์ที่ commit ไว้ในคอมมิตเดียวกับที่เปลี่ยนพฤติกรรม ซึ่งเป็นสิ่งเดียวที่ตาข่ายนี้พยายามบังคับ

**พิสูจน์ว่าจับได้จริง** — ปิดกฎ "งานที่ผิดแล้วเสียหายไม่ใช้ on-device" (E.7) ชั่วคราวแล้วรัน:

```
การตัดสินใจเปลี่ยนไปจากที่บันทึกไว้ใน routing.golden — บรรทัดที่ 26
    เดิม: ลำดับที่พิจารณา: gx10 → mlx-qwen
    ใหม่: ลำดับที่พิจารณา: gx10 → mlx-qwen → apple-fm
```

⇒ จับได้ตรงจุด และ**บอกบรรทัดที่ต่าง ไม่ใช่พ่นเอกสารสองชุดมาเทียบเอง** เพราะ diff 60 บรรทัดในผลเทสคือกำแพงที่ไม่มีใครอ่าน

**ที่ยังไม่ครอบคลุม**: การเล่นซ้ำแผนของ agent จริง ๆ ยังต้องมี endpoint และยังทำไม่ได้ใน `check.sh` — ตรงนี้บันทึกไว้ว่ายังเป็นช่องว่าง ไม่ใช่ปิดไปเงียบ ๆ

|---|---|
| พร็อกซี TCP บน `127.0.0.1:18010` → GX10 (เพื่อ**ตัดสายได้จริงโดยไม่ต้องแตะการตั้งค่าระบบ**) | ✅ ต่อผ่านได้ `/v1/models` ตอบปกติ |
| ชี้ endpoint GX10 ไปที่พร็อกซี แล้วเปิดแอปใหม่ | ✅ หน้าสถานะขึ้น **"GX10 — พร้อมใช้"** ผ่านพร็อกซี |
| ถามผ่านหน้าแชทจริง (พิมพ์ด้วยตัวขับ กด "ส่งข้อความ") | ✅ ส่งได้ · บันทึกได้ (การแก้ `pinned` ใน E.32 ยืนยันบนของจริงอีกครั้ง) |
| **ให้ GX10 เป็นตัวที่ตอบ** | ❌ **ทำไม่ได้จากหน้าจอ** |

**ทำไมถึงทำไม่ได้ และทำไมมันสำคัญกว่าที่คิด**

ลำดับของ §9.2 ทำงานถูกต้องตามที่เขียนไว้: เทิร์นในหน้าแชทเป็น `.disposable` (มีคนนั่งรอ) จึงเรียงจาก tier ที่ใกล้ที่สุดขึ้นไป และเพราะเทิร์นมีทูลติดไปด้วย **Tier 0 ถูกตัดออกเองอัตโนมัติ** (Foundation Models เรียกทูลไม่ได้) ⇒ ผู้ชนะคือ **Tier 0.5 โมเดล 4B บนเครื่อง** ทุกครั้ง ซึ่ง*ถูกต้องเรื่องค่าใช้จ่าย*

แต่เมื่อไล่หาวิธีบอกระบบว่า "คำถามนี้ขอตัวใหญ่หน่อย" **ไม่มีเลยสักทาง**:

- หน้าโมเดลมีแค่ **"ใช้ตัวนี้"** กับ **"ลบ"** — *ไม่มีปุ่มเลิกใช้* Tier 0.5
- ไม่มีตัวเลือก "ตอบด้วย endpoint นี้" ที่หน้าแชท
- `RoutingPolicy` ตัดสินจากชนิดของงาน ไม่ใช่จากที่คนขอ

⇒ **ข้อค้างของ P15.1 ไม่ใช่ "ยังไม่ได้ทดสอบ" แต่คือ "ยังไม่มีของให้ทดสอบ"** — สิ่งที่ขาดคือ*ตัวควบคุม* ไม่ใช่*การวัด* · และมันคือสิ่งที่คนอยากได้พอดีในนาทีที่โมเดลเล็กตอบไม่ดี ซึ่งเป็นนาทีที่เกิดขึ้นจริงบ่อยที่สุด

**สิ่งที่เจอระหว่างทางด้วย**: บทสนทนายาว (42 ข้อความ) ทำให้เทิร์นเข้าสู่ **"ย่อบทสนทนาให้พอดีหน้าต่างบริบท"** และการย่อนั้นวิ่งบน Tier 0.5 — บนเครื่องนี้มันช้าพอที่**หน้าจอดูเหมือนค้าง**ทั้งที่กำลังทำงาน · แถบสถานะบอกว่ากำลังย่ออยู่ ซึ่งถูกแล้ว แต่ไม่มีตัวเลขว่าเหลืออีกเท่าไร

**เก็บกวาดแล้ว**: พร็อกซีปิด · `baseURL` ของ GX10 กลับไปที่ `192.168.1.205:8000` · โฟลเดอร์โมเดลที่ย้ายออกไปชั่วคราวถูกย้ายกลับ · `defaultEndpointID` ตั้งกลับเป็น `migrated-self-hosted` ตามเดิม — **ไม่เปลี่ยนค่าที่เจ้าของเครื่องตั้งไว้โดยไม่ได้ขอ** แม้ปลายทางนั้นจะต่อไม่ได้ในตอนนี้ (การเปลี่ยน default ให้เป็น GX10 เป็นการตัดสินใจของเจ้าของ ไม่ใช่ผลพลอยได้จากการทดสอบ)

## E.37 สร้างสวิตช์ที่ E.36 บอกว่าไม่มี แล้ว GX10 ก็ตอบผ่านหน้าแชทจริง (2026-08-16)

E.36 จบด้วยข้อสรุปว่าของค้างของ P15.1 **ไม่ใช่การทดสอบ แต่คือของที่ยังไม่มี** — รอบนี้จึงสร้างมัน

**กติกาที่ทำให้ตัวเลือกนี้ไม่กลายเป็นช่องโหว่** (5 เทส) — *ตัวเลือกคือ **ลำดับ** ไม่ใช่ **ตัวกรอง***:

| กฎ | เหตุผล |
|---|---|
| เลื่อนขึ้นหน้าแถว **ไม่ตัดตัวอื่นทิ้ง** | endpoint ที่เลือกไว้ล่มกลางคำถาม = ตอบช้าลง ไม่ใช่ตอบไม่ได้ · ตัวกรองจะทำให้สายหลุดเส้นเดียวกลายเป็นแอปตาย |
| **เลือกแล้วไม่ทำให้ tier ที่ทำงานนี้ไม่ได้ กลายเป็นทำได้** | ขอโมเดลที่เรียกทูลไม่ได้ ในเทิร์นที่ต้องเรียกทูล = คำขอที่ทำตามไม่ได้ ⇒ **ปฏิเสธโดยระบุชื่อ** ในบรรทัดเดียวกับที่อธิบายการตัดตัวอื่น ไม่ใช่เมินเงียบ ๆ |
| **เลือกแล้วไม่ปลดล็อกการใช้เงิน** | ไม่งั้นตัวเลือกบนหน้าจอกลายเป็นวิธีจ่ายเงินโดยไม่มีการตัดสินใจจ่ายเงิน · ข้อความปฏิเสธพูดทั้งสองครึ่ง ("คุณเลือกไว้ แต่…ไม่ได้อนุญาตให้ใช้เงิน") เพราะครึ่งเดียวอ่านเป็นบั๊ก หรือไม่ก็ไม่บอกว่าต้องแก้อะไร |
| **ชื่อที่ไม่ตรงกับอะไรเลย = ไม่เปลี่ยนอะไร ไม่ใช่ error** | endpoint ถูกลบได้ในขณะที่บทสนทนายังจำชื่อมันอยู่ — การทำให้บทสนทนานั้นค้างคือคำตอบที่แย่กว่าการวิ่งตามลำดับปกติ |
| **ตัวเลือกอยู่ในคำอธิบาย** | ถ้าไม่โผล่ในบรรทัดเหตุผล คำอธิบายว่า "ทำไมคำตอบมาจากที่นี่" จะกลายเป็นคำอธิบายที่ผิด |

**ต่อหนึ่งบทสนทนา ไม่ใช่ค่าตั้งรวม** — คำถามคือ "รอบ*นี้*ขอตัวใหญ่" และค่าที่อยู่ยาวกว่าคำถามจะแอบใช้โมเดลใหญ่กับทุกอย่างหลังจากนั้น

**ขับจริงแล้ว**: กดตัวเลือกในหน้าแชท → เลือก `GX10 · 1a` → พิมพ์ "17 คูณ 3 เท่ากับเท่าไร" → ส่ง

```
บนหน้าจอ:  คุณเลือก GX10 ไว้สำหรับคำถามนี้ — ถ้าเรียกไม่ได้จะไล่ต่อตามลำดับเดิม
คำตอบ:     17 คูณ 3 เท่ากับ 51
```

**หลักฐานเสริมที่ไม่ได้ตั้งใจให้เป็นหลักฐาน**: คำถามเดียวกันนี้ตอนที่ Tier 0.5 ตอบ ได้ข้อความไทยที่สระหายเป็น `17 คณ 3 เทากบ 51` (เห็นในบทสนทนาเก่าบนเครื่องนี้) · รอบนี้ตัวอักษรครบทุกตัว ⇒ **คนละโมเดลตอบจริง** ไม่ใช่แค่ป้ายเปลี่ยน

⇒ **P15.1 ปิดข้อ "ถามผ่านหน้าแชทจริงแล้ว GX10 ตอบ" ได้แล้ว** · ที่ยังเหลือคือการตัดสายกลางสตรีมบนหน้าจอจริง ซึ่งตอนนี้*ทำได้แล้ว*เพราะมีทางเลือกให้บังคับ Tier 1 (เดิมบังคับไม่ได้เลย จึงตัดสายให้ดูก็ไม่มีความหมาย)

## E.38 ตัดสายกลางสตรีมบนหน้าจอจริง — และความเงียบที่ระบบเรียกว่า "สำเร็จ" (2026-08-16)

ข้อสุดท้ายของ **P15.1** · ทำได้เพราะ E.37 เพิ่งสร้างตัวเลือกที่บังคับ Tier 1 ได้ (ก่อนหน้านี้ทุกเทิร์นไปลงที่โมเดลบนเครื่อง การตัดสายจึงไม่ได้พิสูจน์อะไร) · ตัดด้วยการฆ่าพร็อกซี TCP ที่คั่นอยู่ ⇒ **สายขาดจริงกลางคำตอบ โดยไม่ต้องแตะการตั้งค่าระบบ**

**รอบแรก — สิ่งที่คนเห็นคือไม่มีอะไรเลย**

```
คำถามของตัวเอง
▸ ความคิดของโมเดล 2 วินาที        ← พับอยู่
(จบ)
```

ไม่มีคำตอบ ไม่มีข้อความผิดพลาด ไม่มีอะไรบอกว่าเกิดอะไรขึ้น · ทางจัดการความล้มเหลวกลางสตรีมที่เขียนไว้แล้ว (`"สตรีมคำตอบขาดกลางคัน"`) **ไม่ทำงาน เพราะไม่มีอะไร throw**: การเชื่อมต่อ SSE ที่หลุดไม่ได้โยน error เสมอไป — ซ็อกเก็ตปิด การวนจบ และ**สตรีมที่ว่างเปล่าแยกไม่ออกจากสตรีมที่พูดจบพอดี** ⇒ เทิร์นเดินเข้าทาง "สำเร็จ" โดยไม่มีข้อความและไม่มีการเรียกทูล แล้วรายงานความสำเร็จด้วยการเงียบ

**กฎที่ได้จึงไม่เกี่ยวกับการเชื่อมต่อเลย** — และนั่นคือเหตุผลที่มันควรอยู่ที่ชั้นเทิร์น ไม่ใช่ชั้นขนส่ง: **รอบที่ไม่ได้ผลิตข้อความและไม่ได้เรียกทูล คือรอบที่ยังไม่ได้ตอบ** ไม่ว่าด้วยเหตุใด · คำตอบที่ถูกตัด · โมเดลที่คืนมาแต่ความคิด · เซิร์ฟเวอร์ที่ปิดก่อน — จากที่ที่คนนั่งอยู่ ทั้งหมดนี้คือสิ่งเดียวกันคือ**คำตอบเปล่า** และการรายงานคำตอบเปล่าว่าเป็นเทิร์นที่สำเร็จ คือระบบอ้างว่าทำสิ่งที่มันไม่ได้ทำ (§2.5)

**รอบสอง หลังแก้ (2 เทสที่แดงมาก่อน)** — ตัดที่เดิม:

```
GX10 คิดอยู่แล้วหยุดกลางคัน — ไม่มีคำตอบส่งกลับมา ·
อาจเป็นการเชื่อมต่อที่ขาดโดยไม่แจ้ง ลองถามใหม่ หรือเลือกโมเดลอื่นที่ช่องเลือกข้างกล่องข้อความ
```

**ระบุชื่อว่าใครเงียบ** (ไม่งั้นคนอ่านไม่รู้จะไปดูที่ไหน) และ**บอกทางออกที่มีอยู่จริงบนหน้าจอเดียวกัน** ซึ่งคือตัวเลือกที่ E.37 เพิ่งใส่ไว้

⇒ **P15.1 ปิดครบทุกข้อแล้ว** · และข้อนี้ให้ผลตรงกับที่ Done-when ตั้งใจ: การถอดสายไม่ได้ไปยืนยันว่าข้อความผิดพลาดสวยดี แต่ไปเจอว่า**ไม่มีข้อความผิดพลาดเลย**

**เก็บกวาด**: พร็อกซีปิด · `baseURL` กลับไปที่ LAN · `defaultEndpointID` เป็น `migrated-self-hosted` ตามที่เจ้าของเครื่องตั้งไว้
