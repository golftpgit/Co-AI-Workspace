## 1. หลักการ 7 ข้อ

เรียงตามลำดับความสำคัญ — **ข้อบนชนะข้อล่างเสมอเมื่อขัดกัน** นี่คือสิ่งที่ทำให้มันเป็นหลักการ ไม่ใช่รายการความชอบ

| # | หลักการ | คำที่ใช้ตัดสิน | ตัวอย่างที่เคยผิดในแอปนี้ |
|---|---|---|---|
| **1** | **ตัวเลขต้องอ่านถูก** | อะไรที่คนอ่านค่าออกไปใช้ตัดสินใจ (p-value · ช่วงความเชื่อมั่น · เงิน · เวลา · โทเคน) อยู่บนพื้นทึบเสมอ ห้ามมีอะไรวิ่งผ่านข้างหลัง | — (กฎนี้บังคับใน `check.sh` แล้ว) |
| **2** | **สถานะที่แสดงต้องเป็นสถานะจริง** | ถ้าหน้าจอบอกว่า "พร้อมใช้" แล้วกดไม่ได้ = บั๊กระดับสูงสุด · ค่าที่ต้องรีสตาร์ทถึงมีผล **ต้องบอกตรงนั้น** | เพิ่ม endpoint GX10 แล้วหน้าแชทไม่มีให้เลือก เพราะ router ประกอบตอน boot — ไม่มีอะไรบนหน้าจอบอก ([AUDIT F-1](AUDIT_2026-08-17.md)) |
| **3** | **การตัดสินใจอยู่ตรงที่มืออยู่** | สิ่งที่เป็นการตัดสินใจ *ต่อเทิร์น* (โมเดล · ใบงาน · โหมด) อยู่ในหรือติดช่องพิมพ์ · สิ่งที่เป็นการตั้งค่า *ระยะยาว* อยู่ใน ระบบ | ตัวเลือกโมเดลเคยอยู่แต่ในหน้า settings (U18) |
| **4** | **บอกเหตุผล ไม่ใช่แค่ผล** | ทุกครั้งที่ระบบเลือกแทนคน (tier ไหน · ทูลไหน · ทำไมถูกปฏิเสธ) ต้องกดดูเหตุผลได้ และเหตุผลต้องมาจาก *กลไกที่เลือกจริง* ไม่ใช่ให้โมเดลเขียนอธิบายย้อนหลัง | P20.5 · `routedWhy` |
| **5** | **ที่เดียวต่อหนึ่งความหมาย** | ปัญหาเดียวกันต้องแก้ด้วย control ตัวเดียวกันทั้งแอป — ห้ามมี `GroupBox` ที่หนึ่ง `List` ที่หนึ่ง แถวปุ่มอีกที่หนึ่งสำหรับเรื่องเดียวกัน | §24.1 ระบุเองว่านี่คือข้อที่แย่ที่สุด |
| **6** | **ตำแหน่งไม่ขยับ** | หน้าจอปรับ *การเน้น* ตาม project type ได้ แต่ **ห้ามย้ายตำแหน่ง** — คนหาของด้วยตำแหน่งก่อนอ่านตัวหนังสือเสมอ | P20.6 (ทำถูกแล้ว: ใส่ `•` นำหน้าแท็บที่เน้น ไม่ได้เรียงใหม่) |
| **7** | **คำอธิบายไม่ถูกลบ ถูกย้าย** | บรรทัดแรก = คำตอบ · เหตุผลไปอยู่ `help`/popover — คำอธิบายในแอปนี้คือสิ่งที่ทำให้ตัวเลข *เถียงได้* จะลบไม่ได้ | §24.1 |

## 2. Information Architecture — โครงจริงในแอปวันนี้

**5 พื้นที่ (⌘1–⌘5) + ⌘0 ไปสถานะระบบ** — อ่านจาก `CoAIWorkspaceApp.Area` และ `SubTab` โดยตรง

| ⌘ | พื้นที่ | คำถามที่พื้นที่นี้ตอบ | Sub-tab (ตามโค้ดวันนี้) | เห็นใน General? |
|---|---|---|---|---|
| ⌘1 | **สนทนา** | จะให้ใครทำอะไร | *ไม่มี sub-tab* — ใช้โครงสามเสาแทน | ✅ |
| ⌘2 | **แผนงาน** | ตกลงกันว่าอะไรคือเสร็จ ใครรับผิดชอบ | *ไม่มี sub-tab* — ใช้แถบซ้ายภายในหน้า | ✅ (ขึ้นว่าไม่มีแผน + รายการโปรเจกต์) |
| ⌘3 | **โต๊ะทำงาน** | ข้อมูลอยู่ไหน ทำอะไรกับมัน | เก็บข้อมูล · ลงรหัส · ฐานข้อมูลภายใน · ฐานข้อมูลภายนอก · สคริปต์+คอนโซล · ผลลัพธ์+เอกสาร | ⚠️ เห็น 3 จาก 6 (ภายนอก · สคริปต์ · ผลลัพธ์) |
| ⌘4 | **คลังความรู้** | อะไรจริง และรู้ได้ยังไง | เอกสาร · กราฟ · ข้อขัดแย้ง · แหล่งและ tier | ✅ ครบ 4 |
| ⌘5 | **ระบบ** | เครื่องมือตั้งค่ายังไง | โมเดล · งบ+endpoint · ช่องทาง · สถานะระบบ · สายบังคับบัญชา · ผังหน้าจอ | ✅ ครบ 6 |

> **สองจุดที่ ARCH §19.2 ยังเขียนไว้ผิดจากของจริง** (ต้องแก้ที่ ARCH ไม่ใช่ที่นี่):
> - §19.2 บอกว่า "Knowledge มี 3 sub-tab ไม่ใช่ 4 — กราฟยังไม่แยกแท็บ" · **โค้ดวันนี้มี 4 แท็บและมีแท็บกราฟจริง**
> - §19.2 วาง "ระบบ" ไว้เป็น *(นอกพื้นที่งาน)* · **โค้ดวันนี้ระบบเป็นพื้นที่เต็มที่ 5 มี 6 sub-tab** และมีสองแท็บที่ตารางนั้นไม่มีเลย (สายบังคับบัญชา · ผังหน้าจอ)
> - §19.2 ไม่มี "ลงรหัส" ใน Workbench · **โค้ดมี**

**ผังหน้าจอ (⌘5 → ผังหน้าจอ) คือของจริงที่ตรวจได้** — `IAInventory.swift` มีหนึ่งแถวต่อหนึ่งหน้าจอใน §14.2 พร้อมสถานะ ครบ/บางส่วน/ยังไม่ได้ทำ และ `check.sh` แดงถ้ามีหน้าใน §14.2 ที่ไม่มีแถว **ให้ถือว่านี่คือความจริง ไม่ใช่ตารางในเอกสาร**

## 3. โครงสามเสา — ซ้าย · กลาง · ขวา

โครงนี้ตัดสินไว้แล้วเมื่อ 2026-08-13 (§19.2.6) โดยอ้างจาก Claude Code desktop **ใช้กับพื้นที่ "สนทนา" เต็มรูปแบบ ส่วนพื้นที่อื่นใช้เท่าที่ตรง**

```
┌────────────┬────────────────────────────────┬──────────────┐
│  ซ้าย       │  กลาง                          │  ขวา          │
│  ที่อยู่     │  งานที่ทำอยู่                    │  หลักฐาน       │
├────────────┼────────────────────────────────┼──────────────┤
│ แถบแท็บ     │ [หัวเรื่อง + ไอคอนเครื่องมือเล็ก]  │ เฝ้าดูทีม      │
│ workspace  │                                │ โปรเซส        │
│            │  บทสนทนา / sub-tab             │ span ของเทิร์น │
│ รายการ      │  (คอลัมน์เดียว กว้างจำกัด)        │ หลักฐานใบงาน   │
│ บทสนทนา     │                                │ diff ไฟล์      │
│            │  ┌──────────────────────────┐  │              │
│            │  │ แถบตัดสินใจ (ถ้ามี)         │  │              │
│            │  ├──────────────────────────┤  │              │
│            │  │ ช่องพิมพ์ + ชิปควบคุมโหมด   │  │              │
│            │  └──────────────────────────┘  │              │
├────────────┴────────────────────────────────┴──────────────┤
│  แถบสถานะ 6 ช่อง (กดได้ทุกช่อง) — เฉพาะเมื่ออยู่ในโปรเจกต์        │
└─────────────────────────────────────────────────────────────┘
```

### 3.1 กฎของแต่ละเสา

| เสา | ใส่อะไรได้ | **ห้ามใส่** |
|---|---|---|
| **ซ้าย** | ที่อยู่: workspace ที่เปิดอยู่ · รายการบทสนทนา (จัดกลุ่มตาม workspace **ไม่ใช่รายการแบน**) · ค้น · ปักหมุด | เนื้อหา · การตั้งค่า |
| **กลาง** | สิ่งที่กำลังทำ · คอลัมน์เดียว **จำกัดความกว้างไว้เสมอ** · เครื่องมือของหน้านี้เป็นไอคอนเล็กบนหัวเรื่อง | แถบเครื่องมือเต็มความกว้าง |
| **ขวา** | **ของที่พิสูจน์** — span · หลักฐาน · diff · รายงานที่เพิ่งออก | **ของที่ตั้งค่า** — ถ้ามันเป็นการตั้งค่า มันอยู่ผิดที่ |

### 3.2 สองอย่างที่ยืมมาแล้วสำคัญกว่าต้นฉบับ

1. **แถบตัดสินใจลอยเหนือช่องพิมพ์** — สิ่งที่ระบบอยากให้ตัดสิน อยู่ตรงที่มืออยู่ ไม่ใช่ในหน้าอื่น
   ของเรา = **Exception Report · ประตูขั้นที่พร้อมแล้ว · คำขอเปลี่ยนแปลงที่รออยู่ · การอนุมัติทูล**
2. **ตัวควบคุมโหมดอยู่ในช่องพิมพ์** — ของเรา = **โมเดล/tier · ใบงานที่กำลังทำ · Plan-only · Run-until-done · โฟลเดอร์งาน · มิเตอร์บริบท**

### 3.3 แถบสถานะ 6 ช่อง — เป็นแดชบอร์ดที่กดได้ ไม่ใช่ป้าย

ทุกช่องเปิด popover ที่มีทั้ง **ที่มาของตัวเลข** และ **ปุ่มที่ทำอะไรได้จริง**

| ช่อง | กดแล้วเห็น | ทำอะไรได้ตรงนั้น |
|---|---|---|
| ขั้น | เงื่อนไข gate ถัดไป ข้อไหนผ่าน/ค้าง | กดข้อที่ค้าง → กระโดดไปต้นเหตุ |
| เวลา | เส้นเวลาที่ใช้เทียบ p50–p90 ของงานชนิดเดียวกัน **พร้อมชื่อประชากรที่ใช้คำนวณ** | ขยายกรอบ (บันทึกเป็นการตัดสินใจ) |
| งบ | แยกตาม role และทูล + กราฟการเผาไหม้ | ปรับเพดานขั้นนี้ · สลับ tier ของ role |
| คุณภาพ | rework กี่รอบ + เหตุผลจาก QA ทุกรอบ | สั่ง rework · ผ่อน DoD (บันทึก) |
| ขอบเขต | ส่วนต่างจาก baseline รายใบ | เปิดคำขอเปลี่ยนแปลง |
| Exception | Exception Report เต็ม | ตัดสินตรงนั้น |

## 5. ชั้นและวัสดุ — Solid vs Glass

**นี่ไม่ใช่รสนิยม** แอปนี้แสดงค่า p · ช่วงความเชื่อมั่น · เงิน · เวลา ตัวเลขที่อ่านผิดเพราะพื้นหลังโปร่งแสงพาดผ่าน คือความเสียหายที่แก้ไม่ได้ในงานวิจัย

| ชั้น | ใช้กับ | API |
|---|---|---|
| **`Surface.floating`** (แก้ว) | เฉพาะสิ่งที่**ลอยเหนือเนื้อหาและปิดมันบางส่วน**: แถบเครื่องมือ · แถบสถานะ · popover · sheet | `.glassEffect(.regular, in:)` |
| **`Surface.solid`** (ทึบ) | เนื้อหาทุกชนิดที่ต้องอ่าน: ตาราง · ตัวเลข · ผลสถิติ · ข้อความอ้างอิง · บทสนทนา | `.background(.background.secondary, in:)` |

**กฎที่บังคับแล้ว 2 ข้อ**
1. ห้ามใส่ `.background(.ultraThinMaterial)` หรือ `.glassEffect(` ตรง ๆ ในไฟล์ view — ต้องผ่าน `.surface(_:)` เท่านั้น จะได้ grep ตอบได้ทั้งแอปว่า "อันนี้อยู่ชั้นไหน"
2. ไฟล์ไหนที่มี `Surface.floating` ห้ามมี `%.Nf` ในไฟล์เดียวกัน (heuristic ที่ตั้งใจให้หยาบ — ค่าของ false alarm คือคอมเมนต์หนึ่งบรรทัด ค่าของ miss คือ p-value ที่อ่านผิด)

> **ข้อควรรู้เรื่อง API** — บน SDK เครื่องนี้ `.glassEffect(_:in:)` **ไม่มีพารามิเตอร์ `isEnabled:`** (วัดแล้ว E.27) การเปิด/ปิดแก้วต้องแยกสาขาใน view ไม่ใช่ส่งเป็น argument

## 7. Agentic UX — สี่อย่างที่หน้าจอของระบบอัตโนมัติต้องมี

| ข้อกำหนด | มีแล้ว | ที่ต้องเติม |
|---|---|---|
| **Status Communication** — เห็นว่ากำลังเกิดอะไร | span stream · Live Monitor · แถบสถานะ 6 ช่อง · การ์ด "คิดอยู่ N วินาที" · มิเตอร์บริบท | **การ์ดต่อ step ที่กางดู raw output ได้** · **Command Tree** (เห็นว่าใครสั่งใคร) |
| **Visible Decision-Making** — เห็นว่าทำไมถึงเลือกทำแบบนี้ | hook chain บอกว่าอะไรถูกหยุดด้วยกฎข้อไหน · `routedWhy` บอกว่าทำไม tier นี้ | รวมเป็น `ReasonPopover` ตัวเดียว · เหตุผลของการเลือก *ทูล* ยังไม่แสดง |
| **Human-in-the-loop** — แทรกได้ตลอด | ApprovalBroker · pause/stop รายตัว · Plan-only · แก้ argument ก่อนอนุมัติ | **แทรกกลางทางระดับทีมย่อย** (หยุดทีมเดียวโดยไม่หยุดทั้งองค์กร) |
| **Confidence Indicators** — รู้ว่าเชื่อได้แค่ไหน | `ConflictDetector` มี confidence · `ToolProficiency` มีอัตราสำเร็จ · P20.4 ปิดเส้นทางอนุมัติอัตโนมัติเมื่อความมั่นใจต่ำ | `ConfidenceBadge` ตัวกลาง ให้ทุกจุดอนุมัติใช้รูปเดียวกัน |

### 7.1 กฎ 4 ข้อของ "ความคิดของโมเดล"

จาก U18 — สี่ข้อนี้เป็นหนึ่งชุด ตัดข้อใดข้อหนึ่งออกแล้วอีกสามข้อพัง

1. ความคิดแสดงในการ์ด **พับไว้** เหนือคำตอบ กดแล้วกาง (`คิดอยู่ N วินาที ›`)
2. **ความคิดไม่ใช่คำตอบ** — ห้าม `text +=` เด็ดขาด พอรวมกับ `text` มันจะถูกบันทึกเป็นคำตอบและถูกส่งเข้า structured-output parser (บังคับใน `check.sh`)
3. ไม่นับเป็นเทิร์นในบทสรุป และไม่ถูกบันทึกลงบทสนทนา — การ์ดบอกไว้ตรงนั้น
4. **ไม่มีบทพูดกับตัวเองภาษาอังกฤษบนหน้าแชท** — ตัดที่ `reasoning_content` ของ endpoint หรือที่ `</think>` ใน `VLLMExecutor` (P15.2b)

### 7.2 กฎของตัวเลือกโมเดลต่อเทิร์น

จาก E.37 — **ตัวเลือกคือ *ลำดับ* ไม่ใช่ *ตัวกรอง*** ห้าเงื่อนไข:

| กฎ | เหตุผล |
|---|---|
| เลื่อนขึ้นหน้าแถว **ไม่ตัดตัวอื่นทิ้ง** | endpoint ที่เลือกล่มกลางคำถาม = ตอบช้าลง ไม่ใช่ตอบไม่ได้ |
| เลือกแล้ว**ไม่ทำให้ tier ที่ทำงานนี้ไม่ได้ กลายเป็นทำได้** | ขอโมเดลที่เรียกทูลไม่ได้ ในเทิร์นที่ต้องเรียกทูล ⇒ ปฏิเสธโดยระบุชื่อ |
| เลือกแล้ว**ไม่ปลดล็อกการใช้เงิน** | ไม่งั้นตัวเลือกบนหน้าจอกลายเป็นวิธีจ่ายเงินโดยไม่มีการตัดสินใจจ่ายเงิน |
| ชื่อที่ไม่ตรงกับอะไรเลย = **ไม่เปลี่ยนอะไร ไม่ใช่ error** | endpoint ถูกลบได้ขณะที่บทสนทนายังจำชื่อมันอยู่ |
| **ตัวเลือกต้องโผล่ในบรรทัดเหตุผล** | ไม่งั้นคำอธิบาย "ทำไมคำตอบมาจากที่นี่" จะกลายเป็นคำอธิบายที่ผิด |

**ต่อหนึ่งบทสนทนา ไม่ใช่ค่าตั้งรวม** — ค่าที่อยู่ยาวกว่าคำถามจะแอบใช้โมเดลใหญ่กับทุกอย่างหลังจากนั้น

## 12. ข้อเสนอหน้าตา — และคำตอบของคำถามที่ค้าง

**สถานะ**: ผมเสนอ · **รอยืนยัน** — ไม่มีข้อไหนถูกลงมือก่อนได้รับคำตอบ
เจ้าของโปรเจกต์ตอบ Q4 ว่า *"ไม่มีตัวอย่างที่อยากได้ ให้เสนอเอง"* (2026-08-17) ⇒ ส่วนนี้คือข้อเสนอนั้น

---

### 12.1 ข้อเสนอหลัก — "หน้าจอที่พิสูจน์ตัวเองได้"

เข็มทิศที่บันทึกไว้เดิม (Claude Code · LM Studio · Bionic) ให้*โครง* มาแล้ว แต่ไม่ได้ตอบว่าแอปนี้ควรรู้สึกอย่างไร ข้อเสนอของผมคือประโยคเดียว:

> **ทุกตัวเลขบนหน้าจอนี้ ต้องกดเข้าไปดูได้ว่ามันมาจากไหน — และหน้าจอต้องไม่แสร้งทำเป็นรู้ในสิ่งที่มันไม่รู้**

ไม่ใช่เพราะสวย แต่เพราะนี่คือแอปที่คนเอาผลไปเขียนรายงานวิจัย และรอบตรวจในโปรเจกต์นี้พิสูจน์ซ้ำ ๆ ว่าความเสียหายที่แพงที่สุดคือ**ความเงียบ** ไม่ใช่ความผิดพลาดที่ดัง

**สามอย่างที่ทำให้ประโยคนั้นเป็นของจริง**

| # | สิ่งที่ต้องเห็นบนหน้าจอ | มีแล้วไหม |
|---|---|---|
| 1 | **ที่มาของทุกตัวเลข** — กดที่ค่าใดก็ได้แล้วเห็นว่าคำนวณจากอะไร | 🔶 แถบสถานะทำแล้ว · ตัวเลขในหน้าอื่นยังไม่ทำ |
| 2 | **สิ่งที่ระบบไม่รู้ ต้องอ่านต่างจากสิ่งที่มันรู้ว่าเป็นศูนย์** | 🔶 มีบางที่ · ยังไม่เป็นระบบ |
| 3 | **งานที่กำลังทำอยู่ ต้องบอกว่าเหลืออีกนานแค่ไหน** | ❌ ยังไม่มี — และวัดแล้วว่าจำเป็น: การตัดสินข้อขัดแย้งหนึ่งคู่ใช้เวลา **48–610 วินาที** ([E.45](verification/03-e31-e46.md)) |

**ข้อ 3 คือสิ่งที่ผมเสนอให้ทำก่อนเรื่องความสวยทั้งหมด** — หน้าจอที่นิ่งไป 10 นาทีโดยไม่บอกอะไร คือหน้าจอที่คนกดปิดทิ้ง และนั่นทำให้งานที่ถูกต้องกลายเป็นงานที่ไม่มีใครรอ

**Q6 — สิ่งที่ตัดสินไปแล้ว และสิ่งที่ตามมา**

*ระบบหลายภาษา* ไม่ใช่ *แปลทางเดียว* — ต่างกันตรงที่ภาษาถัดไปเป็นงานแปล ไม่ใช่งานเขียนโค้ด

### 12.4 สิ่งที่ผมยังไม่เสนอ และทำไม

- **ไม่เสนอให้รื้อ information architecture** — 5 พื้นที่ + sub-tab ทำงานได้ และ `IAInventory` บังคับว่าไม่มีหน้าจอไหนหายเงียบ · การรื้อตอนนี้จะเสียของที่พิสูจน์แล้วเพื่อแลกกับความรู้สึก
- **ไม่เสนอ animation หรือ transition ใด ๆ** — ยังไม่มีข้อมูลว่าที่ไหนคนหลงทาง
- **ไม่เสนอ onboarding** — ผู้ใช้คือคนเดียวที่สร้างมันเอง
