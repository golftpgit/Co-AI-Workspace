## เหตุผลและสิ่งที่วัดได้ — รายละเอียดต่อ task


### P20.1 — ตรวจ API จริงก่อนออกแบบ

**สถานะ**

✅ **วัดแล้ว ([E.27](../verification/02-e16-e30.md#e27-liquid-glass-บน-sdk-ของเครื่องนี้--และเครื่องมือตรวจที่ตอบผิด-2026-08-16))**

- `.glassEffect()`
- `.glassEffect(_:in:)`
- `GlassEffectContainer(spacing:)`
- `.regular.tint().interactive()`
- `.buttonStyle(.glass)` **มีจริงบน SDK 26.5**
- **แต่ `.glassEffect(_:in:isEnabled:)` ที่ ARCH §24.2 เขียนไว้ ไม่มีพารามิเตอร์ `isEnabled` จริง** — คอมไพล์ไม่ผ่าน เปิด/ปิดแก้วต้องแยกสาขาใน view (แก้ใน ARCHITECTURE แล้ว)
- **บทเรียนเรื่องเครื่องมือตรวจ**: grep ใน `.swiftinterface` เจอแค่ `GlassButtonStyle` และตอบว่าไม่มี `glassEffect` ทั้งที่มี — ไฟล์ interface ไม่ใช่รายการ API ต้องคอมไพล์โค้ดจริงถึงจะรู้
- แพ็กเกจตั้ง `.macOS(.v26)` อยู่แล้ว จึงไม่ต้องมี `@available` ห่อ

### P20.2 — Design tokens + component กลาง

**สถานะ**

- 🔶 **token + กฎทำแล้ว
- หนี้เก่ายังอยู่ในรายการ (2026-08-16)** — `DesignTokens.swift` ถือระยะ (`Space`) มุม (`Radius`) และ**ชั้น** (`Surface`) ที่เดียว
- **ไม่มีจานสีของตัวเอง** เพราะสีระบบตอบโหมดสว่าง/มืด/คอนทราสต์สูง/สีเน้นที่ผู้ใช้เลือกไว้แล้ว ส่วนจานสีที่เขียนเองตอบไม่ได้สักข้อแต่ดูเรียบร้อยในภาพหน้าจอเดียว
- **กฎใน check.sh พิสูจน์แล้วว่าแดง** เมื่อ view ใหม่เขียน `.padding(11)` เอง
- **รายการหนี้เก่าว่างเปล่าแล้ว (2026-08-16)** — ทุก view ในแอปเอาระยะและมุมจาก `DesignTokens` แล้ว
- ตัวแปรรายการยังอยู่ เพราะรูปของกฎคือสิ่งสำคัญ: จะใส่ไฟล์กลับต้องมีคนเขียนเหตุผลกำกับ และรายการว่างคือรูปที่แข็งที่สุดของ "มีแต่หดได้" (พิสูจน์แล้วว่ากฎยัง fail ได้ด้วย `.padding(11)` ในไฟล์จริง)
- **ค้าง**: ระยะสี่ค่าแทนค่าที่ตั้งกันเองห้าค่า กล่องบางใบจึงขยับ 2pt และ**ยังไม่มีใครไล่ดูทุกหน้าจอหลังย้าย**
- ชุด component กลาง (แถว/กล่อง/popover/sheet) ที่ตอนนี้มีแค่ `contentBox()` กับ `SectionHeading`

### P20.3 — ชั้นแก้วที่ทำหน้าที่

**สถานะ**

- 🔶 **บังคับเชิงโครงสร้างแล้ว
- การมองด้วยตาสองโหมดยังค้าง (2026-08-16, 2 กฎใน check.sh)** — **เจอของจริงระหว่างทำ**: แถบสถานะวางเงิน เวลา และจำนวน rework ไว้บน `.bar` ซึ่งโปร่งแสง และมันอยู่ก้นหน้าจอที่เลื่อนได้ ⇒ เนื้อหาที่เลื่อนผ่านวิ่งทะลุตัวเลข — ย้ายไป solid แล้ว ส่วนแถบแท็บยังเป็นแก้วถูกต้อง เพราะมันลอยเหนือเนื้อหาและถือ*ชื่อ* ไม่ใช่ตัวเลข
- **กฎสองข้อ พิสูจน์แล้วทั้งคู่**: พื้นหลังโปร่งแสงต้องประกาศผ่าน `Surface` เท่านั้น (ทำให้ "อันนี้อยู่บนแก้วไหม" ตอบได้ด้วย grep เดียว)
- ไฟล์ที่ format ตัวเลข (`%.Nf`) ห้ามใช้ `Surface.floating` — heuristic หยาบโดยตั้งใจ เพราะราคาของการเตือนเกินคือคอมเมนต์หนึ่งบรรทัด ส่วนราคาของการพลาดคือค่า p ที่อ่านผิด
- **ค้าง**: ไล่ดูด้วยตาทุกหน้าจอทั้งสองโหมด ซึ่งเป็นงานที่ต้องมีคนมอง

### P20.4 — Confidence indicators

**สถานะ**

✅ **ทำแล้ว (2026-08-16, 6 เทส)**

- `HookChain` อ่าน `ToolProficiency` ตอนตัดสิน และ**ต่ำกว่า 2 ใน 3 = ปิดทางอัตโนมัติ ไม่ว่าสวิตช์ autonomy จะตั้งไว้ยังไง**
- ตัวเลขไปอยู่ตรงหน้าคนที่กำลังจะกดอนุมัติ ซึ่งเป็นที่เดียวที่มันเปลี่ยนอะไรได้ — ตัวเลขข้างปุ่มที่ไม่มีวันโผล่คือของประดับ
- **"ยังใช้ไม่พอจะบอกอะไร" ต้องไม่เท่ากับ "แย่"** — ต่ำกว่า 5 ครั้งไม่ปิดทาง ไม่งั้นทูลใหม่ทุกตัวเกิดมาพร้อมการถาม และสิ่งแรกที่ทุกคนทำคือปิดประตูทิ้ง
- build ที่ไม่มีคลังสถิติก็ไม่เริ่มถามทุกเรื่อง
- **ไม่มีช่องทางถาม = ปฏิเสธ** ตามกฎเดิมของ chain ตั้งแต่ P1
- ต่อกับ span จริงผ่าน `ProficiencyCache` (แคช 1 นาที เพราะ gate อยู่บนทางของทุก call แต่คำตอบที่เก่ากว่านั้นคือการตัดสินด้วยสถิติสัปดาห์ที่แล้ว)

### P20.5 — เหตุผลของการเลือกทำ

**สถานะ**

✅ **ทำแล้ว (2026-08-16, 9 เทส · 2 กฎใน check.sh)**

- **คำอธิบายคือการตัดสินใจเอง ไม่ใช่เรื่องเล่าเกี่ยวกับมัน**: `RoutingChoice` ออกมาจาก `choose(from:for:policy:)` ซึ่งเป็น pass เดียวกับที่คัดจริง — ตัวกรองข้อไหนตัด tier ไหนออก ข้อนั้นเขียนเหตุผลเอง ⇒ คำอธิบายจะเพี้ยนจากพฤติกรรมไม่ได้ถ้าตัวกรองไม่เปลี่ยน
- เทสยึดมาตรฐานเดียวที่มีความหมาย: **เปลี่ยน policy แล้วประโยคต้องเปลี่ยน** และ `order` ที่โชว์คืออาร์เรย์เดียวกับที่จะไล่จริง
- เหตุผลที่รู้ได้ตอนรันเท่านั้น (tier ที่ลองแล้วล่ม) ถูกเติมเข้าไปทีหลัง ไม่งั้นหน้าจอจะบอกว่า endpoint มาก่อน ทั้งที่คำตอบมาจากที่อื่น
- ฝั่งทูลใช้ `RiskAssessment.reasons` ของ scorer ที่ตัดสินจริง — และ outcome ที่ไม่มีอะไรจะบอกก็ไม่บอก เพราะ "ปกติดี" ทุกใบคือวิธีสอนคนให้เลิกอ่านบรรทัดที่สำคัญ
- **กฎ**: ตัวกรอง capability ใน `ModelRouter` ต้องมีชุดเดียว (สองชุด = มีคำอธิบายที่แอบเป็นคนละทางกับการตัดสิน) และเส้นทางส่ง `why` ถึง event ต้องยังอยู่

### P20.6 — Adaptive ตาม project type เท่านั้น

**สถานะ**

✅ **ทำแล้ว (2026-08-16, 6 เทส · 3 กฎใน check.sh)**

- `PanelEmphasis` รับ input เดียวคือ `ProjectKind` ที่ผู้ใช้เลือกเองตอนสร้างโครงการ
- **การปฏิเสธคือเนื้อของงานนี้**: span บันทึกทุกหน้าจอที่ใครเปิดอยู่แล้ว การเรียงแผงที่ใช้บ่อยขึ้นมาก่อนจึงห่างแค่ import เดียว — และนั่นคือวิธีที่หน้าจอเลิกเป็นสิ่งที่เรียนรู้ได้ คนหาของด้วยตำแหน่งก่อนจะหาด้วยการอ่านเสมอ
- **เน้น ≠ ย้าย**: ลำดับแผงเท่ากันทุกชนิดโครงการ ชนิดโครงการตัดสินแค่ว่าอันไหนติดจุด และเปิดมาที่อันไหน
- **"ที่ที่คุณค้างไว้" ชนะ "ที่ที่ชนิดโครงการแนะนำ"** — emphasis ใช้เฉพาะแท็บที่ยังไม่เคยเข้า
- `blank` ไม่มีความเห็น ไม่เดาจากชื่อ
- **กฎ**: ไฟล์ emphasis ห้ามแตะข้อมูลพฤติกรรม (ตัดคอมเมนต์ก่อนตรวจ เพราะไฟล์นี้เถียงเรื่อง usage-based adaptation ยาว)
- รายการแท็บห้ามสร้างจาก emphasis
- ชื่อแผงทุกอันต้องมีอยู่จริงในแอป
