## เหตุผลและสิ่งที่วัดได้ — รายละเอียดต่อ task


### P7.1 — Telegram channel

**สถานะ**

- 🔶 **โค้ดครบและขับจบทั้งเส้นทางในเทส 13 ตัว
- ยังไม่ได้ยิงกับบอทจริง** — long polling ตาม §8.1 (เป็น request ขาออก จึงไม่ต้องเปิดพอร์ต ไม่ต้องมี tunnel และไม่พังเมื่อย้ายเครือข่าย)
- transport เป็น protocol ที่ฉีดเข้าไปได้ เทสจึงป้อน JSON แบบเดียวกับที่ Telegram ส่งจริงแล้วตรวจว่า channel ทำอะไรกับมัน — บทเรียนจาก P3.3: โค้ดที่รันได้เฉพาะกับ API ของคนอื่นจะถูกรันครั้งเดียวด้วยมือแล้วไม่ถูกรันอีกเลย
- **การ์ดอนุมัติแสดงคำสั่งคำต่อคำ** ไม่ใช่สรุป (§5.4 — อนุมัติจากมือถือก็ยังคือการอนุมัติ)
- ตอบแล้ว**แก้ข้อความเดิมทิ้งปุ่ม** เพราะปุ่มที่ยังกดได้แต่ไม่ตัดสินอะไรคือวิธีที่คนเชื่อว่าตัวเองอนุมัติสิ่งที่ไม่ได้อนุมัติ
- **โทเคนอยู่ใน URL path ของทุก request** ที่ Telegram รับ ทุกอย่างที่ log จึงผ่าน `redacted` ก่อน
- คำตอบวิ่งกลับไปที่ห้องที่ถาม ไม่ใช่กระจายทุกห้อง
- `ok:false` มาพร้อม HTTP 200 จึงถือเป็น error ไม่ใช่คำตอบว่าง
- loop ไม่ตายเพราะเน็ตล่มหนึ่งนาที
- **เจ้าของมีโทเคนแล้วและจะกรอกเอง (2026-08-16)** — ที่ ระบบ → ช่องทาง → เพิ่มบอท: ตั้งชื่อที่เก็บ (เช่น `TELEGRAM_BOT_TOKEN`) พิมพ์ค่าลง `SecretField` แล้วกดบันทึกลง Keychain
- แอปไม่เคยเห็นค่า ไม่มีปุ่มแสดง และไม่มี API ไหนอ่านกลับ
- ต้องใส่ chat id ที่อนุญาตด้วย (ว่าง = ไม่รับใคร ไม่ใช่รับทุกคน)
- มีผลรอบถัดไปที่เปิดแอป
- **ค้าง**: การยิงกับ Bot API จริงเป็นของเจ้าของเครื่อง
- ✅ **หน้าจอเพิ่มบัญชีทำแล้ว (2026-08-15)** ที่ ระบบ → ช่องทาง — ก่อนหน้านี้ตั้งค่าได้ทางเดียวคือแก้ไฟล์ `channels.json` + ตัวแปรสภาพแวดล้อม
- ปุ่มมีแค่ อนุมัติ/ไม่อนุมัติ ไม่มี "แก้อาร์กิวเมนต์ก่อน" (§2.6) เพราะการแก้คำสั่งเชลล์บนคีย์บอร์ดมือถือคือวิธีที่การอนุมัติกลายเป็นการพิมพ์ผิด

### P7.2 — Discord + LINE

**สถานะ**

- 🔶 **ผ่าน Done-when ในเชิงโครงสร้าง (13 เทส)
- ยังไม่ได้ยิงกับแพลตฟอร์มจริง** — ทั้งสามตัวเป็น `RunnableChannel` ตัวเดียวกัน ใช้ `ChannelAccount`/allow-list/`SecretStore` ชุดเดียวกัน และ `Engine` สร้างทั้งสามด้วย `switch` เดียว ไม่มี special case ที่ไหน
- **Discord**: Gateway WS ตาม §8.1 (Hello op10 → Identify op2 → Heartbeat op1 → MESSAGE_CREATE) ฉีด socket ได้ เทสจึงขับ handshake จริงโดยไม่ต้องมีโทเคน
- **ขอ intent `MESSAGE_CONTENT` (1<<15)** ไม่งั้น Discord ส่งข้อความมาโดยเนื้อความถูกตัดออก ทุกอย่างจะดูเหมือน prompt ว่าง
- **กรองข้อความของตัวเอง** — ถ้าไม่กรอง คำตอบแรกจะกลายเป็น prompt ถัดไปแล้วบอทคุยกับตัวเองไม่จบ ซึ่งบนระบบที่รันเชลล์ได้ไม่ใช่บั๊กที่ตลก
- heartbeat หยุดตามเมื่อ socket ตาย
- **LINE**: เป็น channel เดียวที่ต้อง**ฟัง** (ไม่มี polling API) จึงเปิด `NWListener` เอง
- **ลายเซ็นคือของจริงที่ต้องมี** — ใครก็ตามที่รู้ URL ยิงเข้ามาได้ ทุก request ต้องมี `x-line-signature` (HMAC-SHA256 ของ**ไบต์ดิบ** ใต้ channel secret) **เทียบแบบ constant-time** เพราะการคืนค่าเร็วบอกคนเดาว่าเดาถูกไปกี่ตัว
- **HMAC ต้องคิดจากไบต์ที่ LINE ส่งมาจริงๆ** — เอา JSON ที่ parse แล้วมา encode ใหม่จะได้ digest คนละตัวสำหรับข้อความเดียวกัน (เทสมีเคสนี้ตรงๆ)
- เทสยิงของปลอมเข้าไปแล้วยืนยันว่าได้ 401 และ**ไม่มีอะไรถึง core**
- allow-list ทำงาน**หลัง**ลายเซ็นผ่าน — secret ไม่ใช่สิ่งที่ตัดสินว่าใครคุยได้
- ตอบด้วย **push API ไม่ใช่ reply token** ตาม §8.1 (token อายุราวหนึ่งนาที สั้นกว่าเทิร์นที่มี tool call กับ approval)
- **สถานะจากเจ้าของเครื่อง (2026-08-16)**: **LINE — ปิดเคสว่าไม่ได้ทดสอบ** เจ้าของแอปไม่มีบัญชี LINE Official Account และการทดสอบต้องไปสมัครก่อน จึงไม่นับเป็นของค้างที่รอโค้ด แต่เป็นเรื่องที่ยังไม่ได้ตรวจและ**ห้ามรายงานว่าใช้ได้**
- **Discord — เจ้าของมีโทเคนแล้วและจะกรอกเอง** ที่ ระบบ → ช่องทาง (แอปไม่เคยเห็นค่า มันลง Keychain ตรงจากช่องกรอก)
- **ค้าง (โค้ด)**
- **Discord ต่อกลับเองและ RESUME แล้ว (2026-08-16, 3 เทส)** — เดิม**ไม่มีการต่อกลับเลย**: read loop จบพร้อมกับ socket แล้วบอทก็เงียบจนกว่าจะเปิดแอปใหม่ ⇒ ฝาแล็ปท็อปหรือเราเตอร์ = บอทที่ "เลิกตอบ" ในสายตาคนอีกฝั่ง
- ต่อกลับพร้อม backoff ทวีคูณจนถึง 60 วิ เพราะ gateway ที่กำลังปฏิเสธเราคือ gateway ที่การยิงรัวทำให้โกรธกว่าเดิม (Discord จำกัดอัตรา identify และโทษของการรัวคือแบนนานกว่าตัวเหตุขัดข้อง)
- **ต่อกลับอย่างเดียวไม่พอ**: identify คือการเริ่ม session ใหม่ ซึ่ง**ทิ้งข้อความที่เข้ามาระหว่างหลุด** — มีแต่ resume (op 6 พร้อม `session_id` + `seq`) ที่ทำให้ gateway เล่นย้อนให้
- resume ไปที่ `resume_gateway_url` ของ session ไม่ใช่ประตูหน้า
- op 9 (session ใช้ไม่ได้) ลืม session ทิ้ง ไม่งั้นจะ resume เข้าหา session ที่ Discord ทิ้งไปแล้ววนไม่จบ
- LINE listener ยังไม่มี TLS — ของจริงต้องมี reverse proxy หรือ tunnel หน้า

### P7.3 — Multi-account + allow-list

**สถานะ**

✅ **ผ่าน Done-when**

- หลายบัญชีต่อแพลตฟอร์ม แต่ละบัญชีมี allow-list ของตัวเอง (7 เทส)
- ข้อความจาก chat นอกรายการ**ไม่ถึง core และไม่ถูกตอบกลับด้วย** — การตอบคือการยืนยันว่าบอทมีอยู่จริงให้คนที่กำลังลองของ
- **รายการว่าง = ไม่รับจากใครเลย ไม่ใช่รับทุกคน** ชื่อบอทเป็นสาธารณะ โทเคนคือความลับเดียว ถ้าค่าเริ่มต้นเปิดกว้าง โทเคนที่หลุดหนึ่งครั้งคือคนแปลกหน้าที่มีเชลล์
- **โทเคนไม่ได้อยู่ในไฟล์** เก็บแค่ชื่อตัวแปรสภาพแวดล้อม (รูปแบบเดียวกับ endpoint §9.3 และ connector §12.2) เทสเปิดไฟล์อ่านแล้วยืนยัน

### P7.4 — ตรวจ invariant ข้าม channel

**สถานะ**

✅ **บังคับด้วยกราฟของโมดูล ไม่ใช่ด้วยเทส**

- target `Channels` ขึ้นกับ AgentKit/Config/Observability เท่านั้น **ไม่มี ToolBelt ไม่มี CoreEngine** ดังนั้น `ToolGateway` และ `AgentTool` ไม่อยู่ในสายตาของ channel เลย จะเรียกก็เรียกไม่ได้ตั้งแต่คอมไพล์
- `check.sh` ตรวจสองฝั่ง: `import` ในไฟล์ของ M4 และบรรทัด dependency ใน `Package.swift` ที่จะเปิดทางให้
- สิ่งที่ channel ทำได้กับข้อความขาเข้ามีอย่างเดียวคือส่งต่อให้ `InboundHandling` และการอนุมัติส่งให้ `ApprovalAnswering` (ทั้งคู่ประกาศไว้ใน AgentKit)
- ตัวเชื่อมจริงคือ `ChannelRouter` ในแอป ซึ่งเรียก **`AgentTurnRunner` ตัวเดียวกับที่หน้าแชทเรียก** ไม่ใช่เส้นทางที่คล้ายกัน — §8.2 จึงเป็นจริงโดยโครงสร้าง

### P7.5 — Notifier + App Intents

**สถานะ**

🔶 **โค้ดครบและพิสูจน์ถึงชั้นที่พิสูจน์ได้โดยไม่ต้องมีคนพูดกับ Siri (15 เทส)**

- `AppIntentsChannel` แปลง intent เป็น `IncomingMessage` ตัวเดียวกับที่ Telegram ส่ง แล้วเข้าทาง `ChannelRouter` เดิม §8.2 จึงยังจริงโดยโครงสร้าง (โมดูลนี้ยังมองไม่เห็น gateway)
- **รูปร่างต่างจาก channel อื่นตรงที่มีคนรออยู่ปลายสาย** — Shortcuts ต้องได้ค่ากลับก่อน timeout ของมันเอง จึงมี `ask()` ที่จับคู่คำตอบผ่าน conversation ที่ router bind มา และมีเทสว่าถามพร้อมกันสองคำถามไม่สลับคำตอบกัน
- **approval ไม่เกิดที่นี่** ตาม §8.1 (Siri ไม่มีที่ให้ดู diff) — แต่สิ่งที่ผู้เรียกต้องไม่ได้คือความเงียบแล้วตามด้วย "หมดเวลา" จึงแยก `needsApproval` ออกจาก `timedOut` และบอกว่าให้ไปอนุมัติในแอป
- **Notifier แยกส่วนตัดสินใจออกจาก `UserNotifications`** เพราะ `UNUserNotificationCenter.current()` **trap** เมื่อโปรเซสไม่มี bundle — โปรเซส `swift test` ไม่มี ตัวตัดสินใจจึงอยู่ใน M4 ที่เทสได้ ส่วนการยิงจริงอยู่ในแอป
- กฎของ Notifier คือกฎของการ**ไม่**พูด: ตอบที่มาถึงตอนคนมองจออยู่ไม่ใช่ข่าว, progress ไม่เคยคุ้ม, **แต่ approval ประกาศเสมอ** (เทิร์นค้างรออยู่) และถูก**ถอนเมื่อมีคนตอบจากที่อื่น** ตาม §5.4
- **`ChannelPlatform.isLocal`** เป็นข้อยกเว้นเดียวจาก token + allow-list พร้อมเหตุผลเขียนไว้ (intent ไม่มีผู้ส่งระยะไกลให้ list) และมีเทสวนทุก platform ว่าอันอื่นยังบังคับเหมือนเดิม
- **`Metadata.appintents` ถูกสร้างจริงตอน `build-app.sh`** — Siri/Shortcuts อ่าน bundle นี้ ไม่ได้อ่าน binary แอปที่ไม่มีมันคือแอปที่ไม่มี intent เลยในสายตาระบบ ต่อให้เขียน `AppIntent` ไว้กี่ตัว (ความล้มเหลวทรงเดียวกับ D6) Xcode ใส่ flag ให้เอง SwiftPM ไม่ใส่ จึงต้องขอ `-emit-const-values` ใน Package.swift แล้วให้สคริปต์รัน `appintentsmetadataprocessor` และ**ตรวจว่ามี intent จริงในไฟล์ที่ออกมา** ไม่ใช่แค่ exit 0 — ตอนนี้ได้ 3 intent พร้อมวลีไทย/อังกฤษ
- **ค้าง**: ยังไม่มีใครพูดกับ Siri จริง — เทสพิสูจน์ถึง channel และ metadata แต่การที่ Shortcuts.app แสดง action จริงต้องมีคนเปิดดู
- ปุ่มบน notification (อนุมัติ/ปฏิเสธจาก banner) ยังไม่ได้ทำ — ตอนนี้ banner พาไปที่แอป

### P7.6 — DocGen engine

**สถานะ**

✅ **ผ่าน Done-when

- เปิดได้จริงทั้งสองฟอร์แมต** (`.pptx` เปิดใน PowerPoint บนเครื่องจริงแล้ว ไม่ขึ้น repair — 2026-08-12) — เทสเขียนไฟล์จริงแล้วส่งให้ `/usr/bin/unzip -t` (ตรวจทุก entry ทุก CRC) และ `/usr/bin/textutil` (ตัวอ่าน OOXML ที่ Apple ใส่มากับเครื่อง เป็นตัวเดียวกับที่ TextEdit ใช้) แล้วข้อความไทย, marker ของ citation, บรรณานุกรม และส่วนข้อจำกัดกลับออกมาครบ — เป็นหลักฐานที่ดีที่สุดเท่าที่ได้โดยไม่ต้องมีคนดับเบิลคลิก
- **zip เขียนเอง (method 0 stored)** ไม่ shell out ไป `zip` เพราะการวางไฟล์ลง temp dir แล้วเรียกโปรเซสเป็นสิ่งที่ไม่ควรอยู่ในเส้นทางของคำว่า "บันทึกเอกสาร" โดยเฉพาะในแอปที่ sandbox
- CRC-32 เทียบกับ test vector มาตรฐาน (`123456789` → `0xCBF43926`)
- **แยกการ render ออกจากการจัดรูปแบบ**: `DocumentBuilder` ทำเป็นบรรทัดที่มี style ส่วน writer แปลงเป็น XML ของ Word หรือ Keynote — ครึ่งที่น่าสนใจจึงเทสได้โดยไม่ต้องแตะ zip และฟอร์แมตที่สามคือ writer ใหม่ ไม่ใช่กฎชุดที่สอง
- **`w:cs` ต้องตั้งคู่กับ `w:ascii`** ไม่งั้น Word เลือก fallback ให้ภาษาไทยเองแล้วสระลอย
- **แหล่งที่ไม่มีผู้เขียน/ปี หยุดการสร้างเอกสาร** ตาม §14.1 ไม่ใช่เตือนข้างๆ เอกสารที่เสร็จแล้ว (ข้ามได้ต้องส่งพารามิเตอร์ ไม่ใช่ค่าเริ่มต้นที่ลืมได้)
- ต่อเข้าแอปแล้วที่ปุ่ม "ส่งออก .docx" บนหน้าแผนวิเคราะห์ — pre-registration คือสิ่งที่ต้องส่งให้คนอื่น
- **`.pptx` เคยขึ้น repair แล้วแก้ไปแล้ว**: แพ็กเกจแรกมีแต่ `presentation.xml` กับสไลด์ ไม่มี slideMaster/slideLayout/theme ทั้งที่สไลด์จบด้วย `masterClrMapping` ที่ต้องมี master ให้ resolve — PowerPoint เสนอ repair แล้ว**สร้าง master ให้เอง** เนื้อหาจึงกลับมาครบ ทำให้อาการดูเหมือนเรื่องความสวยงาม ทั้งที่แพ็กเกจผิดจริง
- เทสเดิมมองไม่เห็นเพราะ `unzip -t` กับ `xmllint` ผ่านได้สบายบนแพ็กเกจที่ไม่สมบูรณ์ ตอนนี้จึงมีเทสที่ตรวจ **กราฟของแพ็กเกจ** แทน: ทุก relationship ชี้ไป part ที่มีจริง, ทุก part มี content type, master เข้าถึงได้จาก presentation, ทุกสไลด์มี layout พอดีหนึ่งอัน (เทสนี้ fail กับโค้ดเดิม 9 จุด)
- **ค้าง**: ยังไม่มี template (P7.9) — ตอนนี้ layout มาจากโค้ด
- ไม่มีรูป/ตารางในเอกสาร
- สไลด์ยังวางกล่องข้อความด้วยพิกัดของตัวเอง ไม่ได้ใช้ placeholder จาก layout

### P7.7 — Citation engine

**สถานะ**

✅ **บังคับด้วย type**

- `CitedText` มี initialiser เดียวและมันรับ `Provenance` ประโยคที่ไม่มีที่มาจึงไม่ใช่สิ่งที่ใครลืมใส่ แต่เป็นสิ่งที่เขียนไม่ได้ตั้งแต่แรก
- 3 style ตาม §14.1: APA อ้างด้วยชื่อ+ปี, IEEE/Vancouver อ้างด้วยเลขตามลำดับที่ปรากฏ — **เลขจึงเป็นสมบัติของเอกสาร ไม่ใช่ของประโยค** การนับจึงอยู่ที่ `Bibliography`
- **บรรณานุกรมนับ "งาน" ไม่ใช่ "ประโยค"** อ้างเปเปอร์เดียวสามครั้งได้เลขเดียว
- แหล่งเว็บพก URL + วันที่เข้าถึงเสมอ (§11.3 — URL เดิมเดือนหน้าพูดอีกอย่าง)
- **ไม่มีปีก็เขียน `n.d.` ไม่เดา** และ `CitationAudit` ยกธงก่อน generate ตามที่ §14.1 สั่ง
- **corroboration ตามชั้นของแหล่ง**: T1–T2 สองแหล่งขึ้นไป = เขียนได้เต็มปาก
- แหล่งเดียวไม่ใช่การยืนยันข้ามแหล่ง
- **T5 สิบแหล่งไม่เท่ากับ T1 สองแหล่ง** ต้องมี T1–T3 ค้ำอย่างน้อยหนึ่ง
- 18 เทส

### P7.8 — Limitations อัตโนมัติ

**สถานะ**

✅ **ผ่าน Done-when

- และเจอกับดักที่ทำให้มันเกือบเป็นศูนย์เสมอ**: พอแผนถูกอนุมัติ `agent_suggested` ทุกตัว**กลายเป็น `human_confirmed` ไปแล้ว** (นั่นคือความหมายของการอนุมัติตาม §12.4) ตัวสร้างที่อ่าน `origin` จึงจะเขียนส่วน Limitations ว่างเปล่าให้กับแผนที่ต้องการมันที่สุดพอดี → เพิ่ม `wasAgentSuggested` ที่ตั้งครั้งเดียวและไม่เคยถูกล้าง
- ทุกบรรทัดในส่วนนี้เป็นการพูดซ้ำสิ่งที่ระบบบันทึกไว้แล้ว ไม่มีอะไรถูกแต่งขึ้น: ข้อสมมติจาก Analysis Plan (§12.4)
- ข้อความที่เคยขัดกันจาก Conflict Ledger (§11.6 ซึ่งเก็บทั้งสองฝั่งคำต่อคำไว้เพื่อการนี้)
- ความหนาแน่นของหลักฐานจากกฎ tier
- ข้อสมมติทางสถิติที่ไม่ผ่านจาก §12.3
- **ข้อขัดแย้งที่ยังไม่ตัดสินไม่ถูกรายงานว่าตัดสินแล้ว** และ run ที่ไม่มีข้อจำกัด**พูดออกมาว่าไม่มี** ซึ่งเป็นคนละเรื่องกับส่วนที่ไม่มีใครเขียน
- เห็นได้จริงบนหน้าแผนวิเคราะห์ ("ข้อจำกัดที่จะขึ้นในเอกสารอัตโนมัติ") — ข้อสมมติอ่านต่างออกไปเมื่อเห็นประโยคที่มันจะกลายเป็น

### P7.9 — Template editor + auto-parse

**สถานะ**

✅ **ผ่าน Done-when (11 เทส)**

- เทสหลักวิ่งครบวง: `.docx` เข้า → ได้แม่แบบ → เท draft **คนละเรื่อง คนละลำดับ** ลงไป → เขียนออกเป็น `.docx` → อ่านหัวข้อกลับด้วย `textutil` ว่ามาตามลำดับของแม่แบบจริง
- **ต้องเขียนตัวอ่านตัวที่สอง** เพราะ `DocumentReader` (P2.3) ดึงแต่ *ข้อความ* ซึ่งถูกแล้วสำหรับคลังความรู้ แต่แม่แบบต้องการสิ่งที่ตัวดึงข้อความมีหน้าที่ทิ้ง — ย่อหน้าไหนเป็นหัวข้อ
- **หัวข้อถูกเขียนสามแบบ เพราะเอกสารมาจากคน**: `w:pStyle`, `w:outlineLvl`, และ**ไม่มีอะไรเลย — บรรทัดสั้นที่เป็นตัวหนาล้วน** ซึ่งเป็นแบบที่พบมากที่สุดในไฟล์ที่คนพิมพ์เอง กฎที่สามใช้ต่อเมื่อสองข้อแรกไม่เจออะไรเลย (เอกสารที่มีสไตล์จริงต้องไม่โดนเลื่อนประโยคเน้นขึ้นเป็นหัวข้อ — มีเทสคุมทั้งสองทาง)
- **เทสกับไฟล์ที่ไม่ใช่ของเรา**: `textutil -convert docx` เขียน Word file จริงจาก HTML แล้วผลคือ**ไม่มี `w:pStyle` และไม่มี `outlineLvl` เลยสักที่** หัวข้อเป็นแค่ run ตัวหนา — ตัวอ่านที่รู้จักแต่มาร์กอัปสวย ๆ ของ Word จะอ่านไฟล์ที่ macOS เขียนเองไม่ออก
- เจอระหว่างทาง: `OfficeWriter` วาด bullet เป็นอักขระ "• " เพื่อเลี่ยง `numbering.xml` (การตัดสินใจของ P7.6) แปลว่าตัวอ่านที่รู้จักแต่ `w:numPr` **อ่านเอกสารที่แอปนี้เขียนเองไม่ออก** จึงต้องรู้จัก bullet ที่วาดด้วยอักขระด้วย
- **แม่แบบคือรูปทรง ไม่ใช่ข้อความให้ใช้ซ้ำ** — ประโยคในไฟล์ตัวอย่างคืองานเขียนจริงของคนที่ให้ไฟล์มา เก็บไว้เป็น `guidance` ให้คนกรอกอ่าน และมีเทสว่าไม่เคยหลุดเข้าเอกสารใหม่
- **เนื้อหาที่แม่แบบไม่มีที่ให้ ไม่ถูกทิ้ง** — ต่อท้ายไว้เสมอ เพราะแม่แบบคือรูปทรงที่คนเลือก ไม่ใช่ใบอนุญาตลบงานส่วนที่ไม่พอดี และการลบเงียบ ๆ ตรงนี้จะถูกพบตอนอยู่ในต้นฉบับที่ส่งไปแล้ว
- หัวข้อที่ขาดถูกรายงานและใส่บรรทัด "ยังไม่มีเนื้อหา" ไว้ให้เห็น
- ต่อเข้าแอปแล้วที่หน้าแผนวิเคราะห์: ปุ่มเพิ่มแม่แบบจากไฟล์ + ตัวเลือกข้างปุ่มส่งออก และตอนส่งออกจะบอกว่าหัวข้อไหนยังว่าง
- **แก้แม่แบบด้วยมือได้แล้ว (2026-08-16, 6 เทส)** — เปลี่ยนชื่อหัวข้อ
- สลับลำดับ
- บอกว่าหัวข้อไหนไม่จำเป็น ทั้งหมดจากในแอป (เดิมทางเดียวคืออัปโหลดไฟล์ใหม่ แม่แบบที่มีหัวข้อผิดลำดับหนึ่งอันจึงเป็นแม่แบบที่ต้องทนใช้)
- **กฎอยู่บน type ไม่ใช่บนหน้าจอ**: หัวข้อว่างและหัวข้อซ้ำถูกปฏิเสธ เพราะหัวข้อที่ไม่มีชื่อหาไม่เจอในเอกสารที่เสร็จแล้ว (ด่าน "หัวข้อไหนยังว่าง" จะปล่อยผ่านตลอดไป) และชื่อซ้ำทำให้คำเตือนบอกไม่ได้ว่าอันไหน
- **`guidance` ติดไปกับหัวข้อเสมอ** เพราะมันคือบันทึกเดียวว่าเอกสารที่ถูกอนุมัติเขียนอะไรไว้ใต้หัวข้อนั้น และไฟล์ตัวอย่างอาจไม่อยู่แล้ว
- เขียนกลับที่ตำแหน่งเดิมในรายการ ไม่ต่อท้าย (แม่แบบที่กระโดดลงล่างทุกครั้งที่แก้ชื่อ คือรายการที่จำที่ไม่ได้)
- `expectsBullets` เก็บไว้แล้วแต่ยังไม่มีใครใช้บังคับรูปแบบ
