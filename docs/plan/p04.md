## เหตุผลและสิ่งที่วัดได้ — รายละเอียดต่อ task


### P4.1 — Specialist actors

**สถานะ**

✅ 4 role เป็น `actor` แยก คืนได้แค่ `Deliverable`

- **compiler การันตี ไม่ใช่วินัย**
- **หลักฐานมาจากสิ่งที่รันจริงเท่านั้น**: คำสั่งที่ exit code ≠ 0 ให้ evidence ที่ `passed == false` แม้โมเดลจะสรุปว่า "ทุกอย่างผ่านแล้ว" (external-truth-gated done ตาม §2.5)
- **แต่ละ role ใช้ได้เฉพาะทูลของตัวเอง** — Writer ขอ `run_shell` แล้วทูลไม่ถูกเรียกเลย
- ทุกการเรียกทูลยังผ่าน hook chain เดิม ไม่มีทางลัด
- artifacts เป็น pointer ไม่ใช่เนื้อหา
- โมเดลล่ม = โยน error ไม่ใช่คืน deliverable ว่าง (ไม่งั้นจะถูกตรวจว่าเป็นงานที่ทำแล้วไม่ได้ผล แทนที่จะเป็นงานที่ไม่ได้ทำ)
- 6 เทส

### P4.2 — Team Orchestrator

**สถานะ**

✅ **ผ่าน Done-when ทั้งสองข้อ (ตรวจซ้ำ 2026-08-17)**

- ข้อความท้ายแถวเรื่อง "เปลี่ยน scope กลางรันไม่ได้" เป็น**ข้อจำกัดที่ตั้งใจ พร้อมเหตุผล** ไม่ใช่ของค้าง
- `TeamOrchestrator` ครบวง plan → assign → review → rework → escalate + cap fan-out + ledger ต่อ assignment
- role นอก enum เป็นไปไม่ได้ตั้งแต่ type
- แผนที่ไม่มี acceptance criteria ถูกทิ้งตอน parse
- ✅ **ledger ลง SurrealDB แล้ว** (ตาราง `task`, 5 เทสกับ DB จริง) เขียนทุกครั้งที่สถานะเปลี่ยน ไม่ใช่ตอนจบ — เพราะ run ที่ถูกขัดจังหวะคือตอนที่คนอยากอ่าน ledger ที่สุด
- `unfinished(scope:)` ตอบว่ามีงานไหนยังต้องการคน
- ✅ **ปล่อย span แล้ว (2026-08-15)** — 1 span ต่อ assignment + 1 ต่อรอบ พร้อม `deliverable_kind` และใบงาน (รายละเอียดอยู่ที่ P10.15)
- `scope` เปลี่ยนตามโปรเจกต์ที่เปิดอยู่ได้แล้ว แต่ **เปลี่ยนกลางรันไม่ได้** เพราะครึ่งหนึ่งของรันลงบัญชีโปรเจกต์หนึ่ง อีกครึ่งลงอีกโปรเจกต์ คือ ledger ที่อ่านไม่ได้ทั้งสองฝั่ง

### P4.3 — QA agent + Definition of Done

**สถานะ**

- ✅ `QAReviewer` ตรวจจาก evidence ล้วน ไม่เคยถามโมเดลว่า "ดีไหม"
- **เทสยิงเคสตรงตาม Done-when**: deliverable ที่สรุปว่า "เรียบร้อย ทุกอย่างผ่านแล้ว" แต่ไม่มี exit code 0 → ตีกลับทั้ง 3 รอบแล้ว escalate
- Researcher ต้องมี ≥2 citation ที่อ่านจริง (มี URL)

**สถานะ**

- ✅ หยุดที่ retry cap พอดี (เทสให้ script 4 รอบ แต่ถูกเรียกแค่ 3)
- **rework ส่งเหตุผลของ QA กลับไปในโจทย์รอบถัดไป** — ส่งโจทย์เดิมซ้ำคือวิธีที่ loop วนซ้ำตัวเอง
- specialist ที่ throw ถูกนับเป็นความพยายามหนึ่งครั้ง ไม่ใช่ผลตรวจ

### P4.6 — Manual mode ทุกชั้น

**สถานะ**

🔶 **สองแถวของ §2.6 ที่ทำได้ตอนนี้ เสร็จและกดจริงแล้ว**

- **ไม่มีทางลัดจากเป้าหมายไปสู่การลงมือทำอีกแล้ว**: ทั้งสองเส้นทางจบที่แผนที่แก้ได้ และไม่มีอะไรเริ่มจนกว่าจะกดอนุมัติ
- **แถว "ข้ามหัวหน้าทีม"**: เลือก role จาก dropdown แล้วเขียนงานเอง — dropdown แบบ v1 ยังอยู่ตามที่ §2.6 กำหนด และไม่ใช่ทางหนีตอนวางแผนพลาด
- **แถว "แก้ระหว่างทาง"**: `propose()` แยกออกจาก `run()` แผนที่ได้มาแก้ได้ทุกช่อง (role · งาน · ผลงานที่ต้องส่ง · เกณฑ์ตรวจรับ) เพิ่ม/ลบงานได้
- **ข้อห้าม §2.4 ขึ้นในตัวแก้ขณะที่ยังแก้ได้** พร้อมเหตุผลเต็ม ("แผนแตกงาน Engineer เป็น 2 ก้อน…") และปิดปุ่มอนุมัติ — เดิมกฎนี้มาถึงผู้ใช้เป็น error หลังกดเริ่มไปแล้ว
- เปลี่ยน role หนึ่งงาน → คำเตือนหาย ปุ่มเปิด
- งานที่ไม่มีเกณฑ์ตรวจรับเริ่มไม่ได้ (§2.5 บังคับที่ UI ไม่ใช่แค่ที่ type)
- **ข้อความเดิมที่ว่าแถว "ข้าม agent ทั้งหมด" ยังไม่มีเครื่องมือให้ข้ามไปหา **ล้าสมัยแล้ว (ตรวจซ้ำ 2026-08-17)** — Notebook (P6.4), DB Explorer (P6.2/P6.3 ยืนยันกับเซิร์ฟเวอร์จริงแล้วที่ E.31) และ File Viewer/editor (P8, 2026-08-15) มีครบทั้งสามแล้ว ⇒ เส้นทาง "ทำเองโดยไม่ผ่าน agent" มีปลายทางจริงทั้งสามทาง
- **เดินบนหน้าจอครบทั้งสามทางแล้ว (2026-08-17)**: โต๊ะทำงานมีทั้ง **สมุดงาน** (สร้างใหม่ · รันทั้งหมด · เริ่มเคอร์เนล), **ไฟล์** และ **ฐานข้อมูลภายนอก** อยู่ในพื้นที่เดียวกัน และกดสลับได้จริงทั้งสองอันที่เหลือ ⇒ เส้นทาง "ทำเองโดยไม่ผ่าน agent" ไปถึงปลายทางได้จากจุดที่คนยืนอยู่จริง
- แถว "หยุด" มีแล้วบางส่วน (Plan-only, หยุดทั้งรัน, stop ราย process) ยังไม่มี pause/rework ราย assignment
- **การกดจริงครั้งแรกพิสูจน์คุณค่าของขั้นนี้ทันที**: แผนที่หัวหน้าทีมเสนอมามีเกณฑ์ตรวจรับข้อเดียวกันวนซ้ำสิบกว่าบรรทัด (โมเดลวนใน structured output) และใส่ชื่องานลงช่อง "ผลงานที่ต้องส่ง" — ถ้าไม่มีขั้นให้แก้ แผนนี้จะถูกส่งให้ specialist ทั้งอย่างนั้น

### P4.7 — Team View

**สถานะ**

✅ **ผ่าน Done-when (ตรวจซ้ำ 2026-08-17

- ไม่พบข้อค้างในแถว)**
- แท็บที่สี่ในแอป และ P4.1–P4.5 เข้าถึงได้จริงเป็นครั้งแรก** — ก่อนหน้านี้ `TeamOrchestrator` และ specialist ทั้งสี่ถูกสร้างเฉพาะในเทสของตัวเอง (ดู U14)
- หน้าจอรวมสองแหล่ง: event สดจากหัวหน้าทีม (อย่างเดียวที่บอกได้ว่างานไหน**กำลัง**ทำอยู่) กับ ledger ที่บันทึกไว้ (อย่างเดียวที่รอดข้ามการปิดแอป) merge ด้วย assignment id
- ทุกแถวบอก role
- จำนวนรอบ
- และเหตุผลที่ QA ตีกลับ — "escalate" เปล่าๆ คือสิ่งที่ทำให้ loop ของ v1 อ่านไม่รู้เรื่อง
- **ขับจริงบนหน้าจอแล้ว**: สั่งเป้าหมาย → หัวหน้าทีมวางแผน → มอบหมาย Engineer → รอบ 1 → ตีกลับ → รอบ 2 → รอบ 3 → escalate ตาม retry cap โดยหน้าจอตามทันทุกสถานะ
- ledger ที่เขียนลง DB ตรงกับหน้าจอแล้ว (U15 ปิด)
- ✅ **ปิดส่วนที่ค้างแล้ว (2026-08-12)**: ทุกแถวมีปุ่ม **สั่งแก้** (บังคับให้พิมพ์เหตุผล — ส่งเข้าไปทางช่องเดียวกับ findings ของ QA เพราะ "ทำใหม่อีกรอบ" เฉยๆ คือคำสั่งที่ทำให้ loop ของ v1 วน) และ **ยกเลิก** (บันทึกเป็น `cancelled` ไม่ใช่ลบทิ้ง — "ตัดสินใจไม่ทำ" เป็นสิ่งที่เกิดขึ้นจริงและ Run-until-done ต้องไม่รื้อขึ้นมาเอง เหมือนกับ escalate)
- รอบของการ rework นับต่อจากเดิม ไม่รีเซ็ต (ไม่งั้นเท่ากับแจกโควตา retry ใหม่ฟรีๆ)
- การสั่งแก้จะดึงงานออกจากกอง "รอคน" ให้เอง เพราะคนที่กดคือคนคนนั้น
- 4 เทส

### P4.8 — Operating modes

**สถานะ**

🔶 **โค้ดครบและมีเทส**

- `OperatingModes` แยกสามสวิตช์ออกจากกันจริง (v1 รวม "ไม่รัน" กับ "ไม่ถาม" เข้าด้วยกันจนปิดอันหนึ่งแล้วอีกอันเปลี่ยนตาม), `planOnly` บังคับใน `ToolGateway` ไม่ใช่ที่ตัว agent, `runUntilDone` เป็นสวิตช์ชัดเจนไม่ใช่การเดา
- ทั้งสามอยู่บนหัวหน้าแชทแล้ว
- **สวิตช์ที่สามเคยไม่ทำอะไรเลย — ตอนนี้ทำแล้ว**: `runUntilDone` ถูกประกาศ ส่งเข้า `ToolGateway` และมี toggle บนหน้าแชท แต่เดิม**ไม่มีโค้ดบรรทัดไหนใน `Sources` อ่านค่ามัน และไม่มีเทสตัวไหนแตะมัน**
- **เกณฑ์ "จบงาน" อ่านจาก ledger ไม่ใช่ถามโมเดล** — สิ่งที่เหลือเป็นข้อเท็จจริง ส่วนความเห็นของโมเดลว่าตัวเองเสร็จหรือยังคือสิ่งที่ทำให้ loop ของ v1 วน
- **ข้อสำคัญ: งานที่ escalate ไปแล้วห้ามถูกรื้อขึ้นมาทำเอง** — §2.5 จบด้วยการขอให้คนตัดสิน การ retry อัตโนมัติคือสิ่งที่คำตัดสินนั้นถูกเลือกมาแทน เดิม ledger แยกไม่ออกเพราะ "ถูกขัดจังหวะ" กับ "escalate" เป็น `!passed` เหมือนกัน จึงเพิ่ม `needs_human` และแยก `resumable(scope:)` ออกจาก `unfinished(scope:)`
- เก็บเกณฑ์ตรวจรับลง ledger ด้วย ไม่งั้นสร้าง `Assignment` กลับมาไม่ได้เลย (type ปฏิเสธถ้าไม่มีเกณฑ์)
- เพดาน: `continuationCap` 3 รอบต่อการรันหนึ่งครั้ง
- **เพดาน token ต่อการรันทำแล้ว (2026-08-16, 5 เทส)**: `RunBudget` ตัวเดียวใช้ร่วมกันระหว่างหัวหน้าทีมกับ `SpecialistEnvironment` — สองตัวนับคือสองตัวที่จะไม่ตรงกันครั้งแรกที่มีใครลืมอัปเดตตัวหนึ่ง
- **โทเคนของรอบที่ไม่ผ่านก็นับ** เพราะมันถูกใช้ไปแล้ว เพดานที่นับเฉพาะงานที่สำเร็จจะหลวมที่สุดตอนที่การรันกำลังไปได้ไม่ดี ซึ่งคือตอนที่มันใช้มากที่สุด
- **หยุดระหว่างการเรียก ไม่ใช่กลางการเรียก** — request ที่ถูกตัดครึ่งจ่าย prompt ไปแล้วและไม่ได้อะไรกลับมา
- **หมดงบแล้วต้องพูด**: มี event ของตัวเอง และงานที่ยังไม่ได้เริ่ม**ถูกเขียนลง ledger ว่ารอคนตัดสิน** เพราะการรันที่คืนผลงานน้อยลงเงียบ ๆ หน้าตาเหมือนการรันที่เจองานน้อย
- ช่องกรอกอยู่บนหน้าทีม เว้นว่าง = ไม่จำกัด (ไม่มีตัวเลขที่ระบบเลือกให้เอง)
- ยังไม่ได้กดสวิตช์นี้บนหน้าจอจริงกับรันที่มีงานค้างจริง (เช็คระดับ ledger ผ่านแล้ว)

### P4.9 — Context Manager

**สถานะ**

✅ **ผ่าน Done-when ทั้งสองข้อ กดจริงบนหน้าจอแล้ว**

- `ContextManager` ย่อที่ 75% ของงบ ไม่ใช่รอเต็ม เพราะ handoff ที่เขียนตอนไม่เหลือที่ คือ handoff ที่เขียนไม่ดีหรือไม่ได้เขียน
- ลำดับการทิ้งเรียงตามความเสียดายน้อยสุดก่อน: ผลลัพธ์เครื่องมือดิบ → บทสนทนาเก่าที่ถูกย่อเข้า handoff → **durable rules ไม่ถูกทิ้งเลย** เก็บแยกจาก transcript ไม่ใช่เป็นข้อความแรกในนั้น (v1 ทิ้งคำสั่งตอนต้น session ก่อนเพื่อน เพราะมันคือข้อความที่เก่าที่สุดพอดี)
- **ปิดหนี้ D-5**: สามฟิลด์ที่ v1 ทำให้ไม่ว่างไม่ได้ ถูกสกัดจาก transcript **ไม่ใช่จากการถามโมเดล** — โมเดลที่ถูกถามว่า "ตัดสินอะไรไปบ้าง" จะแต่งคำตอบที่ฟังดูดี ส่วนการอนุมัติที่เกิดขึ้นจริง คำสั่งที่ exit ไม่ใช่ 0 และ path ที่ถูกเปิดจริง เป็นข้อเท็จจริงที่นอนอยู่ในข้อความอยู่แล้ว
- โมเดล (Tier 0, impact ต่ำ) ใช้เฉพาะสองฟิลด์เชิงเล่าเรื่อง ถ้าเรียกไม่ได้ ครึ่งที่เป็นหลักฐานยังมาครบ
- `file_pointers` เก็บ path ไม่เก็บเนื้อหา มีเทสยืนยันว่าเนื้อไฟล์ไม่รั่วเข้ามา
- การตัดไม่ทำให้ `tool` message กำพร้าจาก `tool_calls` ของมัน (E.9)
- **หลักฐานบนหน้าจอ**: บทสนทนา 33 ข้อความ → ย่อ **18,595 → 3,637 tokens** แล้วโมเดลตอบคำถาม "ตอนนี้ค้างอะไรอยู่" ได้ถูกต้องโดยอ้าง `ChunkerTests.swift` กับอาการ expectation failed ซึ่งมาจาก `file_pointers`/`open_issues` ไม่ใช่จากข้อความดิบที่ถูกย่อไปแล้ว
