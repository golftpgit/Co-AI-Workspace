### P15.1 — ต่อ endpoint จริง

**สถานะ**

✅ **ครบแล้ว

- ต่อจริง ถามจริงผ่านหน้าแชท และตัดสายจริงกลางสตรีม (2026-08-16, 9+5+2 เทส + 2 กฎใน check.sh)** — **ชื่อโมเดลมาจาก `/v1/models` ไม่ใช่จากคอนฟิก**: เว้นช่องโมเดลว่าง = "อะไรก็ตามที่เซิร์ฟเวอร์เสิร์ฟอยู่" ซึ่งเป็นค่าเดียวที่รอดจากการสลับ checkpoint — ชื่อที่ปักไว้จะผิดตั้งแต่วันที่เปลี่ยน และ**อาการไม่ใช่ error**: endpoint หลุดจากสายการ route แล้วแอปไปตอบด้วยโมเดลเล็กบนเครื่องนี้แทน โดยไม่มีอะไรบนจอบอก (เกิดจริงมาแล้วตอนเลิกใช้ `--served-model-name`, [E.21](../verification/02-e16-e30.md#e21-gx10--ค่าที่ถูกต้องจริง-วัดด้วย-gx10-checksh-2026-08-16))
- **เสิร์ฟหลายโมเดลแล้วเว้นว่าง = ปฏิเสธ ไม่ใช่เดา** — เดาบน endpoint ที่คิดเงินคือใบเรียกเก็บที่ไม่มีใครตกลงด้วย
- **สลับ checkpoint ระหว่างแอปเปิดอยู่ก็ตามทัน**: 4xx ทำให้ลืมชื่อเก่าแล้วถามใหม่
- **สายหลุดกลางคำตอบพูดเป็นภาษาคน** — แปลที่ `VLLMExecutor` ที่ยังเห็น `URLError` อยู่ (อีกทอดเดียวมันกลายเป็นสตริงแล้วแปลไม่ได้) เทสยิงว่าข้อความมีชื่อ endpoint และไม่มีคำว่า `NSURLErrorDomain` — พิสูจน์แล้วว่าแดงกับโค้ดเดิม
- **ชุด executor contract ทั้งชุดผ่านกับ GX10 จริงแล้ว** ([E.22](../verification/02-e16-e30.md#e22-gx10--คำสั่งที่ครบแล้ว-ผ่านทุกด่าน-2026-08-16)) ผ่าน `COAI_TEST_ENDPOINT`
- **ลงมือขับจริงแล้ว และการขับหยุดที่บั๊กสองตัวก่อนถึงคำถามแรก ([E.32](../verification/03-e31-e46.md#e32-ขับแอปจริงแล้วเจอสองบั๊กที่เทสทั้งชุดมองไม่เห็น-2026-08-16))** — (1) ข้อความที่พิมพ์บนหน้าแชท**บันทึกไม่ลง** เพราะฟิลด์ `pinned` ที่เพิ่มทีหลังเป็น `NONE` บนแถวเก่า และ `DEFAULT` เติมค่าตอนสร้างแถวเท่านั้น — ฐานข้อมูลของเทสเกิดใหม่ทุกครั้ง จึงไม่มีแถวเก่าให้พัง ⇒ `bootstrap` เติมค่าย้อนหลัง และคำสั่งเติม*สร้างจากรายการนิยามฟิลด์เอง* (3 เทส)
- (2) หลัง build ใหม่ **แอปค้างที่ 'กำลังเริ่มระบบ…' ที่ CPU 0% ไม่มีกำหนด** เพราะ `isReady` ของ channel ไปอ่าน*ค่า*โทเคนจาก Keychain บนเมนเธรด ซึ่ง macOS หยุดรอคนอนุมัติ — คอมเมนต์เหนือจุดนั้นเขียนกฎไว้ถูกแล้ว ("channel ที่รันไม่ได้ต้องไม่ทำให้แอปเริ่มไม่ได้") แต่แพ้ที่*วิธีถาม* ⇒ แยก `exists` ออกจาก `read` และฝั่ง Keychain ถามแอตทริบิวต์ซึ่งไม่ติด ACL (4 เทส)
- **ถามผ่านหน้าแชทจริงได้แล้ว และเจอว่าของค้างที่เหลือไม่ใช่การทดสอบ แต่เป็นของที่ยังไม่มี ([E.36](../verification/03-e31-e46.md#e36-พยายามให้-gx10-ตอบผ่านหน้าแชทจริง--และกำแพงที่เจอคือ-ไม่มีสวิตช์-2026-08-16))**: ยกพร็อกซี TCP ขึ้นมาเพื่อให้*ตัดสายได้จริงโดยไม่แตะการตั้งค่าระบบ*
- ชี้ GX10 ผ่านพร็อกซีแล้วหน้าสถานะขึ้น "พร้อมใช้"
- ส่งข้อความจากหน้าแชทได้จริง
- **แต่ทำให้ GX10 เป็นตัวที่ตอบไม่ได้เลยจากหน้าจอ** — ลำดับ §9.2 ถูกต้องตามที่เขียน (เทิร์นแชทเป็น `.disposable` และมีทูลติดไป ⇒ Tier 0 ถูกตัดเอง ⇒ Tier 0.5 ชนะทุกครั้ง ซึ่งถูกเรื่องค่าใช้จ่าย) แต่**ไม่มีทางบอกระบบว่า "คำถามนี้ขอตัวใหญ่"**: หน้าโมเดลมีแค่ "ใช้ตัวนี้"/"ลบ" ไม่มีปุ่มเลิกใช้ Tier 0.5
- ไม่มีตัวเลือกเลือก endpoint ที่หน้าแชท
- `RoutingPolicy` ดูจากชนิดงาน ไม่ใช่จากที่คนขอ ⇒ **สิ่งที่ขาดคือตัวควบคุม ไม่ใช่การวัด** และเป็นสิ่งที่คนอยากได้พอดีในนาทีที่โมเดลเล็กตอบไม่ดี
- **จึงสร้างมันในรอบเดียวกัน แล้วขับจนปิดข้อนี้ได้ ([E.37](../verification/03-e31-e46.md#e37-สร้างสวิตช์ที่-e36-บอกว่าไม่มี-แล้ว-gx10-ก็ตอบผ่านหน้าแชทจริง-2026-08-16), 5 เทส)**: `RoutingPolicy.preferred` + ตัวเลือกโมเดลข้างช่องพิมพ์
- **ตัวเลือกคือลำดับ ไม่ใช่ตัวกรอง** — เลื่อนขึ้นหน้าแถวแต่ไม่ตัดตัวอื่นทิ้ง (endpoint ที่เลือกล่ม = ตอบช้าลง ไม่ใช่แอปตาย)
- เลือกแล้ว**ไม่ทำให้ tier ที่ทำงานนี้ไม่ได้กลายเป็นทำได้** และ**ไม่ปลดล็อกการใช้เงิน** (ปฏิเสธโดยระบุชื่อพร้อมเหตุผลทั้งสองครึ่ง)
- ชื่อที่ไม่มีอยู่แล้ว = ไม่เปลี่ยนอะไร ไม่ใช่ error
- ต่อหนึ่งบทสนทนา ไม่ใช่ค่าตั้งรวม
- **ขับจริง**: เลือก `GX10 · 1a` → ถาม → บนจอขึ้น "คุณเลือก GX10 ไว้สำหรับคำถามนี้" และได้คำตอบ **17 คูณ 3 เท่ากับ 51** (คำถามเดียวกันตอน Tier 0.5 ตอบ สระหายเป็น `17 คณ 3 เทากบ 51` ⇒ คนละโมเดลตอบจริง)
- **ตัดสายกลางสตรีมบนหน้าจอแล้วด้วย ([E.38](../verification/03-e31-e46.md#e38-ตัดสายกลางสตรีมบนหน้าจอจริง--และความเงียบที่ระบบเรียกว่า-สำเร็จ-2026-08-16), +2 เทส)** — และมันไม่ได้ไปยืนยันว่าข้อความผิดพลาดสวยดี แต่ไปเจอว่า**ไม่มีข้อความผิดพลาดเลย**: คนเห็นแค่คำถามของตัวเองกับ "ความคิดของโมเดล" ที่พับอยู่
- ทางจัดการที่เขียนไว้แล้วไม่ทำงานเพราะ**ไม่มีอะไร throw** — SSE ที่หลุดไม่โยน error เสมอไป ซ็อกเก็ตปิด การวนจบ และสตรีมว่างแยกไม่ออกจากสตรีมที่พูดจบพอดี ⇒ เทิร์นเดินเข้าทาง "สำเร็จ" แล้วรายงานความสำเร็จด้วยการเงียบ
- **กฎที่ได้ไม่เกี่ยวกับการเชื่อมต่อ** จึงอยู่ที่ชั้นเทิร์นไม่ใช่ชั้นขนส่ง: *รอบที่ไม่ได้ผลิตข้อความและไม่ได้เรียกทูล คือรอบที่ยังไม่ได้ตอบ* ไม่ว่าด้วยเหตุใด
- หลังแก้ ตัดที่เดิมได้ข้อความที่**ระบุชื่อว่าใครเงียบ**และ**ชี้ทางออกที่อยู่บนหน้าจอเดียวกัน** ⇒ **P15.1 ครบทุกข้อ**
- เก็บกวาดคืนค่าเดิมครบแล้ว

### P15.2b — สมุดทดของโมเดลต้องไม่โผล่บนหน้าจอ

**สถานะ**

✅ **ทำแล้ว (2026-08-16, 2 เทส + 1 กฎใน check.sh)**

- **กันไว้ทั้งสองทาง**: เซิร์ฟเวอร์ที่ตั้ง `--reasoning-parser` ส่งมาคนละฟิลด์อยู่แล้ว ส่วนที่ไม่ได้ตั้ง (เกิดจริงมาแล้วสองครั้ง — [E.21](../verification/02-e16-e30.md#e21-gx10--ค่าที่ถูกต้องจริง-วัดด้วย-gx10-checksh-2026-08-16)) ส่ง `<think>` มาใน `content` เหมือนโมเดลท้องถิ่นเป๊ะ
- **`ReasoningSplitter` ย้ายจาก MLXRuntime มาอยู่ LLMProviders** เพราะสิ่งที่คิดว่าเป็นปัญหาของ tier ท้องถิ่น จริง ๆ เป็นปัญหาของ*แฟล็กที่เซิร์ฟเวอร์* — ตัวตัดตัวเดียวใช้ทั้งสอง tier
- ตัดระหว่างสตรีม และทนแท็กที่ถูกหั่นคร่อม chunk (`<thi` + `nk>`) ซึ่งเป็นวิธีที่มันมาถึงจริง
- สิ่งที่ค้างในตัวตัดตอนจบสตรีมถูก flush ออก ไม่ใช่ทิ้ง เพราะแท็กที่ขาดกลางคือข้อความที่โมเดลพิมพ์จริง
- **กฎใน `check.sh` ห้ามที่อื่นรู้จักหน้าตาของแท็ก** — พิสูจน์แล้วว่าแดงเมื่อ view model เริ่มตัดเอง ซึ่งเป็นวิธีแก้ที่ผุดขึ้นมาเองตอนเห็นแท็กบนจอ แล้วจบด้วยการตัดคนละแบบในสามที่
- **ค้าง**: ยังไม่ได้ถามจริงผ่านหน้าแชท (เป็นข้อเดียวกับที่ P15.1 ค้างไว้)

### P15.3 — เพดานบริบทอ่านจาก endpoint

**สถานะ**

✅ **ทำแล้ว (2026-08-16, 3 เทส + 2 กฎใน check.sh)**

- `max_model_len` มาจากคำตอบเดียวกับที่บอกชื่อโมเดล จึงไม่มีทางเป็นคนละช่วงเวลากัน
- `capabilities.contextWindow` ของแต่ละ endpoint เป็นค่าที่เซิร์ฟเวอร์ประกาศ ไม่ใช่ `32_768` ที่เขียนไว้ในไฟล์ทุกตัว — **ของเดิมผิดทั้งสองทาง**: ขยายที่เซิร์ฟเวอร์แล้วแอปไม่ได้ใช้ ลดที่เซิร์ฟเวอร์แล้วแอปยิงเกินหน้าต่างที่มันเชื่อว่าใหญ่กว่า
- **งบขาเข้ากันที่ให้ขาออกหนึ่งในสี่** (`ContextManager.promptBudget`) เพราะหน้าต่างถูกแบ่งกับคำตอบ และบนโมเดลนี้สมุดทดกิน `max_tokens` ด้วย — วัดแล้วว่าคำขอที่ตั้ง 200 คืน `content` ว่างพร้อม `finish_reason: length` ([E.20](../VERIFICATION_LOG.md))
- เซิร์ฟเวอร์ที่ไม่บอกหน้าต่าง (LM Studio) ได้ค่า nil ไม่ใช่ 0 แล้วตกไปที่พื้น 16k ซึ่งเป็นตัวเลขที่วัดจากเครื่องนี้ ไม่ใช่การเดา
- **ต้องเปิดแอปใหม่ ไม่ต้อง build ใหม่** — อ่านตอนบูตเพราะ router ถูกประกอบตอนนั้น

### P15.4 — จัด prompt ให้ prefix cache ทำงาน

**สถานะ**

✅ **วัดแล้ว (2026-08-16, [E.24](../verification/02-e16-e30.md#e24-prefix-cache-จ่ายจริง--335-วิ--032-วิ-2026-08-16) · 1 เทส)**

- **TTFT 3.35 วิ → 0.32 วิ (เร็วขึ้น 90%)** เมื่อ prefix เดิมถูกใช้ซ้ำ
- **มีตัวคุม**: prefix อื่นที่ยาวเท่ากันกลับไปใช้ 3.45 วิ ⇒ ที่ประหยัดได้คือ cache ไม่ใช่ "เครื่องอุ่นขึ้น" ซึ่งเป็นคำอธิบายที่ตัวเลขคู่เดียวแยกไม่ออก
- โครงสร้าง prompt ถูกอยู่แล้ว (system เดียวหน้าสุด → รายการทูลเรียงตามชื่อ → ประวัติตามลำดับ) สิ่งที่เพิ่มคือ**เทสที่ล็อกลำดับรายการทูล** เพราะมันถูก render ไว้หน้าบทสนทนา — ปลั๊กอินที่โหลดเร็วกว่าเดิมเสี้ยววินาทีแล้วลำดับสลับ = ทุกบทสนทนาเสีย cache เงียบ ๆ **สามวินาทีต่อเทิร์นแขวนอยู่กับลำดับที่ไม่มีใครนึกว่าต้องรักษา** (พิสูจน์แล้วว่าเทสแดงเมื่อถอด `.sorted` ออก)

### P15.5 — วัดตอนหลายสายพร้อมกัน

**สถานะ**

✅ **วัดแล้ว (2026-08-16, [E.23](../verification/02-e16-e30.md#e23-หลายสายพร้อมกัน--และเพดานที่เจอตัวแรกไม่ใช่ของ-gpu-2026-08-16) · 1 เทส + `swift run TierOneCheck`)**

- **span of control = 16 สายขนาน** เวลาต่อคำตอบแย่ลงแค่ **1.5 เท่า** (7.3 → 11.0 วิ) แต่ปริมาณงานรวมขึ้น **11 เท่า** (11.4 → 128.5 โทเคน/วิ)
- `num_requests_running` อ่านได้ 16 และ `waiting` เป็น 0 ตลอด ⇒ **ยังไม่เจอเพดานของ GPU เลย เพดานที่ 16 เป็นเพดานที่เราตั้งเอง**
- **เพดานตัวแรกที่เจอไม่ใช่ของ GPU**: หกสายเร็วเท่าสายเดียว แต่สายที่เจ็ดทำเวลารวมพุ่ง 60% ทั้งที่เวลาต่อคำขอไม่ขยับ — `URLSession.shared` เปิดได้ 6 connection ต่อ host ⇒ **เพดานจริงของแอปเป็น 6 มาตลอดโดยไม่มีอะไรบอก** (ทีมสี่คน + แชท + ลำดับงาน = ครบโควตาพอดี และอาการของการเกินคือช้าลงเฉย ๆ ไม่ใช่ error)
- `VLLMExecutor` ใช้ session ของตัวเองแล้ว และมีเทสที่ยิง 8 สายผ่านเซิร์ฟเวอร์ปลอมซึ่ง**ไม่ตอบใครจนกว่าจะครบแปด** — พิสูจน์แล้วว่าค้างจนหมดเวลาเมื่อเอาค่าที่ตั้งออก
