### P11.9 — ต้นฉบับ 5 บท และตัวเลขในบทที่ 4 ที่ปลอมไม่ได้ (2026-08-15)

Done-when ของ P11.9 ไม่ใช่ "สร้างเอกสารที่ Word เปิดได้" — ส่วนนั้นเป็นของ P7.7 และทำงานอยู่แล้ว · เป็นข้อที่สอง: **ผลสถิติในบทที่ 4 ผูกกลับถึง cell ที่รันจริง**

นี่คือคำสัญญาเรื่องวิธีที่วิทยานิพนธ์กลายเป็นสิ่งที่ไม่จริงบ่อยที่สุด — ไม่มีใครปลอมผล สิ่งที่เกิดคือตัวเลขถูกคัดลอกเข้าร่าง แล้วอีกสามสัปดาห์มีการแก้ข้อมูลและรันใหม่ แต่ร่างยังบอกเลขเดิม · เล่มนั้นผิดในแบบที่กรรมการมองไม่เห็น และผู้เขียนเองก็จำไม่ได้

**ตัวเลขที่รายงานจึงไม่ใช่ข้อความ** แต่เป็น `ResultReference` (สมุดงาน · เซลล์ · คอลัมน์ · แถว) และต้นฉบับถูกสร้างด้วยการ *แปลง* reference กับผลการรันที่บันทึกไว้ · สามอย่างที่กันตัวเลขค้างไม่ให้ขึ้นหน้ากระดาษ:

| กรณี | ผล |
|---|---|
| อ้างเซลล์ที่ไม่เคยรัน | ปฏิเสธทั้งเอกสาร — เอกสารที่มีช่องว่างตรงที่ควรเป็นค่าเฉลี่ยคือเอกสารที่คนส่งออกไปอยู่ดี |
| ผลการรันที่ source ไม่ตรงกับเซลล์ตอนนี้ | ปฏิเสธ — ตัวเลขนั้นมาจากคำสั่งคนละคำสั่ง เป็นเคสข้างบนพอดี และเป็นเคสที่ไม่มีอะไรดูผิดเลย |
| ป้าย `{...}` ในประโยคที่ไม่มี reference รองรับ | ปฏิเสธก่อนถึงหน้ากระดาษ ไม่ปล่อยให้ปีกกาไปโผล่ในเล่ม |

**`BoundResult` ไม่มี public initializer และมีผู้ผลิตทางเดียว** — ตัวเลขในต้นฉบับ "เขียนลงไปเอง" ไม่ได้ (รูปที่สี่ต่อจาก `PublishedInstrument` · `DiscardableInstrument` · `TranscriptQuotation`)

**ห้าบทเป็น `enum` ไม่ใช่จำนวน** — ต้นฉบับที่ขาดบทที่ 4 ไม่ใช่ต้นฉบับที่ตรวจไม่ผ่าน แต่เป็นต้นฉบับที่สร้างไม่ได้ · เทสยืนยันว่าหัวบททั้งห้าอยู่ครบและเรียงถูก

**เซลล์ Python ไม่บันทึกอะไร และเป็นช่องว่างที่ตั้งใจเปิดไว้** — ตัวเลขในเล่มชี้ที่คอลัมน์และแถว ส่วนคำตอบของเซลล์ Python เป็นสายข้อความ · การขูดตัวเลขจาก `print` คือตัวเลขที่ตามกลับไปไม่ได้ ซึ่งเป็นสิ่งที่ P11.9 มีไว้เพื่อกัน

**ภาคผนวก "ที่มาของตัวเลข"** ติดไปกับเอกสารเสมอ — นิสัยเดียวกับ §12.4: ผลที่คนอ่านตามกลับไม่ได้คือผลที่ต้องเชื่อ และวิธีคืนให้ถูกที่สุดคือพิมพ์คำสั่งไว้ข้างตัวเลข

**การวางโมดูล**: `CellRun` อยู่ใน M2 เพราะเป็นบันทึกที่ M8 กับ M10 ใช้ร่วมกัน — วางไว้ฝั่งใดฝั่งหนึ่งจะทำให้อีกฝั่งต้องพึ่ง DuckDB หรือพึ่งตัวเรนเดอร์เอกสารเพียงเพื่อถือตารางสตริง · schema v15 เก็บแถวเดียวต่อ (สมุดงาน, เซลล์) แทนที่ทุกครั้งที่รัน เพราะการเก็บทุกครั้งจะทำให้ "อันไหนคือตัวเลขในเล่ม" กลายเป็นคำถาม · บันทึกที่จุดที่เซลล์รันจริงในหน้าจอสมุดงาน ไม่ใช่ที่อื่น — ที่อื่นจะเป็นการบันทึกว่า*มีการรัน* ไม่ใช่ว่า*รันแล้วได้อะไร*

**เจอตอนทำ**: กฎ `print()` ใน `check.sh` แดงใส่**ความเห็นในโค้ด**ที่อธิบายว่าทำไมห้ามขูดตัวเลขจาก `print()` · ข้ามบรรทัดคอมเมนต์แล้ว — กฎที่แดงใส่ร้อยแก้วคือกฎที่สอนให้คนไม่เขียนร้อยแก้ว (เป็น false positive ตัวที่สองของกฎนี้ ต่อจาก `InstrumentFootprint(`)

**ค้าง**: ยังไม่มีหน้าจอสำหรับ*ประกอบ*ต้นฉบับ (ผูก reference เข้ากับประโยค) — `exportManuscript` พร้อมและต่อกับที่เก็บผลการรันแล้ว แต่ต้องมี `Manuscript` ส่งเข้าไป · WBS template 5 บทมีอยู่แล้วจาก P11.1 และเป็นที่ที่โครงบทควรมาจาก

### P11.8 ครึ่งหลัง — บทถอดเทปเข้าคลังความรู้ และคำอ้างอิงที่ชี้กลับถึงช่วงข้อความจริง (2026-08-15)

Done-when ข้อที่สองของ P11.8 เป็นคำสัญญาเรื่องสิ่งที่จะเกิดอีกหลายเดือน: มีคนอ่านบทที่ 4 อยากตรวจข้อความที่ยกมา แล้วต้องไปถึงคำเดิมในบทสัมภาษณ์เดิม · ความเห็นในโค้ดรักษาสัญญานั้นไม่ได้ สิ่งที่รักษาได้คือ **ข้อความที่ยกมาถูกผลิตด้วยการเฉือนบทถอดเทป และตำแหน่งที่เฉือนเดินทางไปกับมันเข้าไปในคำอ้างอิง**

| กลไก | ทำไม |
|---|---|
| `TranscriptQuotation` ไม่มี public initializer · ผู้ผลิตทางเดียวคือ `of(_:at:)` | ข้อความกับตำแหน่งเกิดจากการกระทำเดียวกันบนสตริงเดียวกัน จึงขัดแย้งกันไม่ได้ · ข้อความที่*พิมพ์*ลงไปคือวิธีที่คำอ้างอิงค่อย ๆ เพี้ยนระหว่างการวิเคราะห์กับการเขียน (รูปเดียวกับ `PublishedInstrument` และ `DiscardableInstrument`) |
| `TextSpan` บน `Provenance` | บทสัมภาษณ์ไม่มีหน้า 7 · ยัดลง `section` ที่เป็นสตริงจะกลายเป็นเลขสองตัวที่ผู้เรียกคนที่สองจัดรูปแบบต่างออกไป |
| ช่วงที่ไม่พอดีถูกปฏิเสธ ไม่ตัดให้สั้น | บทถอดเทปที่แก้หลังลงรหัสขยับตำแหน่งของตัวเองแล้ว — การคืนอักขระที่บังเอิญอยู่ตรงเลขนั้นคือวิธีที่คำพูดไปอยู่ผิดปาก · หน้าจอขึ้น “อ้างกลับไม่ได้” แทนที่จะแสดงข้อความที่เพี้ยน |
| `Origin.fieldwork(participantCode:)` และ tier เป็น `nil` | ห้าชั้นจัดอันดับแหล่ง*ตีพิมพ์*ตามน้ำหนักที่การทบทวนของคนอื่นให้ · บทสัมภาษณ์ที่เก็บเองไม่มีการทบทวนแบบนั้นให้ชี้ ความน่าเชื่อถือมาจากการออกแบบการศึกษา · การให้ tier จะทำให้กติกา corroboration อ่านบทสัมภาษณ์เหมือนวารสาร |
| `Transcript` ไม่มีช่องให้ใส่ชื่อ | บทถอดเทปคือสิ่งที่ถูกแบ่ง จัดทำดัชนี ฝัง embedding ส่งออก และยกมาอ้าง — ตัวตนที่เข้ามาตรงนี้ออกไปทั้งห้าทาง (§20.7) |
| ใช้ `Chunker` ตัวเดิมของ M7 | บทถอดเทปที่ถูกแบ่งต่างจากทุกอย่างในโปรเจกต์จะถูกค้นเจอต่างออกไป ซึ่งเป็นเหตุผลที่ `Chunker.version` มีอยู่ |

**หน้าจอเปลี่ยนวิธีสร้างช่วงข้อความ** — จากพิมพ์ทีละช่วง เป็น**วางบทถอดเทปทั้งฉบับแล้วแบ่งตามย่อหน้า** · ตำแหน่งคือเหตุผล: ช่วงที่พิมพ์เองมีเลขที่คนแต่งขึ้น และคำอ้างอิงที่ตั้งอยู่บนเลขที่แต่งขึ้นคือสิ่งที่ Done-when ข้อนี้พูดถึงพอดี · แต่ละแถวแสดงข้อความที่**เฉือนจากบทถอดเทป** ไม่ใช่สำเนาที่เก็บไว้ในหน่วย พร้อมตำแหน่งกำกับ

**ขับจริง** — วางบทสัมภาษณ์สี่ย่อหน้าผ่านหน้าจอ ได้สี่ช่วงที่ตำแหน่งต่อเนื่องกันจริง (0–32 · 33–76 · 77–100 · 101–144) และข้อความทุกช่วงตรงกับต้นฉบับ

**ข้อค้นพบจากการขับ**: บรรทัดไทยที่แสดง 43 รูป เป็น **44 code point และ 32 `Character`** เพราะสระและวรรณยุกต์ประกอบบนพยัญชนะ · หน่วยไหนไม่สำคัญเท่ากับว่าใช้หน่วยเดียวกันทั้งตอนสร้างและตอนแปลกลับ — citation ที่ส่งออกแล้วถูกแปลกลับด้วยเครื่องมือที่นับ code point จะไปตกคนละประโยค · เขียนไว้ใน `TextSpan` และ**ปักหมุดด้วยเทสที่ใช้บรรทัดจริงจากการขับ** เพื่อให้การเปลี่ยนหน่วยในอนาคตแดงทันทีแทนที่จะขยับคำอ้างอิงทุกอันเงียบ ๆ

**หมายเหตุการขับ**: ตัวขับหน้าจอสลับ index ของช่องกรอกสามช่อง ทำให้ชื่อบทถอดเทปกลายเป็นชื่อผู้ถอดเทป — เป็นความผิดของตัวขับ ไม่ใช่ของแอป (แอปใช้สิ่งที่อยู่ในช่องนั้นถูกต้อง) และเป็นกับดักที่บันทึกไว้แล้วใน `spikes/ScreenDriver` · ลบข้อมูลทดสอบออกจากโปรเจกต์จริงแล้ว

**ค้าง**: หน้าจอยังไม่มีปุ่ม “ส่งบทถอดเทปเข้าคลังความรู้” — `TranscriptIngest.chunks` พร้อมและมีเทสว่าทุก chunk พก provenance กับตำแหน่งของตัวเอง แต่ยังไม่ได้ต่อเข้า `KnowledgeStore` จากหน้าจอ · P11.9 (ต้นฉบับ 5 บท) เป็นที่ที่คำอ้างอิงเหล่านี้จะถูกใช้จริง

**สิ่งที่ตั้งใจไม่ให้กลายเป็น**: ระบบบัญชีผู้ใช้ ไม่มี login ไม่มี cookie — มีแค่ token สุ่ม 32 ตัวในลิงก์ที่ผู้ตอบเก็บไว้ ซึ่งแปลว่าลิงก์นั้นเป็น bearer credential ของคำตอบครึ่งใบของเขา จึงตามมาด้วยสามอย่าง: token ยาวและสุ่ม (ตรงข้ามกับรหัสผู้เข้าร่วมที่ออกแบบให้อ่านออกเสียงได้ ด้วยเหตุผลตรงข้ามกัน) · หน้าที่บันทึกเสร็จ**บอกตรง ๆ ว่าถ้าลิงก์หาย คำตอบกลับมาไม่ได้** · และร่างตายไปพร้อมรอบของมัน

**รายละเอียดที่เป็นการตัดสินใจ ไม่ใช่รายละเอียด**:

| เรื่อง | ทำไม |
|---|---|
| ปุ่ม "บันทึกไว้ก่อน" เป็น submit ปุ่มที่สองของฟอร์มเดิม (`formaction` + `formnovalidate`) ไม่ใช่ JavaScript | สิ่งที่พิมพ์ไปแล้วอยู่ในฟอร์มอยู่แล้ว หน้าที่ต้องพึ่ง JS เพื่อรักษาคำตอบครึ่งใบคือหน้าที่ทำคำตอบหายตอน JS โหลดไม่ขึ้น · และ `formnovalidate` เพราะการบันทึกร่างต้องไม่บังคับข้อจำเป็นแบบตอนส่ง |
| ส่งฟอร์มแล้วร่างถูกลบ | ไม่งั้นจะเหลือสำเนาคำตอบของคนคนหนึ่งที่ไม่มีจุดประสงค์และไม่มีวันหมดอายุ |

### P11.8 ครึ่งแรก — สมุดรหัส การลงรหัส และ κ ที่มีหน้าจอเรียกใช้ (2026-08-14 ดึกมาก)

ครึ่งที่มี Done-when ตรวจได้: "κ คำนวณจากการลงรหัสสองชุดที่รู้คำตอบ" · `Agreement` มี Cohen's/Fleiss' κ ตั้งแต่รอบ ICC และไม่มีใครเรียกใช้เลยจนถึงวันนี้ — รอบนี้คือชั้นที่ป้อนมันและหน้าจอที่เรียกมัน

**สองอย่างที่กำหนดรูปของทุกอย่างที่เหลือ**:

| เรื่อง | ทำไม |
|---|---|
| **ช่วงข้อความถูกกำหนดครั้งเดียว ทุกคนลงรหัสชุดเดียวกัน** | ผู้ลงรหัสสองคนที่ต่างคนต่างเลือกว่าช่วงเริ่มตรงไหน ไม่ได้เห็นตรงกันหรือไม่ตรงกันกับอะไรที่เทียบได้ — คนหนึ่งเจอสามช่วงตรงที่อีกคนเจอสอง และไม่มีเลขคณิตไหนกู้ตัวหารร่วมกลับมาได้ · นี่เป็นทั้งวิธีมาตรฐานของการรายงานความสอดคล้อง และวิธีเดียวที่ตรวจได้ |
| **"ไม่เข้ารหัสไหนเลย" เป็นหมวดหนึ่ง** | คนที่อ่านแล้วตัดสินว่าไม่มีรหัสไหนใช้ได้ ได้ตัดสินไปแล้ว และสองคนที่เห็นตรงกันเรื่องนี้คือเห็นตรงกัน · ต่างจาก "ยังไม่ได้อ่าน" ซึ่งคือการไม่มีแถว — `Agreement` ปฏิเสธ label ที่เป็น nil อยู่แล้วโดยตั้งใจ ([§20.4](../ARCHITECTURE.md#204-ความตรงและความเที่ยง--คำนวณที่ไหน)) |

**สิ่งที่ตัดออกและบอกว่าตัด**: หน่วยที่มีคนใดคนหนึ่งยังไม่ได้ลง ถูกตัดออกจาก κ **และนับให้ดู** — κ ที่คำนวณจาก 11 ช่วงจาก 40 เป็นคนละคำกล่าวอ้างกับ κ จาก 40 ช่วง

**κ รายรหัสด้วย ไม่ใช่แค่ตัวรวม** — เลขต่ำตัวเดียวส่งคนไปไล่ดูทั้งสมุดรหัส คำถามที่ใช้ได้จริงคือ "ไม่ตรงกันที่รหัสไหน" ซึ่งคือการยุบเป็นสองหมวด (รหัสนี้ / ไม่ใช่รหัสนี้) แบบมาตรฐาน · รหัสที่นิยามไว้แล้วไม่เคยถูกใช้ยังมีแถวของตัวเอง เพราะ "นิยาม 11 รหัส ใช้จริง 9" เป็นประโยคที่บทวิธีวิจัยควรพูดได้

**ความอิ่มตัวเป็นเส้นโค้ง ไม่ใช่คำตัดสิน** — นับรหัสใหม่ต่อฉบับตามลำดับที่ลงรหัสจริง (ลำดับถูกบันทึกตอนฉบับแรกโผล่ ไม่ใช่เดาจากลำดับแถวในฐานข้อมูลทีหลัง) · ถ้าแบนสามฉบับติดกันจะบอกว่า "ไม่มีรหัสใหม่หลังฉบับที่ N — เป็นข้อสังเกต ไม่ใช่ข้อสรุปว่าอิ่มตัว การศึกษาที่หยุดที่ฉบับที่ M ไม่มีหลักฐานเรื่องฉบับถัดไป"

**ที่เก็บ** — schema v13 · สามตาราง · แถวการลงรหัสมีคีย์เป็น (ช่วง, ผู้ลงรหัส) ซึ่งเป็น invariant: การเขียนครั้งที่สองจากคนเดิมคือคนเดิมเปลี่ยนใจ ไม่ใช่ความเห็นที่สอง — เก็บทั้งคู่ไว้จะทำให้คนหนึ่งคนเข้าไปอยู่ใน κ สองครั้ง · มีเทสกับฐานข้อมูลจริงที่ยืนยันข้อนี้โดยเฉพาะ

**หน้าจอ** — sub-tab ใหม่ "ลงรหัส" ในโต๊ะทำงาน (มีเฉพาะในโปรเจกต์ เหมือน "เก็บข้อมูล") · ช่องชื่อผู้ลงรหัสอยู่บนสุดและ**ไม่ถูกจำข้ามครั้ง ไม่มีค่าตั้งต้น** — κ เป็นข้อความเกี่ยวกับคน และวิธีที่การศึกษาความสอดคล้องพังบ่อยที่สุดคือคนที่สองมานั่งลงกับเครื่องที่ยังเป็นชื่อคนแรก · κ กับเส้นโค้งคำนวณสดขณะมอง ไม่ต้องกดปุ่ม (นับเฉย ๆ ไม่ใช่การแยกค่าลักษณะเฉพาะร้อยรอบ) เพราะเลขความสอดคล้องที่โผล่เมื่อกดถามคือเลขที่คนถามตอนจบ ซึ่งเป็นจังหวะเดียวที่สายเกินจะแก้

**ขับจริงแล้ว** — สร้างสมุดรหัส เพิ่มสองรหัสพร้อมนิยาม เพิ่มสี่ช่วงจากสองบทถอดเทป แล้วให้ผู้ลงรหัสสองคนลงจริงผ่านหน้าจอ ตั้งใจให้ไม่ตรงกันหนึ่งช่วง · หน้าจอขึ้น **κ 0.50 · ตรงกันจริง 75% · 4 หน่วย · 2 ผู้ลงรหัส · ปานกลาง (moderate)** ซึ่งตรงกับที่คำนวณบนกระดาษไว้ก่อนรัน (Po .75 · Pe .50 · κ .50) · ลบข้อมูลทดสอบออกจากโปรเจกต์จริงแล้ว

**ปิดช่องว่างในทะเบียนประตูด้วย** — `intercoder_agreement` ย้ายจาก `notAnswerableYet` ไป `answerable`: มีที่เก็บแล้ว "การศึกษานี้ได้ทำการตรวจหรือยัง" จึงเป็นคำถามที่ฐานข้อมูลตอบได้ · แต่ **κ ดีพอหรือไม่ ไม่เข้าประตู** — κ ต่ำคือผลที่ต้องเล่าและตอบด้วยการลับสมุดรหัสแล้วลงรหัสใหม่ ประตูที่บล็อกที่ตัวเลขจะบล็อกโครงการที่กำลังทำสิ่งที่ถูกต้องพอดี · `saturation_reached` ยังอยู่ในทะเบียนช่องว่าง พร้อมเหตุผลใหม่: เส้นโค้งคำนวณแล้ว แต่การ*ประกาศ*ว่าอิ่มตัวเป็นข้อสรุปของผู้วิจัย ไม่ใช่ของซอฟต์แวร์

**เจอตอนทำ**: การย้าย `intercoder_agreement` ทำให้เทสประตูแดง และมันถูก — เงื่อนไขที่ระบบ*ตอบได้* แต่ไม่มีใครส่งคำตอบมา (reader ยังไม่ถูกต่อ) ตกไปอยู่ในกรณี "ไม่รู้จักชื่อนี้" ซึ่งชี้ผิดที่ · แยกเป็นสี่กรณีแล้ว: ตอบได้และตอบแล้ว → ตัดสิน · ตอบได้แต่ยังไม่ได้ตรวจ → บล็อกพร้อมบอกว่ายังไม่ได้ต่อกับที่เก็บ · ช่องว่างที่มีชื่อ → `vacuous` · ไม่รู้จัก → บล็อกพร้อมบอกว่าไม่รู้จักคำไหน

**ค้าง (P11.8 ครึ่งหลัง)**: ถอดเทป → เข้าคลังความรู้พร้อม provenance และ citation ในต้นฉบับที่ชี้กลับถึงช่วงข้อความจริง · ตอนนี้ `CodingUnit` เก็บ `documentID` กับช่วงตำแหน่งไว้แล้ว ซึ่งเป็นปลายที่รออีกฝั่ง

### ลบร่างเครื่องมือได้ และ gate ที่ชนิดโปรเจกต์ประกาศกลายเป็นของจริง (2026-08-14 ดึก รอบสอง)

**1. ลบร่างเครื่องมือ** — รอบขับก่อนหน้าทิ้งเครื่องมือทดสอบไว้สองชิ้นในโปรเจกต์จริง เพราะหน้าจอไม่มีทางเอาออก · แต่ "ลบแบบสอบถาม" ไม่ใช่การเก็บกวาดในงานวิจัย จึงมีสามอย่างที่ทำให้ลบไม่ได้ และแต่ละอย่างมีเหตุผลของตัวเอง:

| เงื่อนไข | ทำไมต้องอยู่ต่อ |
|---|---|
| ผ่านประตูแล้ว | [§20.6](../ARCHITECTURE.md#206-m15--module-และ-invariant) บอกว่าเวอร์ชันที่ผ่านประตูแก้ไม่ได้ เพราะมันคือบันทึกว่าผู้ตอบเห็นอะไร — ลบทิ้งคือลบคำตอบของคำถามที่กรรมการถามเมื่อผลออกมาน่าแปลกใจ |
| มีคำตอบผูกอยู่ | คำตอบเขียนทับไม่ได้อยู่แล้ว ([§19.17](../ARCHITECTURE.md#1917-ฐานข้อมูลภายในของโปรเจกต์--sql-nosql-และช่องว่างจริงที่ต้องเติม) invariant 2) — เครื่องมือที่หายไปทิ้งตารางตัวเลขที่ไม่มีใครบอกได้ว่าคำถามคืออะไร |
| เคยเปิดรอบเก็บข้อมูล | แม้รอบที่ไม่มีใครตอบ ก็เป็นบันทึกว่าลงพื้นที่วันไหน และ attrition คือส่วนต่างระหว่างคนที่ถูกถามกับคนที่ตอบ |

กติกาถูกยกให้ **types เป็นคนถือ** ไม่ใช่ให้คนจำ: `InstrumentStore.delete` รับ `DiscardableInstrument` ซึ่งไม่มี public initializer และมีผู้ผลิตทางเดียวคือ `InstrumentDisposal.check` — รูปเดียวกับ `PublishedInstrument` แต่คนละทิศ · มีเทสที่ปักหมุดว่าทั้งสองข้อนี้ยังจริง · หน้าจอ**แสดงปุ่มไว้แล้วปิดการใช้งานพร้อมเหตุผลข้าง ๆ** ไม่ใช่ซ่อน — ตรงข้ามกับปุ่ม "เปิดฟอร์ม" ที่หายไปเลยเมื่อยังไม่ผ่านประตู เพราะตรงนั้นไม่มีอะไรให้เสิร์ฟ ส่วนตรงนี้มีของให้ลบและมีกฎบอกว่าอย่า — กฎที่มองไม่เห็นอ่านเหมือนหน้าจอเสีย · **ขับจริงแล้ว**: ลบเครื่องมือทดสอบทั้งสองชิ้นออกจากโปรเจกต์จริงผ่านหน้าจอ และเห็นข้อความปฏิเสธจริงบนเครื่องมือที่ผ่านประตูแล้วทั้งสองตัว

**2. gate ที่ชนิดโปรเจกต์ประกาศ** — P11.1 ทิ้งไว้ว่า "ยังเก็บเป็นข้อมูล ยังไม่ถูกบังคับ" ซึ่งเป็นรูปเดียวกับ `Scope.project` ที่เป็นฟิลด์ว่าง ๆ อยู่เก้าเฟส

**บังคับที่ไหน** — ประตูเหล่านี้ยืนอยู่ที่ milestone กลางขั้น ไม่ใช่ที่ขอบขั้น การสร้างเครื่องจักร milestone มารองรับคือการสร้างเครื่องจักรขั้นตัวที่สองข้าง ๆ ตัวที่ [§19.4](../ARCHITECTURE.md#194-project-life-cycle-5-ขั้น--stage-gate) มีอยู่แล้ว · ที่แข็งแรงที่สุดโดยไม่สร้างของซ้ำคือ**ขอบขาออกจากขั้นดำเนินการ**: โครงการจะถูกห่อจบไม่ได้ขณะที่คำสัญญาที่ชนิดของมันเองประกาศไว้ยังไม่เป็นจริง · สำหรับงานวิจัย นี่เป็นตาข่ายรอง ไม่ใช่ด่านแรก — ด่านแรกคือ `InstrumentGate.approve` ที่เป็นผู้ผลิตเพียงทางเดียวของสิ่งที่ M16 ยอมเสิร์ฟ ซึ่งหยุดตั้งแต่ก่อนลงพื้นที่

**ตอบสามทาง และความต่างของสามทางคือทั้งหมดของการออกแบบนี้**:

| กรณี | ผล | ทำไม |
|---|---|---|
| ระบบตอบได้ | บล็อกเมื่อเป็นเท็จ | นี่คือ "บังคับ" ที่งานนี้พูดถึง — วันนี้ตอบได้สามข้อ อ่านจากเครื่องมือของโปรเจกต์เอง |
| ช่องว่างที่มีชื่อ | ไม่บล็อก แต่ขึ้นเป็น `vacuous` | ถ้าบล็อก 4 ใน 6 ชนิดที่ ship อยู่จะออกจากขั้นดำเนินการไม่ได้เลย — บั๊กที่แต่งตัวเป็นความเข้มงวด · ธง `vacuous` มีอยู่แล้วตั้งแต่ §19.4 เพื่อไม่ให้ "ไม่ได้ตรวจ" เรนเดอร์เป็นติ๊กเขียว และหน้าจอทั้งสองที่แสดงประตูรองรับอยู่แล้ว |
| ไม่รู้จักชื่อ | บล็อก พร้อมบอกว่าไม่รู้จักคำไหน | เงื่อนไขที่แต่งขึ้นได้แล้วเงียบ ๆ ไม่ทำอะไร คือการทำให้บรรทัด `gate:` กลับไปเป็นของประดับ — ในทางปฏิบัติแปลว่าสะกดผิดในไฟล์ชนิดจะหยุดโปรเจกต์ของชนิดนั้นและบอกว่าคำไหน |

`notAnswerableYet` เขียนไว้เหมือน `RiskScorer.notBuiltYet`: ทุกเงื่อนไขที่ยังตอบไม่ได้มีชื่อเฟสที่จะมาปิดมันกำกับ และมี**เทสที่อ่านไฟล์ชนิดโปรเจกต์ที่ ship จริง**แล้วยืนยันว่าไม่มีเงื่อนไขไหนหลุดจากทั้งสองทะเบียน — เพิ่มชนิดใหม่ที่เอ่ยเงื่อนไขที่ไม่มีใครตอบได้ แล้วเทสแดงทันที

**เจอระหว่างทาง**: กฎ `print()` ใน `check.sh` จับ `InstrumentFootprint(` เป็น false positive (ลงท้ายด้วยหกตัวอักษรเดียวกัน) — ผูกขอบคำแล้ว เพราะกฎโครงสร้างที่แดงเพราะชื่อตัวแปรคือกฎที่คนเรียนรู้ที่จะเลี่ยง · โปรเจกต์เดิมทั้งสองบนเครื่องนี้ `typeName` เป็น null จึงไม่มี gate ของชนิดใดมาบังคับ ซึ่งถูกต้องตามการออกแบบ แต่แปลว่าฟีเจอร์นี้มีผลกับโปรเจกต์ที่สร้างใหม่จากไฟล์ชนิดเท่านั้น

### P11.3 ปิดแล้ว — EFA ผ่าน Accelerate และหน้าจอที่เรียกมันได้ (2026-08-14 ดึก)

ชิ้นสุดท้ายของ P11.3 คือความตรงเชิงโครงสร้าง ซึ่งต่างจาก IOC/CVI ตรงที่ **ถามหลังเก็บข้อมูล ไม่ใช่ก่อน** — จึงไม่ใช่ประตู และตั้งใจไม่ให้เป็น: ประตูที่ตั้งบนข้อมูลที่เก็บมาแล้วคือประตูที่ปฏิเสธเครื่องมือที่ถูกใช้ไปแล้ว

**ตรวจยังไงว่าไม่ได้ผิดแบบเงียบ ๆ (R12)** — สองชั้น ทั้งคู่ใช้เลขที่โปรเจกต์นี้ไม่ได้เป็นคนผลิต:

1. **รูปปิดเชิงพีชคณิต** — เมทริกซ์ equicorrelation `(1−ρ)I + ρJ` มี eigenvalue เป็น `1+(p−1)ρ` หนึ่งตัวและ `1−ρ` อีก p−1 ตัว, determinant เป็น `(1−ρ)^(p−1)(1+(p−1)ρ)`, KMO ยุบเหลือ `k²/(k²+1)` เมื่อ `k = 1+(p−2)ρ`, และน้ำหนักองค์ประกอบเดียวเท่ากับ `√ρ` พอดี — ไม่มีเลขคณิตของเราอยู่ในค่าที่คาดหวังเลยสักตัว
2. **implementation อิสระ** — เขียน EFA ทั้งชุดด้วย Python ล้วน (Jacobi eigen เพราะเครื่องนี้ไม่มี numpy) **ก่อน** เขียน Swift แล้วให้ Swift ต้องได้เลขเดียวกันบนข้อมูล 40×6 ชุดเดิม — ตรงถึง 1e-5 ทุกตัวตั้งแต่รันแรก (eigenvalue · KMO · MSA รายข้อ · Bartlett · น้ำหนักหลังหมุนแกน · ค่าความร่วม · ω)

**สิ่งที่ตั้งใจให้ต่างจากซอฟต์แวร์สถิติทั่วไป**:

| เรื่อง | ทำไม |
|---|---|
| คำนวณ **ทั้ง** Kaiser และ parallel analysis เสมอ แล้วรายงานทั้งคู่ | Kaiser สกัดเกินราวหนึ่งองค์ประกอบต่อห้าข้อ และเป็นค่าตั้งต้นของเกือบทุกโปรแกรม · ถ้าสองเกณฑ์ไม่ตรงกัน นั่นคือ *ข้อค้นพบ* ไม่ใช่การตั้งค่า จึงขึ้นเป็นคำเตือน |
| ตัวสุ่มของ parallel analysis มี seed จากรูปร่างข้อมูล ไม่ใช่จากนาฬิกา | รันซ้ำต้องได้จำนวนองค์ประกอบเท่าเดิม ไม่งั้นบทวิธีวิจัยทำซ้ำไม่ได้ตั้งแต่โครงสร้าง |
| principal axis ไม่ใช่ principal components | component สรุปความแปรปรวนรวม noise ของแต่ละข้อ · factor จำลองเฉพาะส่วนที่ใช้ร่วมกัน — งานพัฒนามาตรวัดต้องการอย่างหลัง |
| Heywood case ถูก**เรียกชื่อข้อ** ไม่ใช่ปัดให้สวย | ค่าความร่วมเกิน 1 ตามคณิตศาสตร์คือคำตอบที่ไม่ถูกต้อง ไม่ใช่ตัวเลขที่ต้องทำให้ดูดี |

**การตัดสินใจเชิงโครงสร้างสองข้อ**:

- **`StatKit` + `CLapack` เป็น target ใหม่** — M15 ห้ามพึ่ง M8 ([§20.6](../ARCHITECTURE.md#206-m15--module-และ-invariant)) แต่ Bartlett ต้องใช้ปลาย chi-square ที่อยู่ใน `Statistics` ของ M8 · ทางเลือกคือคัดลอก continued fraction ไปอีกชุด ซึ่งเป็นรูปความผิดพลาดเดียวกับ SQL guard ที่เคยมีสองชุดแล้วเพี้ยนออกจากกัน — แต่แย่กว่า เพราะสองสำเนาจะตรงกันหลายปีแล้วต่างกันที่ทศนิยมตำแหน่งที่สี่ในตารางเดียวที่มีคนตีพิมพ์ · จึงย้ายออกมาเป็น target ที่ไม่มี dependency แล้ว `Statistics` ส่งต่อ (ไม่มี call site ไหนต้องแก้เลย) และเพิ่มกฎใน `check.sh`: แดงถ้ามีสำเนาที่สองของ incomplete gamma/beta หรือมีใครเรียก LAPACK จาก Swift ตรง ๆ
- **LAPACK ผ่าน C shim** — `ACCELERATE_NEW_LAPACK` เป็น macro ของ C คุยกับ Clang module ไม่ได้ผ่าน `-D` ของ Swift ทางที่ Swift เห็นเองจึงมีแต่อินเทอร์เฟซที่ deprecated ตั้งแต่ macOS 13.3 · shim สี่สิบกว่าบรรทัดทำให้บิลด์ไม่มีคำเตือน และคำเตือนจริงตัวถัดไปยังมีคนอ่าน

**หน้าจอ** — กล่อง “ความเที่ยงและความตรงเชิงโครงสร้าง” ต่อท้ายตารางคำตอบ: α/ω รายมาตรวัด (พร้อมข้อที่ item-total ต่ำกว่า .30 ระบุชื่อ) · KMO/Bartlett · ตารางน้ำหนักหลังหมุนแกน · เทียบกับ construct ที่ประกาศไว้ · คำเตือนขนาดตัวอย่างวางไว้ข้างตาราง ไม่ใช่ให้คนอ่านไปค้นเอง · สลับเกณฑ์จำนวนองค์ประกอบได้จากหน้าจอเพื่อดูว่าคำตอบเปลี่ยนไหม · การคำนวณอยู่นอก main actor เพราะ parallel analysis คือการแยกค่าลักษณะเฉพาะร้อยรอบ

**ตรรกะทั้งหมดอยู่ใน M15 ไม่ใช่ในหน้าจอ** — app target เป็น executable ที่ไม่มี unit test การตัดสินใจที่ไปอยู่ตรงนั้นคือการตัดสินใจที่ไม่มีอะไรตรวจ (บทเรียนเดิม: ConflictDetector ผ่านเทส 7 ตัวโดยไม่มีใครสร้างมันเลย) · หน้าจอเหลือหน้าที่เดียวคือแปลง `ResponseRow` เป็น map ของ item id → ข้อความ ที่เหลือ — อะไรกลายเป็นตัวเลข ใครถูกตัดออก ข้อไหนอยู่มาตรวัดไหน — อยู่ใน `ScoredResponses`/`ScaleReport` ซึ่ง `swift test` เข้าถึงได้

**เทสที่เดินทางยาว**: POST 40 ชุดผ่าน routing table จริงเข้า SQLite จริง อ่านกลับ แล้วสกัดองค์ประกอบ — ได้โครงสร้างสององค์ประกอบที่ปลูกไว้ ข้อลงตรงทุกข้อ · และอีกตัวยืนยันว่าค่าที่ถูก**แก้**คือค่าที่ถูกวิเคราะห์ ขณะที่แถวที่มาถึงยังไม่ถูกแตะ ([§19.17](../ARCHITECTURE.md#1917-ฐานข้อมูลภายในของโปรเจกต์--sql-nosql-และช่องว่างจริงที่ต้องเติม) invariant 2)

**966 เทสผ่าน · `check.sh` เขียวทั้งหมด · `.app` build และ launch ได้ sidecar ขึ้นและถูกเก็บตอน quit** — **ยังไม่ได้ขับกล่องใหม่ด้วยมือ**: ต้องมีโปรเจกต์ที่มีเครื่องมือผ่านประตูและคำตอบจริงหลายสิบชุดก่อน ซึ่งเป็นลำดับยาว · ชั้นข้อมูลพิสูจน์ด้วยเทสที่เดินทางยาวแล้ว สิ่งที่การขับด้วยมือจะเพิ่มคือการจัดวางของกล่องบนหน้าจอ ซึ่งเป็นที่ที่รอบก่อน ๆ เจอบั๊กทุกครั้ง


### P11.3 ที่เหลือ — ICC และ κ (2026-08-14 กลางคืน)

เครื่องถูกล็อกอยู่ จึงทำส่วนที่พิสูจน์ด้วยเทสได้ล้วน ๆ: สถิติความสอดคล้องระหว่างผู้ประเมิน ซึ่งไม่ต้องใช้หน้าจอเลย

**วิธีตรวจที่ความเสี่ยง R12 เรียกร้อง** — "สถิติที่เขียนเองผิดแบบเงียบ ๆ" แก้ด้วยการเทียบกับตัวอย่างที่คนอื่นตีพิมพ์ ไม่ใช่กับผลของตัวเอง: คำนวณตาราง 2 ของ Shrout & Fleiss (1979) ด้วย Python แยกก่อน ได้ .1657/.2898/.7148 และ .4428/.6201/.9093 ซึ่งตรงกับที่ตีพิมพ์ (.17/.29/.71 · .44/.62/.91) แล้วจึงเขียน Swift ให้ได้เลขเดียวกัน · Cohen’s κ เทียบกับ 2×2 ที่คำนวณบนกระดาษได้ (Po .70 · Pe .50 · κ .40) · Fleiss’ κ เทียบกับเมทริกซ์เล็กที่ตรวจมือได้

**สิ่งที่ตั้งใจให้ต่างจากไลบรารีทั่วไป**:

| เรื่อง | ทำไม |
|---|---|
| คืน **ICC ทั้ง 6 รูป** ไม่ใช่ "the ICC" | การเลือกว่าใช้รูปไหนเป็นการตัดสินใจเชิงออกแบบที่ผู้วิจัยต้องอธิบายได้ ไลบรารีที่เลือกให้เงียบ ๆ คือไลบรารีที่ตัดสินใจแทน |
| ผู้ประเมินคนเดียว / หน่วยเดียว / ทุกหน่วยคะแนนเท่ากัน → `nil` | ไม่ใช่การศึกษาความเที่ยง และตัวเลขที่ออกมาจะถูกเอาไปอ้างในเล่ม |
| รายงาน **% ตรงกันจริง คู่กับ κ เสมอ** | κ ต่ำเพราะหมวดเดียวกินหมด (ลงตรงกัน 96% แต่ κ ≈ 0) เป็นคนละเรื่องกับผู้ลงรหัสไม่เก่ง — คนอ่านที่เห็นเลขเดียวสรุปผิดทั้งสองทาง |
| κ เมื่อทุกคนใช้หมวดเดียวทั้งหมด = 1 ไม่ใช่ 0 | สูตรเป็น 0/0 ที่จุดนั้น และการรายงาน 0 คือการบอกว่า "ไม่ดีกว่าการเดา" กับผู้ลงรหัสที่ไม่เคยขัดแย้งกันเลย |

**หมายเหตุ**: `check.sh` ล้ม 1 ครั้งแล้วผ่านสองครั้งถัดมา และ `swift test` เต็มชุดก็ล้มครั้งหนึ่งที่เทส "pause suspends the process" ซึ่งผ่านทุกครั้งเมื่อรันเดี่ยว — เข้ากับ U12 ที่บันทึกไว้แล้วว่ามีเทสที่ขึ้นกับ wall-clock


### P11.7b ครึ่งหลัง — รหัสถึงคำตอบ และหน้าจอผู้เข้าร่วม (2026-08-14 ค่ำ)

**สิ่งที่ขาดไปในรอบก่อน**: รหัสที่เก็บไว้ในไฟล์ตัวตนแต่ไม่เคยเดินทางไปกับฟอร์ม เชื่อมอะไรไม่ได้เลย รอบนี้จึงต่อครึ่งหลัง — ลิงก์ที่ส่งให้ผู้เข้าร่วมลงท้ายด้วย `?code=P-…` หน้าเว็บพารหัสไปเป็น hidden field และคำตอบถูกเก็บคู่กับรหัสนั้น **M16 ยังทำได้แค่เก็บสตริง**: มันแปลงรหัสเป็นคนไม่ได้ เพราะ `Linkage` ไม่อยู่ใน module graph ของมัน และ `check.sh` แดงถ้าวันหนึ่งมันอยู่

**เรื่อง migration ที่เกือบพลาด**: `CREATE TABLE IF NOT EXISTS` ไม่ทำอะไรกับตารางที่มีอยู่แล้ว ฐานข้อมูลที่สร้างก่อนคอลัมน์ `participant_code` จะเกิดจึง**ขาดคอลัมน์อย่างเงียบ ๆ** และความผิดพลาดจะโผล่อีกหลายเดือนถัดมาในรูป "รอบนี้เชื่อมกับรอบก่อนไม่ได้" — เติมด้วย `ALTER TABLE` ที่ตรวจ `PRAGMA table_info` ก่อน และมีเทสที่สร้างไฟล์รูปแบบเก่าขึ้นมาจริงเพื่อพิสูจน์

**หน้าจอผู้เข้าร่วม** — ปิด §20.6 invariant 3 ที่รอบก่อนยังไม่ผ่าน: ลงทะเบียนแล้วได้รหัส · คัดลอกลิงก์เฉพาะคน · เชิญทุกคนเข้ารอบที่เปิดอยู่ · attrition ต่อรอบ (เชิญกี่คน ตอบกลับกี่คน กี่เปอร์เซ็นต์) · และ "ดูว่าเป็นใคร" ที่**ตั้งใจให้ไม่สะดวก**: ต้องกรอกเหตุผลและชื่อ แสดงทีละคน และลืมทันทีที่ปิดแผ่น — หน้าจอที่ค้างชื่อไว้คือหน้าจอที่โชว์ให้คนที่เดินผ่านมาคนถัดไป

**ยังไม่ได้ขับด้วยมือ**: build ผ่าน · 908 เทสเขียว · `check.sh` เขียว แต่**เครื่องถูกล็อกระหว่างรอบนี้** (`CGSSessionScreenIsLocked = true`) แอปจึงเปิดขึ้นมาโดยไม่มีหน้าต่าง ซึ่งหน้าตาเหมือน boot ล้มเหลวเป๊ะ — เป็นสถานการณ์เดียวกับ U19 และปลดล็อกเองไม่ได้ ไม่ควรปลด การกดยืนยันหน้าจอนี้ยกไปรอบหน้าทั้งหมด


### P11.7b ชั้นข้อมูล — ตัวตนที่แยกไฟล์และผนึกไว้ (2026-08-14 เย็น)

ยังไม่ได้ขับหน้าจอ **เพราะยังไม่มีหน้าจอ** — รอบนี้เป็นชั้นข้อมูลล้วน และบันทึกไว้ตรง ๆ ว่าเท่ากับยังไม่ผ่าน §20.6 invariant 3

**สิ่งที่ป้องกันคนละอย่างกัน สองชั้น** — §20.7 ขอทั้งสอง และเหตุผลต่างกัน: *แยกไฟล์* ทำให้สำเนาข้อมูลคำตอบ (ไฟล์ที่ถูกส่งให้อาจารย์ที่ปรึกษา ใส่ USB แนบไปกับการส่งเล่ม) ไม่มีตัวตนติดไปเลย ส่วน *คีย์ใน Keychain* ทำให้ไฟล์ตัวตนที่หลุดไปเดี่ยว ๆ เป็นแค่ ciphertext — backup ของเครื่องที่หายไม่ใช่รายชื่อว่าใครตอบว่าตัวเองหมดไฟ

**วิธีพิสูจน์ที่เลือก**: เทสอ่าน**ไบต์ดิบของไฟล์ฐานข้อมูลรวม `-wal`** แล้วค้นหาชื่อผู้เข้าร่วมกับตัวคีย์ — เพราะ "เราเข้ารหัสแล้ว" เป็นคำอ้างเกี่ยวกับโค้ด ส่วน "สตริงนี้ไม่มีอยู่ในไฟล์" เป็นข้อเท็จจริงเกี่ยวกับดิสก์ (ค่าที่เขียนแล้วแต่ยัง checkpoint ไม่ถึงก็ยังอยู่บนดิสก์ จึงต้องอ่าน `-wal` ด้วย)

**รายละเอียดที่ตั้งใจ**: คีย์แยกต่อโปรเจกต์ (คีย์เดียวทั้งแอป = สองงานวิจัยกลายเป็นการรั่วครั้งเดียว) · ไม่ sync ข้ามเครื่อง · `resolve` เขียน span **ก่อน**คืนค่าและเขียนแม้หารหัสไม่เจอ · รหัสผู้เข้าร่วมไม่มีสระ (สะกดเป็นคำไม่ได้) และไม่มี O/0 I/1 เพราะภาคสนามมีคนต้องอ่านรหัสให้กันฟังทางโทรศัพท์ และรหัสที่ฟังผิดคือคำตอบที่ไปต่อกับคนผิดอย่างเงียบ ๆ


### กดหน้าจอจริง รอบ materialize (2026-08-14 บ่าย)

ปิดเส้นทางข้อมูลที่เหลืออยู่: ฟอร์ม → SQLite → **DuckDB** → สมุดงาน/explorer

**ทางที่เลือกและเหตุผล**: [§19.17](../ARCHITECTURE.md#1917-ฐานข้อมูลภายในของโปรเจกต์--sql-nosql-และช่องว่างจริงที่ต้องเติม) วาดลูกศรนี้เป็น DuckDB `ATTACH` ไฟล์ SQLite ซึ่งเป็นภาพที่ถูกแต่กลไกที่ใช้ไม่ได้ที่นี่ — P6.2 กับ U19 บันทึกไว้แล้วว่า DuckDB ในแอปที่ sandbox โหลด `sqlite_scanner` ไม่ได้ถ้าไม่มีเน็ต ลูกศรนั้นจึงทำงานบนเครื่อง developer แล้วพังในวันที่นักวิจัยออฟไลน์อยู่กับข้อมูลของตัวเอง จึงอ่านผ่าน `OLTP` แล้ว `INSERT` แทน — ไม่ต้องมี extension ไม่ต้องมีเน็ต และ**ทิศทางไม่เปลี่ยน: แอปเป็นฝ่ายดึง** M16 ยังไม่รู้จัก DuckDB เลย (`check.sh` เพิ่มกฎว่า `OLTP` ห้าม import `Analysis`/`DuckDB` ด้วย)

**ที่ยืนยันด้วยการกดจริง**: กดปุ่มในหน้าคำตอบ → ขึ้นชื่อตารางกับจำนวนแถว · เปิด "ฐานข้อมูลภายใน" เห็นตารางกับ 15 แถว · query แล้วได้ `I feel tense during a night shift | 5 | true` — คือค่าที่ถูกแก้ มาในรูปค่าใหม่ **พร้อมคอลัมน์บอกว่าถูกแก้** และหัวข้อคำถามเป็นข้อความจริง ไม่ใช่ id ที่อ่านไม่ออก

### กดหน้าจอจริง รอบ P11.7 + P11.1 (2026-08-14 สาย)

เจ้าของเครื่องเปิดจอให้แล้ว จึงขับของที่ค้างจากรอบก่อนทั้งหมด **ผ่านทุกข้อ** และเจอเพิ่มอีกสอง

**ที่ยืนยันด้วยการกดจริง**: ตารางคำตอบขึ้นครบ 4 ชุดจากรอบ LAN เมื่อวาน คอลัมน์เป็นข้อคำถามจริง · แก้ค่าหนึ่งช่อง (4 → 5 พร้อมเหตุผลและชื่อ) แล้ว **แถว `answer` ในฐานข้อมูลยังเป็น 4** และ `correction` เก็บ 4|5|เหตุผล|ชื่อ ไว้ข้าง ๆ — ช่องนั้นขึ้นไอคอนดินสอ · ตัวนับเดินเอง 4 → 5 ภายใน 3 วินาทีหลัง `curl` ส่งคำตอบเข้ามา **โดยไม่ต้องกดอะไร** · เปิดเซิร์ฟเวอร์แล้วมีแถว `wave` เกิดขึ้นจริง · **หยุดเซิร์ฟเวอร์แล้วรอบยังเปิด** และเปิดใหม่ได้รอบเดิม (id เดียวกัน) · ปิดรอบแล้ว POST ได้ 410 · **ออกจากแอปแล้วเปิดใหม่ รอบที่ปิดยังปิด** และกดเปิดฟอร์มได้รอบใหม่ โดยรอบเก่ายังแสดงวันปิดกับจำนวนชุดของมัน

### P11.7 รอบแรก — รอบเก็บข้อมูลที่ปิดแล้วต้องปิดจริง และหน้า "คำตอบ" (2026-08-14)

ทำตอนเจ้าของเครื่องไม่อยู่ จึง**ไม่ได้ขับหน้าจอเลย** — ทุกข้ออ้างในรอบนี้พิสูจน์ด้วยเทส (882 ผ่าน) ไม่ใช่ด้วยการกด และการกดยืนยันยกไปรอบหน้าทั้งหมด

**สองข้อที่เขียนผิดไว้ตั้งแต่ P11.5 และแก้แล้ว** — ทั้งคู่ทำให้ "วันที่เก็บข้อมูล" ในบทวิธีวิจัยเป็นสิ่งที่พิสูจน์ไม่ได้:

| # | สิ่งที่ผิด | แก้แล้ว |
|---|---|---|
| U27-1 | **การปิดรอบอยู่ในหน่วยความจำของเซิร์ฟเวอร์เท่านั้น** — ปิดรอบแล้วออกจากแอป เปิดใหม่ รอบที่ปิดไปแล้วกลับมาเปิดรับคำตอบอีก | ตาราง `wave` ในฐานข้อมูลของโปรเจกต์ · เปิดรอบเขียนแถวก่อนคำตอบแรกจะเข้ามาได้ · ปิดรอบ `UPDATE … WHERE closed_at IS NULL` จึงมีวันปิดวันเดียว กดซ้ำไม่เลื่อน |
| U27-2 | **หยุดเซิร์ฟเวอร์ = ปิดรอบเก็บข้อมูล** — ปิดแล็ปท็อปตอนกลางคืนแล้วรอบจบถาวร เปิดใหม่ก็ต่อรอบเดิมไม่ได้ ซึ่งจะทำให้ประชากรกลุ่มเดียวถูกแยกเป็นสองรอบในรายงาน | `stop()` หยุดฟังอย่างเดียว · `start()` **ต่อรอบที่ยังเปิดอยู่** ของ version นั้น และเปิดรอบใหม่ต่อเมื่อไม่มีรอบเปิดค้าง · หน้าจออ่านสถานะจากฐานข้อมูล ไม่ใช่จากที่ตัวเองจำไว้ |

**หน้า "คำตอบ" (§19.17)** — ทำงานเหมือน Sheet แต่ไม่ใช่ Sheet: แถวละผู้ตอบ คอลัมน์ตามลำดับข้อจริง · ช่องที่ถูกแก้มี**ไอคอน**กำกับ (ไม่ใช่แค่สี เพราะสีอย่างเดียว screen reader ไม่เห็น) · กดที่ช่องแล้วเห็นค่าเดิมที่ผู้ตอบส่งมา เหตุผล ชื่อผู้แก้ และเวลา · แก้ค่าต้องกรอกทั้งเหตุผลและชื่อ ไม่งั้นปุ่มกดไม่ได้ และ store ก็ปฏิเสธซ้ำอีกชั้น · ดูได้แม้เซิร์ฟเวอร์ปิดอยู่ เพราะเวลาที่คนอยากดูคำตอบที่สุดคือหลังปิดรอบแล้ว

**ค้างตอนนั้น ทำแล้วในรอบถัดมา**: materialize เข้า DuckDB — [§19.17](../ARCHITECTURE.md#1917-ฐานข้อมูลภายในของโปรเจกต์--sql-nosql-และช่องว่างจริงที่ต้องเติม) วาดไว้ว่าใช้ `ATTACH` แต่ P6.2/U19 บันทึกไว้แล้วว่า DuckDB โหลด `sqlite_scanner` ในแอปที่ sandbox ไม่ได้ถ้าไม่มีเน็ต ทางที่น่าจะถูกคืออ่านผ่าน `OLTP` แล้ว `INSERT` เข้า DuckDB จากฝั่งแอป (M16 ยังไม่แตะ DuckDB เหมือนเดิม) — และนั่นคือทางที่ใช้จริง ดูรอบ materialize ด้านล่าง
