## F-1 · Engine เป็นภาพนิ่งตอน boot — และไม่มีอะไรบอก 🔴 สูง

**นี่คือคำตอบตรง ๆ ของ "ทำไม Chat ไม่มี GX10 ให้เลือก"**

### สิ่งที่พบ

สวิตช์เลือกโมเดลต่อเทิร์น **มีอยู่จริง** และทำถูกตามกฎทั้ง 5 ข้อของ E.37:

```
Sources/CoAIWorkspaceApp/ChatView.swift:378   Picker("โมเดล", selection: $model.chosenModel)
Sources/CoAIWorkspaceApp/ChatViewModel.swift:324   offeredModels = await engine.router.offered
```

แต่รายการที่มันแสดง มาจาก `ModelRouter.offered` ซึ่งอ่านจาก:

```
Sources/LLMProviders/ModelRouter.swift:137   private let executors: [any LLMExecutor]   ← let
```

และ `executors` ถูกประกอบครั้งเดียวที่:

```
Sources/CoAIWorkspaceApp/Engine.swift:213-264
    let endpoints = config.effectiveEndpoints       ← อ่าน bootstrap.plist
    for endpoint in endpoints.endpoints { executors.append(VLLMExecutor(...)) }
    let router = ModelRouter(executors: executors, ...)
```

ส่วน `Engine.build` ถูกเรียกจากที่เดียวคือ `AppEnvironment.boot()` (`AppEnvironment.swift:57`) และหน้าจอตั้งค่า endpoint ทำได้แค่เขียนไฟล์:

```
Sources/CoAIWorkspaceApp/AppEnvironment.swift:218   func rememberEndpoints(...) { try BootstrapStore(paths:).save(updated) }
```

⇒ **เพิ่ม GX10 บนหน้าจอ → บันทึกลงไฟล์ → router ไม่รู้เรื่อง → Chat ไม่มีให้เลือก → จนกว่าจะปิด-เปิดแอป**

### ที่ทำให้แย่กว่าเดิม: หน้าจอเดียวกันมีสองพฤติกรรม

| ทำอะไรบนหน้า **ระบบ → งบ + endpoint** | มีผลเมื่อไร |
|---|---|
| แก้เพดานงบ (`setLimits`) | **ทันที** — `await governor?.setLimits(new)` เรียกเข้า object ที่มีชีวิตอยู่ |
| เพิ่ม/แก้/ลบ endpoint | **ต้องรีสตาร์ท** — เขียนไฟล์อย่างเดียว |

ผู้ใช้ไม่มีทางรู้ว่าปุ่มไหนอยู่กลุ่มไหน เพราะอยู่บนหน้าจอเดียวกัน หน้าตาเหมือนกัน และไม่มีข้อความไหนพูดถึงเรื่องนี้เลย (ตรวจแล้วทั้งไฟล์ `EndpointsView.swift`)

### ของอื่นที่ถูกแช่แข็งตอน boot ด้วยกัน

| ค่า | อ่านที่ | ผลถ้าเปลี่ยนแล้วไม่รีสตาร์ท |
|---|---|---|
| `endpointRegistry` | `Engine.swift:213` | endpoint ใหม่ไม่อยู่ในสาย · endpoint ที่ลบแล้วยังอยู่ |
| `localModel` | `Engine.swift:204` | Tier 0.5 ยังใช้โมเดลเดิม |
| `promptBudget` (จาก `max_model_len`) | `Engine.swift:441` | เปลี่ยน `--max-model-len` ที่ GX10 → แอปยังคิดงบด้วยเลขเก่า |
| `modelQuotaGigabytes` | `Engine.swift:210` | โควตาดิสก์เดิม |
| `surrealPort` | `Engine.swift:180` | ต่อพอร์ตเดิม |

> **หมายเหตุเรื่อง P15.3**: Done-when เขียนว่า *"เปลี่ยน `--max-model-len` ที่เซิร์ฟเวอร์แล้วแอปปรับตามโดยไม่ต้อง build ใหม่"* — โค้ดทำได้ตามนั้นจริง (ตรวจแล้ว `ContextManager.promptBudget(forWindow:)`) **แต่ "ไม่ต้อง build ใหม่" ไม่เท่ากับ "ไม่ต้องรีสตาร์ท"** ถ้อยคำของ Done-when ทำให้อ่านแล้วเข้าใจแรงกว่าที่เป็นจริง

### ทางแก้ที่เสนอ (เรียงตามความคุ้ม)

| # | ทางแก้ | ต้นทุน | ได้อะไร |
|---|---|---|---|
| **1** | **ให้ `ModelRouter` เปลี่ยนสายได้** — `executors` จาก `let` เป็น state ใน actor + `func replaceExecutors(_:)` แล้วให้ `rememberEndpoints` เรียกมันหลังบันทึก | เล็ก (~1 ไฟล์ + เทส) | ปิดปัญหาที่ต้นเหตุ · Chat เห็น GX10 ทันทีที่บันทึก |
| **2** | **`StaleConfigBanner`** — ค่าที่ต้องรีสตาร์ทถึงมีผล ขึ้นแถบบอกตรงนั้นพร้อมปุ่ม "เริ่มแอปใหม่" | เล็ก | ถ้าเลือกไม่ทำข้อ 1 อย่างน้อยผู้ใช้ไม่โดนหลอก |
| **3** | **กฎใน `check.sh`** — ค่าใน `BootstrapConfig` ทุกตัวที่ `Engine.build` อ่าน ต้องมีทางอัปเดตขณะรัน หรือมีชื่ออยู่ในรายการ "ยอมรับว่าต้องรีสตาร์ท" | เล็ก | กันไม่ให้ปัญหานี้กลับมาเงียบ ๆ |

**แนะนำ: ทำข้อ 1 + 3** ข้อ 2 เป็นทางเลือกสำรองถ้าข้อ 1 มีเหตุผลที่ทำไม่ได้

## F-2 · เขียวทั้งกระดาน โดยข้ามด่านที่สำคัญที่สุด 🔴 สูง

**นี่คือคำตอบของ "แจ้งแล้วบันทึกมี แต่ไม่ทำตาม"**

### สิ่งที่วัดวันนี้

```
$ ./scripts/check.sh

   ⊘ SKIPPED: no OpenAI-compatible endpoint at http://127.0.0.1:1234/v1 — Tier 1 unchecked

แล้วตรวจ endpoint จริงในนาทีเดียวกัน:

```

{"data":[{"id":"unsloth/Qwen3.8-27B-NVFP4", "max_model_len":32768, ...}]}   ✅ เปิดอยู่

### ทำไมนี่ถึงร้ายแรง

`Tests/LLMProvidersTests/ExecutorContractTests.swift:31` ตั้งค่าเริ่มต้นเป็น `http://127.0.0.1:1234/v1` โดยให้เหตุผลในคอมเมนต์ว่า *"LM Studio on the loopback by default, because that is what a laptop has"* — ซึ่งเคยจริง **แต่ทิศทางของโปรเจกต์เปลี่ยนไปแล้วตั้งแต่ 2026-08-15**: P15 ถูกยกขึ้นหัวคิวด้วยเหตุผลว่า GX10 คือสมองหลัก

⇒ **ด่านที่ตรวจสมองหลักของระบบ ไม่เคยถูกรันในรอบตรวจปกติเลยสักครั้ง** และเพราะ skip อ่านออกมาเหมือน pass ทุกรอบที่ผ่านมาจึงรายงานว่า "เขียวทั้งหมด"

นี่คือรูปแบบเดียวกับ **D6** ที่โปรเจกต์นี้เจอมาแล้ว 8 ครั้ง (ความสามารถมีอยู่ · ไม่มีอะไรเรียกใช้) เพียงแต่ครั้งนี้เกิดกับ *การทดสอบ* แทนที่จะเกิดกับ *ฟีเจอร์*

### และมีหลักฐานที่ชัดกว่านั้นอีก — เครื่องมือที่ทำไว้แล้ว ไม่เคยถูกเรียก

`scripts/gx10-check.sh` **มีอยู่แล้ว** และถูกเขียนมาเพื่อเรื่องนี้โดยเฉพาะ — คอมเมนต์หัวไฟล์บอกเองว่าสร้างเพราะ *"'เซิร์ฟเวอร์เปิดอยู่' เคยไม่ได้แปลว่า 'แอปจะทำงานได้' มาแล้วสองครั้ง"* และมันตรวจ**ผลที่ parse แล้ว ไม่ใช่ status code**

รันวันนี้:

```
$ ./scripts/gx10-check.sh
── endpoint ──          ✓ serving unsloth/Qwen3.8-27B-NVFP4 · max_model_len 32768
── tool calling ──      ✓ tool_calls parsed · arguments เป็น JSON ที่ถูกต้อง
── reasoning split ──   ✓ content มีแต่คำตอบ '4' · ความคิด 232 ตัวอักษรแยกอยู่
── structured output ── ✓ decode ได้ 1 assignment: ['researcher']
── throughput ──        ✓ 362 tokens / 32s ≈ 11 tok/s (สายเดียว)
── metrics ──           ✓ /metrics เปิด num_requests_running

ENDPOINT READY
```

**ผ่านทุกด่าน** แล้ว `check.sh` เรียกมันไหม?

```
$ grep -n "gx10" scripts/check.sh
872:# `gx10-serve.sh` runs on another machine and nothing here ever executes it, ...
```

**ไม่เลย** — ปรากฏครั้งเดียวในคอมเมนต์ ของกฎที่ตรวจว่าสคริปต์ทุกตัว *parse ผ่าน* เท่านั้น

⇒ โปรเจกต์นี้มีเครื่องมือพิสูจน์ Tier 1 ที่ทำงานได้สมบูรณ์ · เขียนไว้อย่างดี · และ**ไม่เคยถูกรันในรอบตรวจปกติ** นี่คือ D6 ครั้งที่ 9 และเป็นครั้งที่เจ็บที่สุด เพราะมันปิดบังของที่คุณสนใจที่สุดพอดี

## F-3 · RAM คือตัวแปรที่ซ่อนอยู่เบื้องหลัง "ตอนแรกได้ ตอนหลังไม่ได้" 🟠 กลาง

### หลักฐานจากรอบวันนี้

```
── local chat model (Tier 0.5) ──
⊘ ข้ามเช็คพื้นรับประกัน — Qwen3.5-9B-MLX-4bit ต้องการราว 7.1 GB แต่ว่างอยู่ 3.1 GB
   — ตั้งเป็นตัวหลักไม่ได้ เพราะจะทำให้เครื่องค้าง ไม่ใช่แค่ตอบช้า
```

**P5.4 คือข้อที่รับประกันว่า "ปิด endpoint แล้วแอปยังตอบได้"** และในรอบที่ขึ้น `ALL CHECKS PASSED` นี้ ข้อนั้น**ไม่ได้ถูกตรวจ**

### สามอย่างที่บวกกันแล้วอธิบายอาการ "วนไปวนมา" ได้ทั้งหมด

| ตัวแปร | อาการที่เห็น |
|---|---|
| **RAM ว่างไม่เท่ากันทุกรอบ** (16 GB) | โมเดลโหลดได้บ้างไม่ได้บ้าง โดยโค้ดไม่ได้เปลี่ยนเลย |
| **U17 — sidecar `surreal` ค้างเมื่อโดน SIGTERM** (ตัวละ ~200 MB, เคยค้าง 11 ตัว) | รันครั้งที่ 3 มี RAM น้อยกว่าครั้งที่ 1 ทั้งที่ทำเหมือนกัน |
| **F-1 — สถานะแช่แข็งตอน boot** | ตั้งค่าถูกแล้วแต่ยังไม่มีผล จนกว่าจะรีสตาร์ท ⇒ "เมื่อกี้ได้ ทำไมตอนนี้ไม่ได้" |

**ทั้งสามข้อไม่ใช่โค้ดที่พังสลับไปมา — แต่เป็นสภาพแวดล้อมที่ไม่ถูกวัดและไม่ถูกรายงาน**

### ทางแก้

1. **`check.sh` พิมพ์ RAM ว่าง ก่อนและหลังรอบ** และเทียบกับที่โมเดลต้องการ — ตัวเลขนี้เป็นเงื่อนไขของผลลัพธ์ ไม่ใช่ของแถม
2. **ปิด U17** — ให้ sidecar ตายตามพ่อ (watchdog หรือให้ลูกเช็ค parent pid — `PR_SET_PDEATHSIG` ไม่มีบน macOS)
3. **ก่อนทุกรอบทดสอบ: `pkill -f 'vendor/helpers/surreal'`** — เข้าไปอยู่ใน [`TEST_PROTOCOL.md`](TEST_PROTOCOL.md) §1 แล้ว

## F-8 · กฎ design token มีรูโหว่ 🟡 ต่ำ-กลาง

`check.sh` พิมพ์ว่า *"every view outside the legacy list uses the design tokens"* แต่กฎจับแค่:

```bash
grep -qE "\.padding\([0-9]|cornerRadius: [0-9]|Color\(red:"
```

**ไม่จับ `.padding(.horizontal, N)` / `.padding(.vertical, N)`** ⇒ วัดจริงในไฟล์ view:

| รูปแบบ | จำนวน |
|---|---|
| `.padding(N)` ดิบ | 0 ✅ |
| `.padding(.ทิศทาง, N)` ดิบ | **~114 จุด ใน 27 ไฟล์** |
| ค่าที่ใช้จริง | 1, 2, 3, 4, 5, 6, 7, 8, 10, 12, 16 — **11 ค่า** ทั้งที่ token มี 4 |

**ทางแก้**: เพิ่ม `\.padding\(\.[a-z]+, *[0-9]` เข้าไปในกฎ แล้วไล่แปลง — คาดว่าใช้เวลาไม่นานเพราะส่วนใหญ่แมปเข้า 4 ค่าเดิมได้ตรง ๆ
