## E.31 DB connector กับเซิร์ฟเวอร์จริง (2026-08-16)

แผนเขียนไว้ตั้งแต่ P6.2 ว่า PostgreSQL กับ MySQL "ใช้เส้นทางเดียวกันเป๊ะ" และ**ไม่มีใครยืนยันกับเซิร์ฟเวอร์จริง เพราะไม่มีเซิร์ฟเวอร์** · รอบนี้ยกคอนเทนเนอร์ชั่วคราวขึ้นมาสองตัวบนเครื่องนี้แล้วยิงจริงด้วย [`Sources/ConnectorCheck`](../../Sources/ConnectorCheck/main.swift)

| สิ่งที่ยิง | ผล |
|---|---|
| PostgreSQL 16 — `ATTACH` + อ่าน `information_schema` + `SELECT` | ✅ ต่อได้ · เห็นตาราง · คืนค่าครบ |
| **ชื่อตารางและคอลัมน์ภาษาไทย** (`ผู้ป่วย`, `ชื่อ`, `คะแนน`) | ✅ อ่านผ่าน DuckDB ได้ตรง ไม่ต้องแปลง |
| MySQL 8 — เส้นทางเดียวกัน | ✅ ต่อได้ · `SELECT label, value FROM my.readings` คืน 2 แถวถูกต้อง |
| ชนิดข้อมูลที่ DuckDB รายงานกลับ | `varchar` / `double` ทั้งสองฝั่ง — ไม่มีคอลัมน์ไหนกลายเป็น NULL ทั้งคอลัมน์ (กับดักที่ E.x ของ P6.1 บันทึกไว้) |
| **รหัสผ่านผิด** | ✅ ล้มเหลวพร้อมข้อความอ่านรู้เรื่อง และ**รหัสผ่านถูกปิดเป็น `••••`** — DuckDB คืนคำสั่งที่ล้มเหลวกลับมาทั้งประโยค ซึ่งคือ connection string ที่มีรหัสผ่านอยู่ในนั้น |

**สรุป**: ข้อความในแผนที่ว่า "สองเส้นทางเหมือนกัน" เป็นจริงตามที่เขียน — ทั้งสองใช้ `ATTACH` แบบ key/value เดียวกัน ต่างกันแค่ชื่อ extension · และการปิดรหัสผ่านทำงานบนเส้นทางที่มันสำคัญที่สุด คือตอนล้มเหลว

**เก็บกวาดแล้ว**: คอนเทนเนอร์ทั้งสองถูกลบ (`--rm`) และ Docker ถูกปิดหลังวัดเสร็จ — ไม่มีอะไรค้างบนเครื่อง

## E.32 ขับแอปจริงแล้วเจอสองบั๊กที่เทสทั้งชุดมองไม่เห็น (2026-08-16)

ตั้งใจจะปิดของค้างของ **P15.1** (ถามผ่านหน้าแชทจริงให้ GX10 ตอบ) แต่การขับหยุดที่บั๊กสองตัวก่อน — **ทั้งคู่เป็นชนิดที่ชุดเทสสีเขียวทั้งชุดมองไม่เห็นโดยหลักการ ไม่ใช่เพราะเขียนเทสน้อย**

### 1. ฟิลด์ที่เพิ่มทีหลัง ทำให้แถวเก่าบันทึกอะไรไม่ได้อีกเลย

พิมพ์คำถามลงหน้าแชทแล้วกด "ส่ง" — ข้อความไม่ถูกบันทึก และบนจอขึ้นว่า

```
บันทึกข้อความไม่สำเร็จ: server(1): stmt 1 ERR: Couldn't coerce value for field
`pinned` of `conversation:ijab6unitfg3diz09izt`: Expected `bool` but found `NONE`
```

`DEFINE FIELD … TYPE bool DEFAULT false` **อ่านเหมือนครอบคลุมแถวที่มีอยู่แล้ว แต่ไม่ใช่**: `DEFAULT` เติมค่าตอน*สร้าง*แถว และแถวเก่าถูกสร้างไปแล้ว ⇒ ฟิลด์เป็น `NONE` และการตรวจชนิดจะไปเกิดตอน**อัปเดตแถวนั้นครั้งถัดไป** — อัปเดตอะไรก็ได้ ไม่ใช่เฉพาะที่แตะ `pinned` (การ `append` ข้อความแตะแค่ `updated_at`)

| ทำไมเทสจับไม่ได้ | |
|---|---|
| ฐานข้อมูลของเทสเกิดใหม่ทุกครั้ง | ทุกแถวถูกสร้าง*หลัง*ฟิลด์มีอยู่แล้ว จึงไม่มีแถวเก่าให้พัง |
| CI ก็เหมือนกัน | ความล้มเหลวนี้ต้องการ "เครื่องที่ใช้แอปมาก่อนหน้านี้" ซึ่งเป็นสิ่งเดียวที่ CI ไม่มี |

**เทสที่เขียน** จำลองแถวเก่าตามลำดับที่มันเกิดจริง — ถอดฟิลด์ออก สร้างแถว แล้วนิยามฟิลด์กลับ — แล้วยืนยันว่าแดงด้วยข้อความเดียวกันเป๊ะกับที่ผู้ใช้เห็น

**สิ่งที่แก้**: `bootstrap` เติมค่าย้อนหลังหลังนิยามฟิลด์เสร็จ และ **คำสั่งเติมถูก*สร้างจากรายการนิยามฟิลด์เอง* ไม่ได้เขียนมือ** — รายการที่เขียนมือคือรายการที่ล้าสมัยครั้งแรกที่มีคนเพิ่มฟิลด์แล้วไม่ได้นึกถึงไฟล์นี้อีกครึ่งหนึ่ง ซึ่งคือความผิดพลาดที่กำลังแก้อยู่พอดี · ฟิลด์ `option<…>` ถูกข้าม เพราะการไม่มีค่าคือความหมายของมัน · รันทุกครั้งที่เปิดแอป ไม่ผูกกับเลขเวอร์ชัน: การซ่อมที่ทำงานต่อเมื่อมีคนจำได้ว่าต้องบวกเลข คือการซ่อมที่จะถูกข้ามพอดีในครั้งที่สำคัญ

### 2. บูตค้างตลอดกาล เพราะถาม Keychain ว่า "โทเคนคืออะไร" แทนที่จะถามว่า "มีโทเคนไหม"

หลัง build ใหม่ แอปค้างที่ "กำลังเริ่มระบบ…" **ที่ CPU 0% ไม่มีกำหนด** · `sample` ตอบทันทีว่าค้างตรงไหน:

```
Engine.build → ChannelAccount.isReady → .token → SecretStore.value
  → KeychainVault.read → SecItemCopyMatching     (main thread, 1716/1716 samples)
```

`SecItemCopyMatching` ที่ขอ `kSecReturnData` คือการขอ**ตัวข้อมูล** และการคืนตัวข้อมูลคือสิ่งที่ ACL ของ item นั้นคุ้มครองอยู่ · แอปที่เพิ่ง build ใหม่คือไบนารีคนละตัวสำหรับ ACL นั้น ⇒ macOS ขึ้นกล่องขออนุญาต และ**เรียกไม่คืนจนกว่าจะมีคนตอบ** — บนเมนเธรด ทั้งแอปจึงรอ พร้อมตัวหมุนที่บอกไม่ได้ว่ารออะไร (ยืนยันด้วยภาพหน้าจอ: กล่อง *"Co-AI Workspace wants to use your confidential information stored in 'com.coaiworkspace.app.secrets'"*)

**คอมเมนต์สองบรรทัดเหนือจุดนั้นรู้กฎอยู่แล้ว** — *"a channel that cannot run must not stop the app from starting"* — แต่แพ้ที่**วิธีถาม ไม่ใช่สิ่งที่ตัดสิน**: `isReady` ต้องรู้แค่ว่า*มี*โทเคนไหม แล้วไปอ่าน*ค่า*เพื่อหาคำตอบ

**สิ่งที่แก้**: `SecretVault` มี `exists(_:)` แยกจาก `read(_:)` และฝั่ง Keychain ถาม**แอตทริบิวต์ ไม่ใช่ข้อมูล** ซึ่งไม่ติด ACL จึงขึ้นกล่องไม่ได้และค้างไม่ได้ · `status`/`has` เดินทางนี้ทั้งหมด ส่วน `value` ยังอ่านของจริงเหมือนเดิม — **ย้ายที่ ไม่ใช่เอาออก** และย้ายไปอยู่กับ channel ที่กำลังจะส่งจริง ซึ่งไม่ใช่เมนเธรดและไม่ใช่ตอนบูต

**วัดหลังแก้**: `sample` ชี้ว่าเมนเธรดอยู่ใน run loop ปกติ (1736/1736) ไม่ได้อยู่ใน `SecItemCopyMatching` อีก — ซึ่งคือความต่างที่วัดได้ตรง ๆ ระหว่างก่อนกับหลัง

### ที่ยังปิดไม่ได้ และเพราะอะไร

กล่อง Keychain ที่ค้างอยู่บนจอ **ขอรหัสผ่าน login keychain ของเจ้าของเครื่อง** ⇒ เป็นสิ่งที่ระบบนี้กรอกแทนไม่ได้และไม่ควรกรอก · ตราบใดที่ยังไม่มีคนตอบกล่องนี้ หน้าต่างแอปไม่ขึ้น จึงยังขับต่อไม่ได้ ⇒ **P15.1 ข้อ "ถามผ่านหน้าแชทจริง" ยังค้าง** และค้างที่คน ไม่ใช่ค้างที่โค้ด

## E.33 ตัวขับหน้าจอบนของจริง — และการ "พิมพ์สำเร็จ" ที่แอปไม่รู้เรื่องด้วย (2026-08-16)

ปิด **P17.1** และ **P17.2** ด้วยการขับบนแอปจริง (สิทธิ์ Accessibility ที่เจ้าของเครื่องให้ไว้แล้ว)

### P17.1 — กดปุ่มจากชื่อที่ screen reader อ่าน

| สิ่งที่ทำ | ผลจริง |
|---|---|
| กด "ส่งข้อความ" | `กด ส่งข้อความ \| ขึ้นใหม่: …` — ระบุด้วยว่าหน้าจอเปลี่ยนอะไรบ้าง |
| กด "โมเดล" ตอนมีห้าอันชื่อคล้ายกัน | **ปฏิเสธ**: "เจอที่มีคำว่า 'โมเดล' 5 อัน — ต้องระบุให้เจาะจงกว่านี้ ก่อนจะกดอันไหนก็ได้แล้วหวังว่าถูก" |
| กดชื่อที่ไม่มีบนจอ | บอกว่าหาอะไรไม่เจอ **และแสดงรายการที่เห็นจริง** ไม่ใช่คลิกที่ว่าง |

ข้อกลางคือข้อที่มีค่าที่สุด: กฎ "เจอสองอันขึ้นไป = error" เคยพิสูจน์ได้แค่ในเทส รอบนี้**ยิงใส่หน้าจอจริงแล้วมันยิงกลับ**

### P17.2 — พิมพ์ไทยลงช่องค้นหาแล้วผลค้นต้องเปลี่ยน (และรอบแรกมันไม่เปลี่ยน)

พิมพ์คำไทยลงช่อง "ค้นข้อความในบทสนทนาเก่า" — **ตัวอักษรขึ้นบนช่องครบ แต่รายการผลลัพธ์ไม่ขยับเลย ไม่ว่าจะพิมพ์คำไหน** รวมถึงคำที่อยู่ในข้อความที่เก็บไว้แบบเห็น ๆ ทุกคำได้ป้ายเดียวกันคือ *"— ตรงกับเรื่องที่คุยกัน ไม่ใช่คำที่พิมพ์ —"* ซึ่งเป็นป้ายของผลที่มาจาก**เวกเตอร์**เท่านั้น

ไล่ที่มาทีละชั้นแทนการเดา:

| ชั้น | วัดได้ว่า |
|---|---|
| ข้อความในฐานข้อมูลจริง | มีคำนั้นอยู่จริง 3 แถว |
| `BM25Index` บนคลังจริงทั้ง 42 ข้อความ (ดึงออกมารันนอกแอป) | **เจอ 3 hits คะแนน 4.168** · และ "หมดไฟ" ที่ไม่มีจริง = **0 hits** ⇒ ตัวค้นถูกต้อง |
| `ConversationStore.search` กับคลังรูปทรงเดียวกัน (เทสใหม่ 2 ข้อ) | ✅ ผ่าน — ยกประโยคที่ตรงมาให้ |

⇒ สิ่งที่ไม่เกิดขึ้นคือ **การค้นเอง** · `AXUIElementSetAttributeValue(kAXValue)` บน `TextField` ของ SwiftUI **คืน `.success`** แต่ไม่ได้เดินผ่าน responder chain ⇒ binding ไม่เปลี่ยน ⇒ วิวที่รันใหม่ด้วย `.task(id: query)` ไม่มีอะไรให้รันใหม่

**บทเรียนที่เป็นกฎ**: **การเขียนค่าที่ตัวควบคุมยอมรับ ไม่เท่ากับการเขียนที่แอปรับรู้** — และตัวขับ*แยกสองอย่างนี้จากภายนอกไม่ได้* เพราะค่าขึ้นบนจอเหมือนกันทั้งคู่ · เดิมโค้ดเลือก `AXValue` ก่อนด้วยเหตุผลว่า "เร็วกว่าและรบกวนน้อยกว่า" ซึ่งเป็นเหตุผลที่จริงและ**ตอบผิดคำถาม** ⇒ สลับลำดับ: **คีย์บอร์ดคือทางหลัก เขียนค่าคือทางสำรอง**สำหรับช่องที่รับโฟกัสไม่ได้ และเมื่อใช้ทางสำรอง หลักฐานจะเขียนออกมาตรง ๆ ว่า "แอปอาจไม่รู้ว่าค่าเปลี่ยน" · ราคาคือหนึ่งคีย์ต่อหนึ่งตัวอักษร ซึ่งเป็นราคาที่ถูกกว่าตัวขับที่รายงานว่าสำเร็จทั้งที่แอปข้างใต้ไม่ได้ทำอะไร — ความล้มเหลวชนิดเดียวกับการคลิกที่พิกัด

**วัดใหม่หลังแก้** — ผลเปลี่ยนตามคำที่พิมพ์จริง และแยกได้สี่แบบตามที่ออกแบบไว้:

| พิมพ์ | ได้ |
|---|---|
| `ผ่าตัด` (อยู่กลางประโยคไม่มีช่องว่างล้อม) | **ยกประโยคนั้นมา** — ตรงด้วยคำ |
| `นาที` (ท้ายประโยค) | ยกประโยคนั้นมา |
| `หมดไฟ` (ไม่มีในข้อความ แต่เรื่องใกล้กัน) | *"— ตรงกับเรื่องที่คุยกัน ไม่ใช่คำที่พิมพ์ —"* — ตรงด้วยเวกเตอร์ และ**บอกว่าตัวเองเป็นแบบไหน** |
| `เบาหวาน` (ไม่มีและไม่ใกล้) | **ไม่มีผลลัพธ์เลย** |

แถวที่สามคือเหตุผลที่ป้ายนั้นมีอยู่: ผลที่มาจากเวกเตอร์ล้วนที่แสดงบรรทัดแรกของบทสนทนาเป็น "ผลการค้น" คือการทำให้คนอ่านเชื่อว่าเจอคำที่พิมพ์

## E.34 แท็บจำที่ของตัวเองไหม — และการวัดที่กลืนคำปฏิเสธของตัวเองทิ้ง (2026-08-16)

ปิด **P21.1** ด้วยการขับจริง และรอบนี้**สิ่งที่ผิดคือการวัด ไม่ใช่แอป** ซึ่งเป็นบทเรียนที่ใหญ่กว่าตัว task

### สิ่งที่วัดได้ในที่สุด

เปิดสามแท็บ ตั้งคนละพื้นที่ แล้วไล่กลับ:

| ขั้น | ตั้ง | อ่านกลับ |
|---|---|---|
| 1 | tab1 = โต๊ะทำงาน | โต๊ะทำงาน |
| 2 | General = คลังความรู้ | คลังความรู้ |
| 3 | tab2 = ระบบ | ระบบ |
| 4 | กลับ tab1 | **โต๊ะทำงาน** |
| 5 | กลับ General | **คลังความรู้** |
| 6 | กลับ tab2 | **ระบบ** |

⇒ Done-when ของ P21.1 ("แต่ละอันจำสถานะของตัวเอง · ไม่มีข้อมูลของอีกโปรเจกต์รั่วมา") **ผ่านบนหน้าจอจริง**

### ทางที่ไปผิด และทำไมมันดูน่าเชื่อ

รอบแรกวัดได้ว่า **ทั้งสามแท็บอ่านกลับเป็น "ระบบ" หมด** ซึ่งอ่านเหมือนบั๊กรั่วข้ามแท็บที่ชัดเจนมาก · ที่จริงคือ**ไม่มีการสลับแท็บเกิดขึ้นเลยสักครั้ง**: คำสั่งกดแท็บถูก**ปฏิเสธ**เพราะชื่อกำกวม —

```
"แท็บ Burnout among ICU nurses · กดเพื่อสลับมา"
"ปิดแท็บ Burnout among ICU nurses — ปิดแค่หน้าต่าง ไม่ใช่ปิดโครงการ"
```

คำว่า `ปิดแท็บ` **ลงท้ายด้วย** `แท็บ` ⇒ ถามหา "แท็บ X" แล้วเจอสองอัน ⇒ ตัวขับปฏิเสธตามกฎของมันเอง (ซึ่งถูกต้อง) · **แต่สคริปต์ที่ใช้วัดเขียนว่า `>/dev/null`** ⇒ คำปฏิเสธห้าครั้งอ่านออกมาเป็นการสลับแท็บสำเร็จห้าครั้ง และสิ่งที่เกิดขึ้นจริงคือการเปลี่ยนพื้นที่ของแท็บ General ห้ารอบ

**บทเรียน**: *ตัวขับที่ปฏิเสธอย่างถูกต้อง ไม่มีค่าเลยถ้าผู้เรียกทิ้งคำปฏิเสธ* — และความเสียหายไม่ใช่แค่เสียเวลา แต่คือ**เกือบยื่นบั๊กใส่แอปในเรื่องที่แอปไม่เคยถูกสั่งให้ทำ** · เทียบเคียงตรง ๆ กับ E.33: ที่นั่นตัวขับรายงานสำเร็จทั้งที่แอปไม่รู้เรื่อง ที่นี่ตัวขับรายงานล้มเหลวแต่ผู้เรียกไม่ฟัง — ความล้มเหลวเงียบสองด้านของสิ่งเดียวกัน

**ตรวจสมมติฐานย้อนหลังแล้ว**: build โค้ดเดิม (ก่อนแก้) พร้อม trace แล้ววัดด้วยวิธีที่กดติดจริง — **โค้ดเดิมก็ผ่านทั้งหกขั้น** ⇒ ที่แก้ไปจึงเป็น **การรัดกุมขึ้น ไม่ใช่การแก้บั๊กที่วัดได้** และบันทึกไว้ตรงนี้อย่างนั้น

### สิ่งที่แก้จริงในรอบนี้

1. **`TabAreaMemory` (ProjectKit, 5 เทส)** — เดิมเป็น `onChange` สองตัวบน state สองก้อน และ**ทั้งคู่ทิ้งค่า `previous` ที่ SwiftUI ส่งให้** แล้วไปอ่าน `active` เพื่อเอา id มาเก็บ ซึ่งระหว่างการสลับมันขยับไปแล้ว ⇒ แท็บที่กำลัง*ออก*ถูกเก็บใต้ชื่อแท็บที่กำลัง*เข้า* · และเพราะการกู้คืนเขียนลง `area` ตัวเดียวกับที่ตัวบันทึกเฝ้าอยู่ **การกู้คืนจึงแยกไม่ออกจากการที่คนเลือกเอง** ⇒ เหลือ observer เดียวที่รับทั้งสองปลายของการสลับมาพร้อมกัน (`leaving` / `showing` / `arriving`) ไม่มีอะไรต้องเดาจาก state ที่กำลังเคลื่อน · เทสที่ทำให้แดงก่อนคือการถอดความพฤติกรรมเดิมตรง ๆ (เก็บใต้ id ปลายทาง)
2. **"ตรงที่ต้นชื่อ ชนะตรงที่กลางชื่อ" ใน `ElementFinder` (4 เทส)** — ตัวควบคุมที่ชื่อ*ขึ้นต้น*ด้วยสิ่งที่ถาม คือตัวที่ถูกเรียกชื่อ ส่วนตัวที่แค่*เอ่ยถึง*คืออีกตัวที่พูดถึงเรื่องเดียวกัน · **เป็นการหุบวงเท่านั้น**: ถ้าไม่มีอันไหนขึ้นต้นตรง ก็ใช้ชุดเดิม และเสมอจริง (ปุ่ม "บันทึก" สามอัน) ยัง**ปฏิเสธเหมือนเดิม** เพราะกฎห้ามเดายังเป็นเหตุผลของฟังก์ชันนี้ทั้งฟังก์ชัน
3. **`AXNavigator.locate` มีตรรกะการจับคู่ของตัวเอง** และไม่ได้รับกฎข้อ 2 ไปด้วย ⇒ แก้แล้วทั้งสองทางใช้ helper เดียวกัน — **การมีสองอิมพลีเมนต์ของ "ชื่อนี้หมายถึงตัวไหน" คือวิธีที่อันหนึ่งได้กฎที่อีกอันไม่มี** ซึ่งคือสิ่งที่เพิ่งเกิดขึ้นจริง

## E.35 ตาข่ายกันถอยหลังสำหรับสิ่งที่ตัดสินใจก่อนถามโมเดล (P9.1, 2026-08-16)

P9.1 ค้างมาตลอดด้วยเหตุผลว่า "ต้องมีงานจริงที่สำเร็จแล้วพอเป็นชุด regression ก่อน" ซึ่ง**จริงสำหรับรูปที่คิดไว้ตอนแรก** (เล่นซ้ำการรันของ agent ทั้งรอบ) และรูปนั้นไปต่อไม่ได้: การเล่นซ้ำต้องมีโมเดล และโมเดลคือสิ่งเดียวที่ `check.sh` บนแล็ปท็อปไม่มี

**สิ่งที่ควรตรึงไม่ต้องใช้โมเดลเลย** — ก่อนจะถาม LLM สักคำ ระบบตัดสินไปแล้วว่า **tier ไหนจะตอบและเพราะอะไร**, **ทูลที่กำลังจะเรียกอันตรายแค่ไหนและเพราะอะไร** ทั้งสองเป็นฟังก์ชันบริสุทธิ์ของคำขอ และเป็นจุดที่การถอยหลังแบบเงียบแพงที่สุด: ไม่มีอะไรพัง ไม่มีอะไร fail — คำตอบแค่เริ่มมาจากโมเดลที่เล็กลง หรือคำสั่งเชลล์เลิกถามก่อนรัน และสัญญาณแรกไปโผล่ในผลงานของใครบางคนอีกหลายสัปดาห์ถัดมา

**รูปแบบ**: ชุดงานคงที่ + ไฟล์บันทึกการตัดสินใจวางไว้ข้าง ๆ เทส · **ไฟล์คือสาระ** — `#expect` บอกว่า "อันนี้ควรเป็นความเสี่ยงสูง" ส่วนไฟล์บอกว่า**ภาพรวมของการตัดสินใจทั้งชุดวันนี้หน้าตาแบบไหน** และ diff ของมันอ่านรู้เรื่องสำหรับคนที่ไม่ได้อยู่ตอนเขียน · การเปลี่ยนพฤติกรรมยังทำได้ แต่ต้องแก้ไฟล์ที่ commit ไว้ในคอมมิตเดียวกับที่เปลี่ยนพฤติกรรม ซึ่งเป็นสิ่งเดียวที่ตาข่ายนี้พยายามบังคับ

**พิสูจน์ว่าจับได้จริง** — ปิดกฎ "งานที่ผิดแล้วเสียหายไม่ใช้ on-device" (E.7) ชั่วคราวแล้วรัน:

```
การตัดสินใจเปลี่ยนไปจากที่บันทึกไว้ใน routing.golden — บรรทัดที่ 26
    เดิม: ลำดับที่พิจารณา: gx10 → mlx-qwen
    ใหม่: ลำดับที่พิจารณา: gx10 → mlx-qwen → apple-fm
```

⇒ จับได้ตรงจุด และ**บอกบรรทัดที่ต่าง ไม่ใช่พ่นเอกสารสองชุดมาเทียบเอง** เพราะ diff 60 บรรทัดในผลเทสคือกำแพงที่ไม่มีใครอ่าน

**ที่ยังไม่ครอบคลุม**: การเล่นซ้ำแผนของ agent จริง ๆ ยังต้องมี endpoint และยังทำไม่ได้ใน `check.sh` — ตรงนี้บันทึกไว้ว่ายังเป็นช่องว่าง ไม่ใช่ปิดไปเงียบ ๆ

## E.36 พยายามให้ GX10 ตอบผ่านหน้าแชทจริง — และกำแพงที่เจอคือ *ไม่มีสวิตช์* (2026-08-16)

ของค้างข้อสุดท้ายของ **P15.1** คือ "ปิด Foundation Models แล้วถามผ่านหน้าแชท และถอดสาย LAN จริงกลางสตรีม" · รอบนี้เตรียมทุกอย่างที่เตรียมได้แล้วลงมือขับ:

| เตรียม | ผล |
|---|---|
| พร็อกซี TCP บน `127.0.0.1:18010` → GX10 (เพื่อ**ตัดสายได้จริงโดยไม่ต้องแตะการตั้งค่าระบบ**) | ✅ ต่อผ่านได้ `/v1/models` ตอบปกติ |
| ชี้ endpoint GX10 ไปที่พร็อกซี แล้วเปิดแอปใหม่ | ✅ หน้าสถานะขึ้น **"GX10 — พร้อมใช้"** ผ่านพร็อกซี |
| ถามผ่านหน้าแชทจริง (พิมพ์ด้วยตัวขับ กด "ส่งข้อความ") | ✅ ส่งได้ · บันทึกได้ (การแก้ `pinned` ใน E.32 ยืนยันบนของจริงอีกครั้ง) |
| **ให้ GX10 เป็นตัวที่ตอบ** | ❌ **ทำไม่ได้จากหน้าจอ** |

**ทำไมถึงทำไม่ได้ และทำไมมันสำคัญกว่าที่คิด**

ลำดับของ §9.2 ทำงานถูกต้องตามที่เขียนไว้: เทิร์นในหน้าแชทเป็น `.disposable` (มีคนนั่งรอ) จึงเรียงจาก tier ที่ใกล้ที่สุดขึ้นไป และเพราะเทิร์นมีทูลติดไปด้วย **Tier 0 ถูกตัดออกเองอัตโนมัติ** (Foundation Models เรียกทูลไม่ได้) ⇒ ผู้ชนะคือ **Tier 0.5 โมเดล 4B บนเครื่อง** ทุกครั้ง ซึ่ง*ถูกต้องเรื่องค่าใช้จ่าย*

แต่เมื่อไล่หาวิธีบอกระบบว่า "คำถามนี้ขอตัวใหญ่หน่อย" **ไม่มีเลยสักทาง**:

- หน้าโมเดลมีแค่ **"ใช้ตัวนี้"** กับ **"ลบ"** — *ไม่มีปุ่มเลิกใช้* Tier 0.5
- ไม่มีตัวเลือก "ตอบด้วย endpoint นี้" ที่หน้าแชท
- `RoutingPolicy` ตัดสินจากชนิดของงาน ไม่ใช่จากที่คนขอ

⇒ **ข้อค้างของ P15.1 ไม่ใช่ "ยังไม่ได้ทดสอบ" แต่คือ "ยังไม่มีของให้ทดสอบ"** — สิ่งที่ขาดคือ*ตัวควบคุม* ไม่ใช่*การวัด* · และมันคือสิ่งที่คนอยากได้พอดีในนาทีที่โมเดลเล็กตอบไม่ดี ซึ่งเป็นนาทีที่เกิดขึ้นจริงบ่อยที่สุด

**สิ่งที่เจอระหว่างทางด้วย**: บทสนทนายาว (42 ข้อความ) ทำให้เทิร์นเข้าสู่ **"ย่อบทสนทนาให้พอดีหน้าต่างบริบท"** และการย่อนั้นวิ่งบน Tier 0.5 — บนเครื่องนี้มันช้าพอที่**หน้าจอดูเหมือนค้าง**ทั้งที่กำลังทำงาน · แถบสถานะบอกว่ากำลังย่ออยู่ ซึ่งถูกแล้ว แต่ไม่มีตัวเลขว่าเหลืออีกเท่าไร

**เก็บกวาดแล้ว**: พร็อกซีปิด · `baseURL` ของ GX10 กลับไปที่ `192.168.1.205:8000` · โฟลเดอร์โมเดลที่ย้ายออกไปชั่วคราวถูกย้ายกลับ · `defaultEndpointID` ตั้งกลับเป็น `migrated-self-hosted` ตามเดิม — **ไม่เปลี่ยนค่าที่เจ้าของเครื่องตั้งไว้โดยไม่ได้ขอ** แม้ปลายทางนั้นจะต่อไม่ได้ในตอนนี้ (การเปลี่ยน default ให้เป็น GX10 เป็นการตัดสินใจของเจ้าของ ไม่ใช่ผลพลอยได้จากการทดสอบ)

## E.37 สร้างสวิตช์ที่ E.36 บอกว่าไม่มี แล้ว GX10 ก็ตอบผ่านหน้าแชทจริง (2026-08-16)

E.36 จบด้วยข้อสรุปว่าของค้างของ P15.1 **ไม่ใช่การทดสอบ แต่คือของที่ยังไม่มี** — รอบนี้จึงสร้างมัน

**กติกาที่ทำให้ตัวเลือกนี้ไม่กลายเป็นช่องโหว่** (5 เทส) — *ตัวเลือกคือ **ลำดับ** ไม่ใช่ **ตัวกรอง***:

| กฎ | เหตุผล |
|---|---|
| เลื่อนขึ้นหน้าแถว **ไม่ตัดตัวอื่นทิ้ง** | endpoint ที่เลือกไว้ล่มกลางคำถาม = ตอบช้าลง ไม่ใช่ตอบไม่ได้ · ตัวกรองจะทำให้สายหลุดเส้นเดียวกลายเป็นแอปตาย |
| **เลือกแล้วไม่ทำให้ tier ที่ทำงานนี้ไม่ได้ กลายเป็นทำได้** | ขอโมเดลที่เรียกทูลไม่ได้ ในเทิร์นที่ต้องเรียกทูล = คำขอที่ทำตามไม่ได้ ⇒ **ปฏิเสธโดยระบุชื่อ** ในบรรทัดเดียวกับที่อธิบายการตัดตัวอื่น ไม่ใช่เมินเงียบ ๆ |
| **เลือกแล้วไม่ปลดล็อกการใช้เงิน** | ไม่งั้นตัวเลือกบนหน้าจอกลายเป็นวิธีจ่ายเงินโดยไม่มีการตัดสินใจจ่ายเงิน · ข้อความปฏิเสธพูดทั้งสองครึ่ง ("คุณเลือกไว้ แต่…ไม่ได้อนุญาตให้ใช้เงิน") เพราะครึ่งเดียวอ่านเป็นบั๊ก หรือไม่ก็ไม่บอกว่าต้องแก้อะไร |
| **ชื่อที่ไม่ตรงกับอะไรเลย = ไม่เปลี่ยนอะไร ไม่ใช่ error** | endpoint ถูกลบได้ในขณะที่บทสนทนายังจำชื่อมันอยู่ — การทำให้บทสนทนานั้นค้างคือคำตอบที่แย่กว่าการวิ่งตามลำดับปกติ |
| **ตัวเลือกอยู่ในคำอธิบาย** | ถ้าไม่โผล่ในบรรทัดเหตุผล คำอธิบายว่า "ทำไมคำตอบมาจากที่นี่" จะกลายเป็นคำอธิบายที่ผิด |

**ต่อหนึ่งบทสนทนา ไม่ใช่ค่าตั้งรวม** — คำถามคือ "รอบ*นี้*ขอตัวใหญ่" และค่าที่อยู่ยาวกว่าคำถามจะแอบใช้โมเดลใหญ่กับทุกอย่างหลังจากนั้น

**ขับจริงแล้ว**: กดตัวเลือกในหน้าแชท → เลือก `GX10 · 1a` → พิมพ์ "17 คูณ 3 เท่ากับเท่าไร" → ส่ง

```
บนหน้าจอ:  คุณเลือก GX10 ไว้สำหรับคำถามนี้ — ถ้าเรียกไม่ได้จะไล่ต่อตามลำดับเดิม
คำตอบ:     17 คูณ 3 เท่ากับ 51
```

**หลักฐานเสริมที่ไม่ได้ตั้งใจให้เป็นหลักฐาน**: คำถามเดียวกันนี้ตอนที่ Tier 0.5 ตอบ ได้ข้อความไทยที่สระหายเป็น `17 คณ 3 เทากบ 51` (เห็นในบทสนทนาเก่าบนเครื่องนี้) · รอบนี้ตัวอักษรครบทุกตัว ⇒ **คนละโมเดลตอบจริง** ไม่ใช่แค่ป้ายเปลี่ยน

⇒ **P15.1 ปิดข้อ "ถามผ่านหน้าแชทจริงแล้ว GX10 ตอบ" ได้แล้ว** · ที่ยังเหลือคือการตัดสายกลางสตรีมบนหน้าจอจริง ซึ่งตอนนี้*ทำได้แล้ว*เพราะมีทางเลือกให้บังคับ Tier 1 (เดิมบังคับไม่ได้เลย จึงตัดสายให้ดูก็ไม่มีความหมาย)

## E.38 ตัดสายกลางสตรีมบนหน้าจอจริง — และความเงียบที่ระบบเรียกว่า "สำเร็จ" (2026-08-16)

ข้อสุดท้ายของ **P15.1** · ทำได้เพราะ E.37 เพิ่งสร้างตัวเลือกที่บังคับ Tier 1 ได้ (ก่อนหน้านี้ทุกเทิร์นไปลงที่โมเดลบนเครื่อง การตัดสายจึงไม่ได้พิสูจน์อะไร) · ตัดด้วยการฆ่าพร็อกซี TCP ที่คั่นอยู่ ⇒ **สายขาดจริงกลางคำตอบ โดยไม่ต้องแตะการตั้งค่าระบบ**

**รอบแรก — สิ่งที่คนเห็นคือไม่มีอะไรเลย**

```
คำถามของตัวเอง
▸ ความคิดของโมเดล 2 วินาที        ← พับอยู่
(จบ)
```

ไม่มีคำตอบ ไม่มีข้อความผิดพลาด ไม่มีอะไรบอกว่าเกิดอะไรขึ้น · ทางจัดการความล้มเหลวกลางสตรีมที่เขียนไว้แล้ว (`"สตรีมคำตอบขาดกลางคัน"`) **ไม่ทำงาน เพราะไม่มีอะไร throw**: การเชื่อมต่อ SSE ที่หลุดไม่ได้โยน error เสมอไป — ซ็อกเก็ตปิด การวนจบ และ**สตรีมที่ว่างเปล่าแยกไม่ออกจากสตรีมที่พูดจบพอดี** ⇒ เทิร์นเดินเข้าทาง "สำเร็จ" โดยไม่มีข้อความและไม่มีการเรียกทูล แล้วรายงานความสำเร็จด้วยการเงียบ

**กฎที่ได้จึงไม่เกี่ยวกับการเชื่อมต่อเลย** — และนั่นคือเหตุผลที่มันควรอยู่ที่ชั้นเทิร์น ไม่ใช่ชั้นขนส่ง: **รอบที่ไม่ได้ผลิตข้อความและไม่ได้เรียกทูล คือรอบที่ยังไม่ได้ตอบ** ไม่ว่าด้วยเหตุใด · คำตอบที่ถูกตัด · โมเดลที่คืนมาแต่ความคิด · เซิร์ฟเวอร์ที่ปิดก่อน — จากที่ที่คนนั่งอยู่ ทั้งหมดนี้คือสิ่งเดียวกันคือ**คำตอบเปล่า** และการรายงานคำตอบเปล่าว่าเป็นเทิร์นที่สำเร็จ คือระบบอ้างว่าทำสิ่งที่มันไม่ได้ทำ (§2.5)

**รอบสอง หลังแก้ (2 เทสที่แดงมาก่อน)** — ตัดที่เดิม:

```
GX10 คิดอยู่แล้วหยุดกลางคัน — ไม่มีคำตอบส่งกลับมา ·
อาจเป็นการเชื่อมต่อที่ขาดโดยไม่แจ้ง ลองถามใหม่ หรือเลือกโมเดลอื่นที่ช่องเลือกข้างกล่องข้อความ
```

**ระบุชื่อว่าใครเงียบ** (ไม่งั้นคนอ่านไม่รู้จะไปดูที่ไหน) และ**บอกทางออกที่มีอยู่จริงบนหน้าจอเดียวกัน** ซึ่งคือตัวเลือกที่ E.37 เพิ่งใส่ไว้

⇒ **P15.1 ปิดครบทุกข้อแล้ว** · และข้อนี้ให้ผลตรงกับที่ Done-when ตั้งใจ: การถอดสายไม่ได้ไปยืนยันว่าข้อความผิดพลาดสวยดี แต่ไปเจอว่า**ไม่มีข้อความผิดพลาดเลย**

**เก็บกวาด**: พร็อกซีปิด · `baseURL` กลับไปที่ LAN · `defaultEndpointID` เป็น `migrated-self-hosted` ตามที่เจ้าของเครื่องตั้งไว้

## E.40 ปิด F-1 — ค่าที่ตั้งบนหน้าจอมีผลทันที และ S7 ผ่านบนหน้าจอจริง (2026-08-17)

**สิ่งที่แก้** — 6 ไฟล์ · 6 เทสหน่วย · 3 กฎใหม่ · 1 scenario ที่ขับจริง

### สิ่งที่ E.39 ค้างไว้ว่า "ยังไม่ถือว่าปิด" — ปิดได้แล้ว

E.39 บันทึกว่ามีรอบหนึ่งขึ้น `CHECKS FAILED` แล้วรอบถัดไปเขียวโดยไม่มีการแก้โค้ด และหาสาเหตุไม่เจอ · กลไกบอกชื่อสิ่งที่ตกที่เพิ่มไว้ตอนนั้น **ชี้ตัวได้ในรอบแรกที่มันเกิดซ้ำ**:

```
สิ่งที่ตก:
   • [local chat model (Tier 0.5)] local chat model
```

**สาเหตุจริง**: ด่านนั้นเคยเขียนว่า `if swift run MLXCheck 2>&1 | tail -16; then` ซึ่งทดสอบ exit ของ `tail` — **จึงไม่เคยแดงได้เลยตลอดอายุโปรเจกต์** · ตอนแก้ให้ตรวจจริง ผมใช้ `grep "✗"` บน output ซึ่งแย่กว่าเดิม เพราะ `MLXCheck` พิมพ์ ✗ กำกับ*ทุกโมเดลในคลังที่ใหญ่เกิน RAM ว่างตอนนั้น* — เป็นรายการสินค้าคงคลัง ไม่ใช่คำตัดสิน ⇒ ด่านแดงหรือเขียวขึ้นกับว่าตอนนั้นเครื่องว่างเท่าไร โดยที่ทุกเคสข้างในผ่านหมด

**แก้เป็น**: ใช้ exit code ของ `MLXCheck` เป็นคำตัดสิน และ**ยังพิมพ์บรรทัด ✗ ให้เห็นทุกครั้งแม้ด่านจะผ่าน** — โมเดลที่ใส่ไม่ลงแล้ว คือวิธีที่ Tier 0.5 เลิกเป็นพื้นรับประกันอย่างเงียบ ๆ

⇒ อาการ "ตอนแรกได้ ตอนหลังไม่ได้" ในด่านนี้ **อธิบายได้ครบและปิดแล้ว** — ไม่ใช่ RAM ทำให้โค้ดพัง แต่เป็นกฎที่อ่าน RAM แล้วตัดสินผิด

**ภาคผนวกของ E.40 — สิ่งที่ยังไม่ปิด (F-11)**

รอบแรกที่ด่านสัญญา Tier 1 ถูกรันจริงในรอบตรวจปกติ ([C1](../DECISIONS.md#c-คำตัดสินของเจ้าของโปรเจกต์--2026-08-17)) มันตก:

| รัน | ผล |
|---|---|
| `--filter VLLMExecutorTests` เดี่ยว | ✅ ผ่าน **73.3 วิ** |
| `check.sh --full` ทั้งชุด | ❌ **ตก 200.5 วิ** — `keeps the executor contract` |
| `check.sh --full` ทั้งชุด อีกรอบ | ✅ ผ่าน **168.6 วิ** |

โค้ดไม่เปลี่ยนระหว่างสามรอบนี้ · **ตามกฎ E7 ถือว่ายังไม่ผ่าน** และไม่รันซ้ำจนเขียวแล้วเรียกว่าจบ

**สิ่งที่ทำแทนการเดา**: รอบตรวจตอนนั้นรายงานได้แค่ `recorded an issue` ซึ่งไม่บอกว่าเคสไหนหรือเห็นอะไร — เป็นความเงียบแบบเดียวกับ M5 ลึกลงไปอีกชั้นหนึ่ง ⇒ `check.sh` พิมพ์บรรทัด `recorded an issue` / `Expectation failed` / `Caught error` ต่อจากชื่อเทสแล้ว

⇒ **ครั้งหน้าที่มันเกิด จะได้ชื่อเคสและสิ่งที่มันเห็น** ไม่ใช่ปริศนา · สมมติฐานที่ต้องตัดออกทีละข้อ: การแย่ง GX10 กับเทสอื่นในชุดเดียวกัน · RAM ตอนรันคู่กับ MLX · timeout ของเคสใดเคสหนึ่งในสัญญา

## E.41 ปิด U17 — sidecar ตายตามโปรเซสที่เปิดมัน · และคำสั่งเก็บกวาดที่ผิดมาตลอด (2026-08-17)

**U17 เปิดมาตั้งแต่ 2026-08-12** — `applicationShouldTerminate` ครอบแค่ ⌘Q · รันที่ถูกฆ่าด้วย SIGTERM ทิ้ง `surreal` ไว้ตัวละ ~200 MB (เคยเจอ 11 ตัว) และบนเครื่อง 16 GB นั่นคือสาเหตุที่ P5.3 รายงานว่าไม่มี RAM ให้โมเดล

### สิ่งที่ทำ

`SidecarReaper` — dispatch signal source สำหรับ **SIGTERM · SIGINT · SIGHUP · SIGQUIT**

| ทางเลือก | ทำไมไม่เอา / เอา |
|---|---|
| `PR_SET_PDEATHSIG` | **ไม่มีบน macOS** |
| signal handler ธรรมดา | ทำงานจริงในนั้นไม่ปลอดภัย |
| **dispatch signal source** | ✅ รันบนคิว จึงทำงานจริงได้ · ต้อง `SIG_IGN` ก่อน ไม่งั้นโปรเซสตายก่อนตัว source ทำงาน |
| SIGKILL | จับไม่ได้ — เหลือไว้ให้การเก็บ orphan จาก pid file ตอน launch ถัดไปเหมือนเดิม |

**ฆ่าลูกแล้วต้องตายตามที่ถูกสั่ง** — คืน `SIG_DFL` แล้ว `raise()` ต่อ · โปรเซสที่กลืน SIGTERM เพื่อความเรียบร้อย คือโปรเซสที่ค้างในทุกสคริปต์ที่คาดว่ามันจะหยุด

ติดตั้งใน `SidecarManager.init` ไม่ใช่ในแอปอย่างเดียว — `swift test` และ executable ตรวจต่าง ๆ ก็เปิด sidecar และ**เป็นรันที่ถูกฆ่ากลางคันจริง ๆ**

### วัดจริงบน `.app` ที่ sandbox แล้ว

```
sidecar ตอนแอปทำงาน: 1
── ฆ่าด้วย SIGTERM ──
sidecar หลัง SIGTERM: 0
log: [sidecar-reaper] signal 15 — เก็บ sidecar 1 ตัว
```

**เทส 2 ข้อ** พร้อมพิสูจน์ว่าแดงได้: ปิดกลไกทั้งหมด → `the registered child survived the reaper` · **กฎ 2 ข้อใน `check.sh`**

### สิ่งที่เจอระหว่างทาง และร้ายแรงกว่า U17 เอง

**คำสั่งเก็บกวาดที่เอกสารทุกฉบับใช้ พลาด sidecar ของแอปที่แพ็กแล้ว**

## E.42 ปิด P9.1 ครึ่งที่ต้องใช้โมเดล — และตัวเลขที่ P15.7 รออยู่ (2026-08-17)

**ทำไมไม่ใช่ golden file แบบเทียบตัวอักษร**: prompt เดียวกันไม่ได้ให้ประโยคเดิมสองครั้ง · เทสที่บังคับให้เหมือนเป๊ะ คือเทสที่คนจะ regenerate แทนที่จะอ่าน (E7/E8) ⇒ ตรึง**ความแม่นเทียบคำตอบที่รู้** กับ**พื้นที่ห้ามต่ำกว่า** แทน

### ผลที่วัดได้ — `unsloth/Qwen3.8-27B-NVFP4`


**พลาดครบทั้ง 4 คู่ที่ขัดกันจริง** — เวลาให้ยา · ขนาดยา 2 ก. กับ 1 ก. · ให้ต่อกับไม่ให้ต่อ · คู่ข้ามภาษา

⇒ บนหน้าจอ Conflict Ledger แปลว่า **"ไม่พบข้อขัดแย้ง"** ซึ่งอ่านเหมือนคลังสะอาด ทั้งที่มันคือการไม่เห็น

### แต่ตัวเลขนี้ไม่ใช่คำตอบว่า "โมเดลไม่เก่งพอ" — ไล่ต่อแล้วเจอสองเรื่องคนละเรื่อง

**1. งบโทเคนเล็กเกินไป (ปัญหาวิศวกรรม)** — 3 ใน 4 ที่พลาดคืนค่า `⚠ อ่านคำตอบไม่ออก` ที่ **180–181 วินาที** พอดี · `ConflictDetector` ตั้ง `maxTokens = 2_048` และ 2,048 โทเคนที่ ~11 tok/s = **~186 วินาที** ⇒ ไม่ใช่การตัดสินผิด แต่คือคำตอบที่ไม่เคยถูกเขียนจบ · `.unparseable` ถูกกลืนเป็น `nil` ใน `detect()` ⇒ ไม่มีการ์ด ไม่มีข้อความ ไม่มีอะไรบอก

**2. schema ทำให้คำตัดสินแย่ลง (ปัญหาการออกแบบ)** — วัดกับคู่ "60 นาที vs 2 ชั่วโมง" ตรง ๆ:

| ถามยังไง | โทเคน | ผล |
|---|---|---|
| ถามเปล่า ๆ `{"contradicts":bool}` | **191** · `stop` | ✅ **`{"contradicts": true}` — ถูก** |
| ถามผ่าน schema 7 ฟิลด์ของ `ConflictDetector` | **802** · `stop` | ❌ `sameQuestion: false` · `mutuallyExclusive: false` — **ผิด** |

โมเดลเดียวกัน คำถามเดียวกัน · **การขอ 7 ฟิลด์พร้อมกัน (รวม `question` และ `explanation` ที่เป็นข้อความอิสระ) ทำให้คำตัดสินแย่ลงและใช้โทเคนมากกว่าสี่เท่า**

และ `question` คืนข้อความจาก prompt มาแบบคำต่อคำ ซึ่งคือ **U12** ที่บันทึกไว้ตั้งแต่ต้น — ตอนนี้รู้แล้วว่ามันไม่ใช่ความไม่เรียบร้อยของหัวการ์ด แต่เป็นอาการของ schema ที่โมเดลตอบไม่ไหว

### ⇒ คำตอบสำหรับ P15.7

**คำถาม "27B ที่ NVFP4 พอไหมสำหรับบทบาทที่ผิดแล้วเสียหาย" ยังตอบไม่ได้จากตัวเลขนี้** เพราะตัวเลขนี้วัดเส้นทางที่มีบั๊กสองชั้นทับอยู่ — โมเดลตอบคำถามเดียวกันได้ถูกเมื่อถูกถามให้ถูกวิธี

**ต้องแก้สองข้อข้างบนก่อน แล้ววัดใหม่** ถึงจะเป็นการวัดโมเดล ไม่ใช่การวัดบั๊กของเรา

**พื้นที่บันทึกไว้ = 4/8** — เป็น*พื้น* ไม่ใช่*เป้า* มีไว้ให้การเปลี่ยนที่ทำให้แย่ลงกว่านี้ลงไม่ได้เงียบ ๆ · `check.sh --full` รัน `QualityCheck` แล้ว

## E.43 แก้งบโทเคนแล้ววัดใหม่ — แยกบั๊กของเราออกจากคุณภาพของโมเดลได้แล้ว (2026-08-17)

[E.42](#e42-ปิด-p91-ครึ่งที่ต้องใช้โมเดล--และตัวเลขที่-p157-รออยู่-2026-08-17) วัดได้ 4/8 บนเส้นทางที่มีบั๊กทับอยู่ · รอบนี้แก้เฉพาะส่วนที่เป็น**วิศวกรรมล้วน ไม่แตะเกณฑ์ตัดสินใด ๆ** แล้ววัดซ้ำ

**สิ่งที่แก้ 2 อย่าง**

| แก้อะไร | ทำไม |
|---|---|
| `maxTokens` 2,048 → **8,192** | 800 โทเคนคือค่าที่วัดได้ของ JSON ตาม schema นี้ · โมเดลที่คิดก่อนตอบใช้หลายเท่าของนั้นก่อนถึงวงเล็บแรก · 2,048 ที่ ~11 tok/s = 186 วินาทีที่ถูกทิ้ง |
| แยก `.truncated(tokens:)` ออกจาก `.unparseable` | "อ่านคำตอบไม่ออก" คือบั๊กของเรา · "คำตอบไม่เคยเขียนจบ" คืองบ ซึ่งบอกคนได้ว่าให้ขยาย — เดิมทั้งคู่ตกลงไปเป็น `nil` เงียบ ๆ เหมือนกัน · **คอมไพเลอร์บังคับให้ทุกที่ที่ switch ต้องตอบเคสใหม่** จึงไม่มีที่ไหนกลืนมันได้อีก |

### ผลหลังแก้

```
ถูก 5/8   (เดิม 4/8)
ข้อขัดแย้งจริงที่พลาด: 3/4   (เดิม 4/4)
คู่ที่ไม่ขัดแต่ถูกฟ้อง: 0/4
```

**การถูกตัดหายไปหมด** — ไม่มี `อ่านคำตอบไม่ออก` เหลือสักเคส ⇒ ที่เหลือคือของจริงล้วน

### สามเคสที่ยังพลาด — และมันไม่ใช่เรื่องเดียวกัน

| เคส | โมเดลตอบ | เป็นปัญหาของใคร |
|---|---|---|
| **ข้ามภาษา** (EN 60 นาที vs TH 3 ชั่วโมง) | **ขัดกัน · ความมั่นใจ 0.85** | **ของเรา** — `crossLanguageConfidence = 0.9` ปัดคำตอบที่**ถูกแล้ว**ทิ้ง |
| ขนาดยา 2 ก. vs 1 ก. | `mutuallyExclusive: false` | **ของโมเดล** — ตัดสินผิดจริง |
| ให้ต่อ 24 ชม. vs ไม่ต้องให้ต่อ | `mutuallyExclusive: false` | **ของโมเดล** — ตัดสินผิดจริง |

⇒ **จาก 4 คู่ที่ขัดกันจริง: โมเดลตัดสินถูก 2 · ผิด 2 · และหนึ่งในสองที่ถูกนั้นถูกเกณฑ์ของเราปัดทิ้ง**

### ตัวเลขสำหรับ P15.7 — ตอนนี้เป็นตัวเลขของโมเดลจริง ๆ แล้ว

`unsloth/Qwen3.8-27B-NVFP4` บนงานตัดสินข้อขัดแย้งทางการแพทย์:

- **ไม่สร้างข้อขัดแย้งปลอมเลย** (0/4 false positive) — ด้านนี้ดี
- **พลาดข้อขัดแย้งจริงครึ่งหนึ่ง** (2/4 จากการตัดสินของมันเอง) — รวมกรณี "ทำกับไม่ทำ" ซึ่งเป็นรูปแบบที่ตรงไปตรงมาที่สุด

**นี่คือสิ่งที่ P15.7 ถามหา** — และมันบอกว่างานที่ผิดแล้วเสียหายแบบนี้ ยังฝากไว้กับ 27B ตัวเดียวไม่ได้ · **แต่ตัวเลือกไม่ได้มีแค่ "เปลี่ยนโมเดล"**: เกณฑ์ข้ามภาษา 0.9 เป็นค่าที่เราตั้งเอง และ schema 7 ฟิลด์ยังไม่ถูกทบทวน (E.42) — ทั้งคู่คือสิ่งที่ต้องลองก่อนสรุปว่าโมเดลไม่พอ

## E.45 ตอบ P15.7 ได้แล้ว — 8/8 และคำตอบคือ *วิธีที่เราถาม* ไม่ใช่ *ความสามารถของโมเดล* (2026-08-17)

เจ้าของโปรเจกต์ตัดสินสองข้อของ [F-13](../AUDIT_2026-08-17.md) · ทั้งคู่แก้แล้ววัดใหม่ในรอบเดียว เพราะผลรายเคสแยกได้เองว่าอันไหนช่วย

| แก้อะไร | เหตุผลที่เสนอ |
|---|---|
| `crossLanguageConfidence` **0.9 → 0.8** | เกณฑ์นี้ตั้งสูงเพราะกลัวคู่ข้ามภาษาเป็นคำแปลกัน — แต่ `isTranslation` ถูกถามใน prompt และถูกตรวจแยกใน `examine` อยู่แล้ว ⇒ เป็นตัวกันชั้นที่สองที่หยาบกว่า ทับของที่เจาะจงกว่า และค่าที่มันปัดทิ้งคือคำตอบที่ถูก |
| **ย้าย `question` + `explanation` มาก่อน boolean ทั้งสี่** | guided decoding emit ตามลำดับที่ประกาศ และวัดแล้วว่า `reasoning_content` ยาว **0** ⇒ โทเคนแรกสุดที่โมเดลพ่นออกมาคือคำตัดสิน โดยไม่มีที่ให้คิดเลย · **ไม่แตะนิยามของเกณฑ์สามข้อแม้แต่ตัวอักษรเดียว — เปลี่ยนแค่ลำดับการถาม** |
| เติม prompt ให้ตรงกับลำดับใหม่ | บอกให้ใช้สองช่องแรกไล่เกณฑ์ก่อนตัดสิน · และ **ห้ามคัดลอกข้อความ A/B มาใส่ `question`** ซึ่งเป็นอาการของ U12 |

### ผล

```
ถูก 8/8          (4/8 → 5/8 → 8/8)
ข้อขัดแย้งจริงที่พลาด: 0/4
คู่ที่ไม่ขัดแต่ถูกฟ้อง: 0/4
```

**ทั้งสี่คู่ที่เคยพลาด ตอบถูกหมด ที่ความมั่นใจ 0.95** — รวมสองคู่ที่ [E.43](#e43-แก้งบโทเคนแล้ววัดใหม่--แยกบั๊กของเราออกจากคุณภาพของโมเดลได้แล้ว-2026-08-17) สรุปว่าเป็น "โมเดลตัดสินผิดจริง" (ขนาดยา 2 ก. vs 1 ก. · ให้ต่อ vs ไม่ให้ต่อ)

⇒ **ข้อสรุปนั้นผิด และการสรุปแบบนั้นคือสิ่งที่ M6 เตือนไว้**: ผมอ่านตัวเลขจากเส้นทางที่ยังมีข้อบกพร่องของเราอยู่ แล้วโยนให้โมเดล

### คำตอบของ P15.7

**`Qwen3.8-27B-NVFP4` ทำงานตัดสินข้อขัดแย้งทางการแพทย์ได้ 8/8 บนชุดนี้** — ไม่พลาดของจริง ไม่ฟ้องผิด

**สิ่งที่เปลี่ยนไม่ใช่โมเดล และไม่ใช่เกณฑ์** — เป็นงบโทเคน (E.43) กับลำดับที่เราถาม (รอบนี้) · เกณฑ์ NLI สามข้อของ §11.7 ยังเหมือนเดิมทุกตัวอักษรตั้งแต่ต้น

⇒ **ไม่ต้องเปลี่ยน checkpoint และไม่ต้องกันบทบาทวิกฤตไว้ให้ endpoint ที่คิดเงิน** สำหรับงานชนิดนี้

### ราคาที่ต้องจ่าย และต้องเขียนไว้

รอบนี้ใช้ **~30 นาที** เทียบกับ ~15 นาทีของรอบก่อน · เคสที่ช้าที่สุด **610 วินาที** เพราะโมเดลเขียนเหตุผลก่อนลงมติทุกครั้ง

⇒ **การตัดสินข้อขัดแย้งหนึ่งคู่ใช้เวลาหลักนาทีบนเครื่องนี้** ซึ่งเป็นของจริงที่หน้าจอต้องบอก ไม่ใช่ปล่อยให้ดูเหมือนค้าง · และเป็นเหตุผลที่ ingest ที่ยกการ์ดหลายคู่พร้อมกันต้องคิดเรื่องคิวตั้งแต่ออกแบบ

**พื้นใหม่ = 8/8** — ตอนนี้พื้นกับเพดานเท่ากัน ⇒ การถอยหลังใด ๆ จะแดงทันที

### สิ่งที่ยังไม่ได้วัด

- ชุดนี้มี 8 เคส · **8/8 ไม่ได้แปลว่าไม่มีเคสที่มันพลาด** แปลว่าชุดนี้ยังไม่เจอ — ควรเพิ่มเคสที่ยากขึ้นเมื่อมีข้อมูลจริง
- ยังไม่ได้ลอง checkpoint อื่น จึงไม่รู้ว่า FP8/AWQ ให้ผลเท่ากันไหมที่ความเร็วต่างกัน

## E.46 พื้นรับประกัน P5.4 ถูกพิสูจน์จริงเป็นครั้งแรก — และสาเหตุที่มันถูกข้ามมาตลอด (2026-08-17)

P5.4 คือคำสัญญาว่า *ปิดเน็ตแล้วแอปยังตอบได้* · ด่านที่พิสูจน์มัน **ถูกข้ามทุกรอบ** ด้วยข้อความว่าแรมไม่พอ และไม่มีใครไล่ต่อว่าทำไม

### สาเหตุที่หนึ่ง — พื้นถูกเลือกด้วยการประมูล ไม่ใช่การตัดสินใจ

`LocalModelCatalog.preferred()` คืน **โมเดลใหญ่ที่สุดที่พอดีกับ RAM ว่าง ณ ตอนนั้น** ซึ่งถูกสำหรับคำถาม *"ควรใช้ตัวไหนทำงาน"* แต่ผิดสำหรับ *"อะไรพิสูจน์ว่ามีพื้น"*

⇒ ด่านพื้นวัดกับคนละโมเดลทุกรอบ: ว่าง 6.9 GB ได้ 4.5 GB · ว่าง 2.7 GB ไม่ได้อะไรเลย · **ผ่านหรือข้ามแบบสุ่มโดยที่โค้ดไม่ขยับ**

⇒ เพิ่ม `floorModel()` ที่คืน**ตัวเล็กที่สุดที่ใส่ลงได้** — ตรงข้ามกับ `preferred()` โดยตั้งใจ · หน้าที่ของพื้นคือ*ตอบได้เมื่อไม่มีอะไรเลย* ไม่ใช่ตอบได้ดี (§9.2 ข้อ 4)

### สาเหตุที่สอง — ด่านตรวจสร้าง `LocalTier` ใหม่ทุกเคส

พอด่านแรกรันได้ ด่านที่สองรายงานว่าโมเดล**เดียวกัน** `unavailable` ทันที · เพราะ `router(with:)` สร้าง `LocalTier` ตัวใหม่ทุกครั้ง และ admission control ถามจาก RAM ว่าง — ซึ่งตอนนั้น weights ของด่านแรกครองอยู่ ⇒ **สอง tier ต่อหนึ่งโมเดล = นับหน่วยความจำซ้ำ**

`Engine` สร้าง `LocalTier` **ตัวเดียว** ⇒ ด่านที่สร้างหลายตัวไม่ได้ทดสอบของที่ส่งมอบจริง · แก้เป็น router ตัวเดียวใช้ร่วมกันทุกเคส

### สาเหตุที่สาม — เครื่อง 16 GB ที่ใช้งานจริงไม่มีที่ให้โมเดล 4B

วัดจริงตามลำดับ:

| โมเดล | บนดิสก์ | ต้องการตอนรัน | ผลบนเครื่องนี้ |
|---|---|---|---|
| `Qwen3.5-9B-MLX-4bit` | 5.6 GB | 7.1 GB | ไม่เคยผ่าน |
| `Qwen3-VL-4B-Instruct-MLX-4bit` | 2.9 GB | 4.5 GB | ผ่านบ้างไม่ผ่านบ้าง |
| **`Qwen3-4B-4bit`** (โหลดมาใหม่) | 2.1 GB | **3.7 GB** | **ยังไม่ผ่าน** — ปิดแอปแล้วยังว่างแค่ 1.9–2.8 GB |
| **`Qwen3-0.6B-4bit`** (โหลดมาใหม่) | 0.33 GB | ~1 GB | ✅ **ผ่าน** |

**ตัวคูณระหว่างขนาดไฟล์กับหน่วยความจำตอนรันคือ ~1.75×** ซึ่งเป็นตัวเลขที่ควรใช้ตอนเลือกโมเดล ไม่ใช่ดูขนาดไฟล์อย่างเดียว

### ผล — P5.4 ผ่านครบเป็นครั้งแรก

```
✓ endpoint ที่ตั้งไว้ต่อไม่ได้จริง
  พื้นรับประกันวัดกับ: mlx-community/Qwen3-0.6B-4bit
✓ งาน high-impact ยังทำงานได้ ตกลงมาที่โมเดลบนเครื่อง (1.2s) → role=researcher
✓ ตรวจข้อขัดแย้งได้โดยไม่มีเน็ต — ไม่ใช่เงียบว่าไม่มีข้อขัดแย้ง (106.3s)
```

**บรรทัดสุดท้ายสำคัญกว่าที่อ่านผ่าน ๆ**: 0.6B ตอบว่า `contradicts: false` ซึ่ง**ผิด** สำหรับคู่ metformin นั้น — แต่ด่านนี้ไม่ได้ถามว่าตอบถูกไหม มันถามว่า **ระบบเงียบหรือเปล่า** และคำตอบคือไม่เงียบ · คุณภาพเป็นเรื่องของ Tier 1 ซึ่งวัดแยกไว้ที่ [E.45](#e45-ตอบ-p157-ได้แล้ว--88-และคำตอบคือ-วิธีที่เราถาม-ไม่ใช่-ความสามารถของโมเดล-2026-08-17) แล้ว

### สิ่งที่ต้องเขียนไว้ตรง ๆ

**พื้นรับประกันบนเครื่องนี้คือ 0.6B ซึ่งตอบคำถามยาก ๆ ผิด** · นั่นคือสิ่งที่ "ยังตอบได้ตอนไม่มีเน็ต" หมายถึงจริง ๆ บนเครื่อง 16 GB ที่มีงานอื่นอยู่ด้วย — ไม่ใช่คำสัญญาเรื่องคุณภาพ และหน้าจอไม่ควรทำให้ดูเหมือนเป็น

## E.47 ปิด F-11 — ความยาวคำตอบของ endpoint นี้เป็นฟังก์ชันของว่ามันยุ่งแค่ไหน (2026-08-17)

`keeps the executor contract` ตกในรอบเต็ม **สามรอบติด** ที่ ~200 วินาที และผ่านทุกครั้งที่รันเดี่ยว · สองรอบแรกผมเดาว่าเป็นงบโทเคน แล้ว**เดาผิดเรื่องกลไก** เพราะยังไม่มีข้อมูล

### สิ่งที่ต้องทำก่อนอย่างอื่น — ทำให้ความล้มเหลวบอกชื่อตัวเอง

Swift Testing พิมพ์แค่ `Issue recorded` และกลืนข้อความของ `Issue.record(...)` ⇒ สามรอบที่ตกไม่ได้บอกว่าเคสไหนหรือเห็นอะไรเลย

⇒ ให้ `runContract` **`print` ควบคู่กับ `Issue.record`** และ `check.sh` เก็บบรรทัด `CONTRACT-FAILED:` มาแสดง · รอบถัดไปมันบอกทันที:

```
CONTRACT-FAILED: [unsloth/Qwen3.8-27B-NVFP4] structured output comes back as decodable JSON
  — not JSON: We need answer user: "Fix a crash in main.swift on launch". Need likely ask for code/error?
    But maybe provide general guidance. Need final. Need be helpful…
```

**ความคิดของโมเดลอยู่ใน `content`** ทั้งที่ guided decoding เปิดอยู่

### แล้ววัดต่อจนได้กลไกจริง

| การทดสอบ | ผล |
|---|---|
| curl ตรง ๆ 3 ครั้งติด | ✅ JSON สะอาดทุกครั้ง · **294 โทเคน** เท่ากันทั้งสาม |
| **ยิงพร้อมกัน 6 สาย · คำขอเดียวกัน · temperature 0** | **172 · 186 · 305 · 530 · 758 · 2048 โทเคน** — สายสุดท้าย `finish_reason: length` **content ว่างเปล่า** |

⇒ **คำขอเดียวกันที่ temperature 0 ใช้โทเคนต่างกันสิบเท่า ขึ้นกับว่าเซิร์ฟเวอร์ยุ่งแค่ไหน** · งบที่ตั้งจากเครื่องว่าง คืองบที่พังตอนมีงานพร้อมกัน — ซึ่งคือตอนที่ชุดเทสทั้งชุดรัน

**สมมติฐานเดิมถูกครึ่งเดียว**: กลไกคือชนเพดานโทเคนจริง แต่เหตุที่มันเกิดเฉพาะรอบเต็มคือ*ความพร้อมกัน* ไม่ใช่ความช้า

### สิ่งที่แก้ และความผิดพลาดระหว่างทาง

ตั้ง `maxTokens = 8_192` คงที่ ⇒ **พัง Tier 0 ทันที** (`context overflow: needs ~8208, has 4096`) — หน้าต่างของ Apple on-device คือ 4,096 · **เป็นความผิดพลาดแบบเดียวกับที่กฎ L1 มีไว้กัน ทำในไฟล์ที่ตรวจกฎเอง**

⇒ แก้เป็นสัดส่วนของหน้าต่าง executor แต่ละตัว:

```swift
func contractAnswerBudget(for executor: any LLMExecutor) -> Int {
    max(512, min(8_192, executor.capabilities.contextWindow / 4))
}
```

4,096 → 1,024 · 32,768 → 8,192

**ผล**: `check.sh` เขียว · ตก 0 · ข้ามไม่ได้ 0

### บทเรียนที่ควรอยู่ต่อ

**ตัวเลขความยาวคำตอบที่วัดบนเครื่องว่าง ใช้ตั้งงบไม่ได้** — และเรื่องนี้กระทบมากกว่าเทส: `ConflictDetector` ตั้ง 8,192 ไว้จากการวัดแบบเรียงลำดับ ([E.43](#e43-แก้งบโทเคนแล้ววัดใหม่--แยกบั๊กของเราออกจากคุณภาพของโมเดลได้แล้ว-2026-08-17)) ⇒ **ยังไม่รู้ว่าพอไหมเมื่อมีหลายคู่ถูกตัดสินพร้อมกัน** ซึ่งเป็นสิ่งที่ ingest จะทำ · ควรวัดก่อนเปิดใช้จริง

## E.48 แปลหน้าจอเป็นอังกฤษ — และภาษาที่ส่งไปในบันเดิลแต่ไม่มีวันถูกเลือก (2026-08-17)

**คำถาม**: ย้าย UI ไปเป็นระบบหลายภาษาโดยมีอังกฤษเป็นฐาน แล้ว*พิสูจน์บนหน้าจอจริง*ว่าสลับภาษาได้

**สิ่งที่ทำ**: แปลง `ChatView` · `StatusBarView` · `BootStatusView` · แถบพื้นที่ 5 อัน รวม **129 สตริง** เข้าแคตตาล็อก `en.lproj`/`th.lproj`

### สิ่งที่เจอ — และมันเงียบยิ่งกว่ากับดัก `.xcstrings`

ขับแอปด้วย `AppleLanguages = (th)` แล้ว **หน้าจอยังเป็นภาษาอังกฤษทั้งหน้า** ทั้งที่ `th.lproj` อยู่ใน `.app` จริง โหลดได้จริง

วัดตรง ๆ จากภายในบันเดิลของแอปเอง:

| | ก่อนแก้ | หลังแก้ |
|---|---|---|
| `Bundle.main.localizations` | `[]` | `["en", "th"]` |
| module `preferredLocalizations` เมื่อบังคับ `(th)` | **`["en"]`** | `["th"]` |
| `String(localized: "Stop", bundle: .module)` | **`Stop`** | **`หยุด`** |
| `String(localized: "Send", bundle: .module)` | `Send` | `ส่ง` |

**สาเหตุ**: `Resources/Info.plist` ไม่มี `CFBundleLocalizations` ⇒ บันเดิลหลักประกาศว่าไม่รองรับภาษาใดเลย ⇒ macOS ตัดสินภาษาของ*แอป*เป็น development region แล้วเอาไปตัดกับทุก module bundle

⇒ **`th.lproj` ถูกแพ็กเข้าไป ถูกหาเจอ โหลดได้ และไม่มีทางถูกเลือก — บนเครื่องไหนก็ตาม ตั้งค่าภาษาอะไรก็ตาม** ไม่มีอะไรเตือนสักบรรทัด

นี่คือกับดักตัวที่สองของกลไกเดียวกัน (ตัวแรกคือ `.xcstrings` ที่ SwiftPM ส่งไปแบบไม่คอมไพล์) และทั้งสองตัวมีอาการเดียวกันคือ **"ดูปกติ"**

### กฎที่ถูกวางไว้ให้จับซ้ำไม่ได้

| กฎ | จับอะไร | พิสูจน์ว่าแดงได้แล้ว |
|---|---|---|
| key ที่ **คอมไพเลอร์** บอกว่าถูกเรียก ต้องมีคำแปลครบทุกภาษา | คำแปลขาด ⇒ คนไทยเห็นอังกฤษเงียบ ๆ | ลบ `"Pinned"` ⇒ แดง |
| ตัวแปรในคำแปลต้องตรงกับ key | `%.0f` หายจากบรรทัดไทย ⇒ `String(format:)` พิมพ์เลขผิด ไม่ใช่ error | เติม `%@` เกิน ⇒ แดง |
| ทุก `.lproj` ที่ส่งไป ต้องประกาศใน `CFBundleLocalizations` | **บั๊กในหัวข้อนี้** | ลบคีย์ออก ⇒ แดง |
| โมดูลที่มีแคตตาล็อก ต้อง emit key ด้วย | โมดูลที่ไม่มีใครตรวจ | ถอด flag ⇒ แดง |

**key มาจากคอมไพเลอร์ ไม่ใช่จากการอ่านซอร์ส** — `-emit-localized-strings` เขียน `.stringsdata` ต่อไฟล์ เพราะอ่านซอร์สแล้วเดาเองไม่ได้: `\(count)` กลายเป็น `%lld` แต่ `\(name)` กลายเป็น `%@` และแยกสองอันนี้ต้องใช้ type checker · การเดาผิดจะ*ผ่าน*การตรวจของตัวเอง ในขณะที่ทุก lookup พลาดตอนรัน — `Tests/ConfigTests/LocalisationTests` ตรึงข้อเท็จจริงนี้ไว้ด้วยการวัด

### ของค้าง

**แอปที่แพ็กแล้วเปิดขึ้นมาโดยไม่มีหน้าต่าง** (`count windows` = 0 · log บอก `No windows open yet`) ส่วนไบนารีดีบักเปิดหน้าต่างปกติทุกครั้ง

หน้าตาเหมือน U24-2 แต่**ทางแก้ของ U24-2 ใช้ไม่ได้**: ลบ Saved Application State แล้วยังเป็นเหมือนเดิม ⇒ **ยังไม่รู้สาเหตุ ไม่ใช่แค่ผลของการปิดแอปแรง ๆ**

⇒ การพิสูจน์รอบนี้จึงวัดจาก**ภายในบันเดิลของ `.app` จริง** (รันโพรบใน `Contents/MacOS` เพื่อให้ `Bundle.main` เป็นตัวแอปเอง) ซึ่งครอบคลุมกลไกทั้งหมดยกเว้นขั้นสุดท้ายคือ SwiftUI หยิบไปวาด — ขั้นนั้นเห็นแล้วเป็นภาษาอังกฤษบน AX tree ของไบนารีดีบัก แต่ยังไม่เคยเห็นภาษาไทยบนจอ

## E.49 ปิด F-17 — สองบั๊กที่ทำให้แอปที่แพ็กแล้ว "ขึ้นแต่ไม่มีอะไร" และ "ตายเงียบ" (2026-08-18)

**คำถาม**: ทำไม `.app` ที่แพ็กแล้วเปิดขึ้นมาโดยไม่มีหน้าต่าง ทั้งที่ไบนารีดีบักตัวเดียวกันเปิดปกติ — และมันบล็อกการพิสูจน์ภาษาบนหน้าจอตามกฎ M2

### บั๊กที่ 1 — ชื่อชนิดที่มี*ที่อยู่หน่วยความจำ*อยู่ข้างใน

ไล่ทีละขั้น: process ไม่ค้าง (`sample` บอกว่า main thread นอนอยู่ใน run loop ปกติ) · ลบ Saved Application State แล้วยังเป็น · ถอด sandbox แล้วยังเป็น · **กด ⌘N แล้วหน้าต่างขึ้นทุกครั้ง** ⇒ scene ไม่พัง ขาดแค่หน้าต่าง*แรก*

log ของ AppKit บอกตรง ๆ:

```
_reopenWindowsAsNecessary…  shouldRestoreState=1  hasPersistentStateToRestore=1
restoreWindowWithIdentifier: identifier=SwiftUI…CoAIWorkspaceApp.(unknown context at $10a276fe8).RootView…-1-AppWindow-1
                             restorerIsValid=YES
_block_invoke …              window=0x0   error=(null)
```

**`(unknown context at $10a276fe8)`** — ชื่อ mangled ของชนิดที่ประกาศเป็น `private` มี**ที่อยู่หน่วยความจำ**อยู่ข้างใน และ ASLR ทำให้มันเปลี่ยนทุกครั้งที่เปิด

### บั๊กที่ 2 — `Bundle.module` ไม่มีทางหาเจอในแอปที่แพ็กแล้ว

พอหน้าต่างขึ้นได้ แอปก็**ตายทันที** — crash report ชี้ตรงจุด:

```
Swift.fatalError  ←  Bundle.module (one-time init)  ←  Text.init(localised:)  ←  BootStatusView.phaseSection
```

accessor ที่ SwiftPM สร้างให้ **ทุก** target (ไม่ว่า library หรือ executable) คือ:

```swift
Bundle.main.bundleURL.appendingPathComponent("CoAIWorkspace_CoAIWorkspaceApp.bundle")
  ?? Bundle(path: "<build directory ของเครื่องที่คอมไพล์>")
  ?? fatalError("could not load resource bundle")
```

`Bundle.main.bundleURL` ของแอปคือ **ตัว `.app` เอง** ⇒ มันมองหาที่**รากบันเดิล** · แต่ `codesign` ปฏิเสธของหลวม ๆ ที่รากบันเดิล (`unsealed contents present in the bundle root`) ⇒ ที่เดียวที่วางได้คือ `Contents/Resources` ซึ่งคือที่เดียวที่มันไม่มอง

⇒ candidate แรกพลาด · candidate ที่สองคือ absolute path ที่มีอยู่บนเครื่องเดียวในโลก · candidate ที่สามคือ **crash**

**นี่คือกับดัก P9.6 เป๊ะ ๆ**: ทำงานที่นี่ พังที่อื่น · และมันเพิ่งโผล่เพราะนี่เป็นครั้งแรกที่ target ของแอปเองมี resource

**แก้**: โมดูล `Localisation` ใหม่ — หาในที่ที่บันเดิลอยู่ได้จริง ตามลำดับที่มันอยู่ได้จริง และ**ตกกลับไปที่ main bundle แทนที่จะ crash** เพราะคำแปลที่ขาดควรกลายเป็นภาษาอังกฤษ ไม่ใช่แอปตาย

### พิสูจน์บนหน้าจอจริง — แอปที่แพ็กแล้ว บิลด์เดียวกัน

| ค่าเริ่มต้นของเครื่อง (`en-TH`) | `Conversations` · `New conversation (⌘N)` · `Search across projects` · `Sidebar` · `20 hours ago` |

เนื้อหาบทสนทนายังเป็นไทยทั้งสองรอบ — ถูกต้อง เพราะนั่นคือ*ข้อมูลของผู้ใช้* ไม่ใช่ข้อความของแอป

### บทเรียน

**`PACKAGE LOOKS PORTABLE` เป็นคำกล่าวอ้างที่ตรวจไม่ตรงกับสิ่งที่มันอ้าง** — มันตรวจว่าไฟล์อยู่ในแอป ไม่ได้ตรวจว่าโค้ดหาเจอ · และสองอย่างนี้ต่างกันตรงที่ accessor มองที่ไหน ซึ่ง audit ไม่เคยอ่าน

## E.51 แปลหน้าจอต่อ 8 ไฟล์ — และ markdown ที่หายไปเงียบ ๆ ระหว่างแปล (2026-08-18)

### บั๊กที่ตัวเองทำระหว่างแปล

`Text("… **รวมรอบที่ต้องแก้** …")` เดิม SwiftUI แกะ markdown ให้ เพราะ argument เป็น *literal*

`Text(localised:)` รอบแรกส่ง `String` ที่ค้นมาแล้ว ⇒ **ไม่ใช่ literal** ⇒ ดอกจันขึ้นจอ

นี่คืออาการเดียวกับกฎ U5 เป๊ะ ๆ แต่เข้ามาทางประตูที่ U5 ไม่ได้เฝ้า — U5 มองหาการต่อสตริงด้วย `+` ซึ่งตรงนี้ไม่มี

**แก้สองชั้น**: `Text(localised:)` เดินผ่าน `Text(markdown:)` · และขยายกฎ U5 ให้จับ `Text(t("… ** …"))` ด้วย

### วิธีทำงานที่ใช้ และเหตุผล

| ขั้น | ทำอะไร |
|---|---|
| 1 | แปลงเป็นก้อน ๆ ก้อนละ ~15 สตริง · `assert` ทุกสตริงว่าหาเจอ แล้ว build ทันที |
| 2 | ดึง key จาก `.stringsdata` ของ **คอมไพเลอร์** ไม่ใช่จากซอร์ส |
| 3 | สร้างไฟล์ `en` อัตโนมัติจาก key + comment ที่ดึงจาก call site |
| 4 | เขียน `th` ด้วยมือจากข้อความไทยเดิม แล้วให้กฎตรวจว่าครบและตัวแปรตรง |

ขั้นที่ 2 คือขั้นที่ทำให้ขั้นที่ 4 เชื่อได้ — `%lld` กับ `%@` ต่างกัน และเดาเองไม่ได้

## E.53 กฎที่จับ "key ที่แปลไม่ได้ตลอดไป" — และ 17 จุดที่มันเจอทันที (2026-08-18)

### บทเรียน

**กฎที่ตรวจจาก "สิ่งที่เครื่องมือรายงาน" มองไม่เห็นสิ่งที่เครื่องมือเงียบเรื่องนั้น** — และวิธีเดียวที่จับได้คือถามอีกด้าน: *มี call site ไหนที่เครื่องมือควรรายงานแต่ไม่รายงาน*

## E.56 `Analysis` แปลครบ — และเครื่องมือแปลที่เขียนทับซอร์ส Python (2026-08-18)

`Analysis` เป็นโมดูลโดเมนที่ใหญ่ที่สุด: 313 บรรทัด → **2** และสองบรรทัดที่เหลือคือคอมเมนต์ที่ยกข้อความจาก ARCHITECTURE มาอ้าง (ข้อมูล ไม่ใช่ข้อความที่โปรแกรมแสดง) · แคตตาล็อก **294 key** ทั้ง `en` และ `th`

### สิ่งที่ต่างจากโมดูลก่อนหน้า

**ชื่อ helper** — โมดูลนี้คำนวณสถิติ และทุกเทสในนั้นเขียน `let t = …` (ค่า t) · helper ชื่อตัวเดียวจะถูก local บังหน้าจนคอมไพล์ไม่ผ่านทีละเทส → โมดูลนี้ใช้ `localised(_:_:)` เต็มคำ

**ผลข้างเคียงที่ตามมาทันที**: กฎ "ทุก call site ที่แปลแล้วต้องมี key" (U20) มองหาแค่ `t(` — พอเปลี่ยนชื่อ **ทั้งโมดูลจึงหายไปจากสายตาของกฎเงียบ ๆ** · แก้ที่ `scripts/check.sh` ให้รู้จักทั้งสองสะกด

> กฎที่ผูกกับ *ชื่อ* ของสิ่งที่มันตรวจ จะพังเงียบตอนสิ่งนั้นเปลี่ยนชื่อ — ไม่ใช่แดง แต่**เลิกตรวจ**

### กับดักที่เจ็ด — ตัวแทนข้อความไปเขียนทับ **ซอร์ส Python**

`NotebookKernel.driver` คือสคริปต์ Python ที่ฝังเป็น raw string (`#"""…"""#`) · ตัวแทนข้อความไม่รู้เรื่องนั้น จึงเปลี่ยน literal ของ **Python** สองตัวให้กลายเป็นการเรียก `localised(…)` ของ Swift → เคอร์เนลพังทั้งตัว

จับได้เพราะ **คอมไพเลอร์ไม่ emit key ให้ทั้งสองบรรทัด** (มันไม่ใช่โค้ด Swift ที่ถูกคอมไพล์) — กฎ U20 ข้อเดียวกันกับที่จับ `\(error)` เมื่อ E.53

**วิธีแก้**: raw string แปลว่า `\(…)` ใช้ไม่ได้ → เจาะช่องชื่อ `__TRUNCATED__` / `__UNREADABLE__` ไว้ในสคริปต์ แล้วแทนค่าหลังหยิบคำแปล · แทนด้วย **JSON-encoded string** เพราะ JSON string เป็น Python literal ที่ถูกต้องอยู่แล้ว — คำแปลภาษาไหนที่มี `"` หรือ `\` จึงกลายเป็นข้อมูล ไม่ใช่ตัวปิด literal ก่อนเวลา

คุมด้วยเทสที่พิสูจน์แล้วว่าแดงได้: ช่องต้องไม่เหลือค้าง **และ** ต้องรันจริงจนเลยลิมิตตัดข้อความ (300k ตัวอักษร) เพื่อให้ตัวที่ถูกแทนเป็นสิ่งที่ถูกทดสอบ ไม่ใช่สตริงที่บังเอิญมีอยู่ในซอร์ส

### กับดักที่แปด — ตัวตรวจอ่าน `.strings` โดยไม่ถอด escape

key ที่มี `"` อยู่ข้างใน (`community \"mongo\" extension`) ถูกรายงานว่า **ขาดคำแปลและมีคำแปลค้าง พร้อมกัน** — เพราะไฟล์ `.strings` *ต้อง* escape แต่รายการ key ของคอมไพเลอร์ไม่ escape · ไฟล์ถูก ตัวตรวจผิด → เพิ่มการถอด escape แบบผ่านเดียว (ผ่านสองรอบจะถอด `\\"` ซ้ำ)

เรื่องเดียวกันซ้ำอีกกับขึ้นบรรทัดใหม่: `"\n… truncated at %d characters"` — ในซอร์สเป็นสองตัวอักษร ใน key เป็นตัวเดียว ในไฟล์ต้องกลับเป็นสองตัว

### `%` เดี่ยว กับ `%%` — วัดแล้ว ไม่ใช่เดา

E.55 บันทึกไว้ว่า `%%` มีปัญหา · คราวนี้อ่าน `.stringsdata` ตรง ๆ: คอมไพเลอร์ **ส่งผ่านทั้งสองแบบตามที่เขียน** ไม่แปลงอะไร → กฎคือ **สตริงที่วิ่งผ่าน `String(format:)` ใช้ `%%`, สตริงที่ไม่วิ่งผ่านใช้ `%` เดี่ยว** · เผลอเขียน `%%` ในสองสตริงที่ไม่ใช่ format string ("Hanley–McNeil 95%% CI", "chance agreement is 100%%") ⇒ จะขึ้นจอเป็น `%%` จริง ๆ — แก้ก่อนเข้าแคตตาล็อก

- **แทนคำสั้นเกินไป**: `contains("linear")` ไปตรงกับ `"no multicollinearity"` (มี `linearity` อยู่ข้างใน) — เทสผ่านโดยจับผิดตัว ⇒ ใช้ชื่อข้อสมมติเต็ม

### กฎใหม่ U24 — ทำเครื่องหมายที่ตัวประกาศ ไม่ใช่รายชื่อในตัวตรวจ

## E.58 `Instruments` แปลครบ — และประโยคที่ต่อกันจนอ่านไม่รู้เรื่อง (2026-08-18)

`Instruments` 109 บรรทัด (โค้ด) → **0** · แคตตาล็อก **109 key** · ไม่มีตารางคำที่ใช้จับคู่ในโมดูลนี้เลย จึงเป็นการแปลตรงไปตรงมาแบบ `Analysis`

### กับดักที่เก้า — ตัวเลขต่อกับวลี แล้วไวยากรณ์พัง

```swift

```

### `\(x.joined(separator: ", "))` — เจอครบทั้งโมดูล

7 จุดใน `FactorStructure` · ตัวแทนข้อความอ่าน literal ด้วย regex จึงหยุดที่เครื่องหมายคำพูดตัวในของ `", "` · ต้องเขียนมือทั้ง 7 (เจอครั้งแรกที่ `Agreement` ใน `Analysis`, E.56)
